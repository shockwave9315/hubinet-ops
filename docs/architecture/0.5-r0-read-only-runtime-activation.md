# Hubinet Ops 0.5 — R0 read-only runtime activation design

Status: **PROPOSED**

This is a bounded runtime-activation design record, not an ADR. It does not
amend ADR 0001–0005, does not authorize any code/schema/config/deployment
change by itself, and is not self-accepted. WAVE R0-A (this document) is
design/inspection only; WAVE R0-B is the future, separately reviewed
implementation. No genuine architecture contradiction was found during this
inspection — every decision below fits inside ACCEPTED ADR 0001–0005 and
`0.5-inventory-model.md`'s Phase 1 runtime activation gate. No new ADR is
required.

## 0. Scope

R0 is the first production activation of the dormant `app.inventory`
authority in **read-only** mode: real discovery against a real Proxmox
source, a real durable SQLite authority database, and a real read-only HTTP
API consumed by the already-implemented Home Assistant integration. R0 does
not add policy, jobs, mutation, endpoint activation/failover, attestation
enrollment automation, or any path to `security_continuity=trusted`.

**Deployment model — clean break, not coexistence.** Hubinet Ops 0.5.0 is a
complete clean break from 0.4.x. The target CT110 is rebuilt from scratch
for 0.5.0; there is no side-by-side production runtime, no requirement to
keep the 0.4 systemd service alive during or after R0 activation, and no
canary/cutover coexistence period on that host. No operational state from
0.4.x is authoritative input to 0.5.0: 0.5 never migrates, reads, dual-
writes to, or falls back to the legacy operational database, the legacy
static resource model, or legacy Home Assistant entities/configuration.
Legacy 0.4 code (`app/main.py`, `app/service.py`, etc.) is inspected in
this document only to identify boundaries and dangerous components that
must never leak into the 0.5 composition root (§2) — it is not R0's
implementation foundation, and it is not something R0 needs to coexist
with at runtime. The repository itself still carries both tracks side by
side as source code (per `CLAUDE.md`'s two-track description), and this
document does not touch or delete any 0.4 file; but on the actual target
host, only the 0.5 runtime this document designs is ever installed or
running.

## 2. Fixed architecture decision #1 — separate 0.5 composition root

R0 **must not** add inventory activation into `app.main:create_app` or
`app.service:OpsService`. Confirmed by inspection: `app/main.py` imports and
instantiates `Database`, `Executor`, `ResourceExecutor`, `HostControlClient`
(when `host_control.enabled`), `MqttTelemetry`, and `OpsService` at
`create_app()`/module-import time (`app/main.py:11-17`, `43-62`, `454-455`
— `settings = load_settings(); app = create_app(settings)` executes on
import), and exposes maintenance/lifecycle/snapshot/self-update/rollback
mutation routes (`app/main.py:129-410`, e.g.
`/api/v1/resources/{vmid}/start`, `/self-update`, `/snapshots/{name}/
rollback`, `/plans/approve`). Importing `app.main` at all — even without
calling `create_app` — is unacceptable for the R0 process, because module
import already constructs a live `OpsService`.

**Design:** a new, separate composition-root module, proposed name
`app/inventory_runtime.py` (final name confirmed at R0-B implementation
time; `app/read_only_runtime.py` is an acceptable alternative — pick one
and keep it consistent with the systemd `ExecStart` module path in §6). It
exposes its own `create_read_only_app(settings) -> FastAPI` factory,
constructs exactly:

- `app.inventory.store.InventoryAuthorityStore` (opened against the R0-only
  DB path, §4);
- `app.inventory.authority.InventoryAuthority`;
- `app.inventory.publication.InventoryPublication`;
- a production `ReadOnlyProviderTransport` implementation (§9);
- an R0-only discovery scheduler (§12);
- the R0 read-only HTTP route table (§15).

**Import denylist** — the R0 composition root, its scheduler module, and
its HTTP route module must never import, directly or transitively:

```text
app.main                      (constructs OpsService at import time)
app.service.OpsService
app.service.ConflictError     (mutation-path exception type; no R0 use)
app.executor.Executor
app.executor.ExecutorError
app.resource_adapters.ResourceExecutor
app.host_control.HostControlClient
app.host_control.HostControlError
app.mqtt.MqttTelemetry
app.mqtt_budget.*
app.database.Database          (legacy 0.4 operational DB, distinct schema)
app.stabilization.*
app.ha_entities.*              (0.4 MQTT Discovery entity generator)
app.contracts.*                (0.4 mutation-path contracts, unless a
                                specific symbol is individually reviewed
                                and proven generic/no-mutation-authority —
                                prefer zero dependency)
```

Permitted imports: `app.inventory.*` in full (it is the subsystem being
activated), `app.config` **only** if a specific helper is proven generic
and config-shape-agnostic (prefer a dedicated small R0 settings loader
instead — §5 — to avoid any risk of accidentally pulling in
`Settings.executor`/`.host_control`/`.mqtt`/`.resources` legacy shape),
`app.time_utils` (29 lines, pure), `app.security` (60 lines — inspect at
R0-B time; reuse only if it is a generic constant-time-compare helper with
no legacy-token coupling), and ordinary third-party libraries (`fastapi`,
`uvicorn`, `httpx`, `pydantic`).

**Required R0-B test** (test #1 in §19): a static/import-graph test that
constructs the R0 composition root and asserts `sys.modules` (or an AST/
import scan of the R0 package) contains none of the denylisted symbols
above. This is stronger than a runtime behavior test — it fails at review
time if a future edit accidentally re-introduces a legacy import.

## 3. Fixed architecture decision #2 — final clean production process/service

R0 is designed as the **final, sole** Hubinet Ops production service on the
rebuilt CT110 — not a temporary sidecar/canary running alongside 0.4. The
0.4 production service (`deploy/hubinet-ops.service`, `app/main.py`) is not
part of the rebuilt host's target state at all; this document does not
edit, reference as a runtime dependency, or design around coexisting with
it. `deploy/hubinet-ops.service` remains, unedited, in the repository as
the historical 0.4 release-line artifact (per `CLAUDE.md`'s two-track
description) — R0-B's own new deployment file lives at its own new repo
path (e.g. `deploy/hubinet-ops-0.5.service`, §25/§29 — the repository-level
filename must differ from the existing 0.4 artifact even though the two
are never installed on the same host; what the installer copies it to on
the target host, e.g. `/etc/systemd/system/hubinet-ops.service`, is a
separate, later packaging decision and does not need to match the repo
source filename).

**Design — final 0.5 service, derived independently from 0.5's own
requirements** (not inherited from `deploy/hubinet-ops.service` as a
compatibility artifact — that file governs a different runtime with a
different threat model: it exists to eventually mediate host-control/
mutation execution, which R0 never does at all):

- Python entrypoint: `uvicorn app.inventory_runtime:app` (module name
  matches §2's chosen composition-root module) — the only entrypoint that
  exists for 0.5's read-only runtime;
- proposed unit name `hubinet-ops.service` — R0-A selects this as the
  natural, self-descriptive name for what will be the only Hubinet Ops
  service on the rebuilt host; R0-B may choose a different exact name;
- listen address/port: **`0.0.0.0:8787`** (§10/§25/§26 close this exactly
  — R0 must be reachable from a separate Home Assistant host on the
  trusted LAN, so it binds all interfaces, paired with a mandatory
  firewall policy restricting inbound access to the HA host/subnet; this
  is not left open for R0-B to decide);
- `EnvironmentFile`: proposed `/etc/hubinet-ops/agent.env` — a fresh path
  populated only with 0.5-relevant secrets (the PVE credential material,
  §7, and the R0 API bearer token, §20) on this clean install; R0-B may
  choose a different exact path;
- database file: its own new canonical path (§4);
- systemd hardening independently justified for exactly what this process
  does — accepts inbound read-only HTTP, makes outbound HTTPS calls to one
  configured PVE endpoint, and reads/writes one local SQLite file; no
  privilege, capability, or filesystem access beyond that is ever needed,
  which is what §25's specific flags are each derived from (evaluated
  fresh, not copied from any other unit's flag list);
- no `host_control` dependency (R0 never talks to hostd/forced-command,
  because R0 has no mutation authority of any kind to route through it);
- no MQTT dependency (R0 has no telemetry/command channel of that kind at
  all).

**Home Assistant** connects to the 0.5 backend via the native
`custom_components/hubinet_ops` integration as **the** Hubinet Ops
integration for that installation — not one of two integrations polling
two backends. There is no design here for HA polling both a 0.4 MQTT
Discovery presentation and a 0.5 native integration simultaneously, and no
requirement to preserve old 0.4-sourced HA entities as part of R0: the 0.5
`backend_instance_id` and its dynamically discovered inventory/resource
identities are the new, sole authority for that config entry. Any
operator-facing procedure for retiring a previous 0.4-based HA setup (MQTT
topics, the legacy `home-assistant/` package YAML) is a separate deployment
task for whoever operates that specific Home Assistant installation, not
part of the 0.5 runtime architecture and not something R0-B needs to design
compatibility for.

## 4. Fixed architecture decision #3 — separate 0.5 authority database

R0 **must not** open `/var/lib/hubinet-ops/ops.db` (or any other deployed
0.4 operational database) as its inventory authority DB. Confirmed by
inspection: `app/inventory/store.py::InventoryAuthorityStore._open_or_
initialize` already implements exactly the required fail-closed contract
with **no R0-B code needed to add it**:

- if the target path does not exist or is empty, it initializes a fresh
  schema-v5 database (`_initialize_fresh_database`: `AUTHORITY_SCHEMA_
  MARKER="hubinet_ops_0_5_authority"`, `AUTHORITY_SCHEMA_VERSION=5`, WAL
  mode, one `backend_instance` row) — this is the "empty-db initial
  bootstrap" case;
- if the target path is non-empty, `_reject_unrecognized_existing_database`
  opens it read-only first and **fails closed** (`AuthorityDatabaseRejected`)
  unless it finds the exact schema-v5 marker, exact required table/index/
  trigger set, and exactly one valid `backend_instance` row — it
  explicitly detects and names a legacy 0.4 database (`user_version==400`
  or known legacy table names) as a distinct rejection reason, and equally
  rejects a v1–v4 (or any wrong-version) 0.5 authority database;
- there is no automatic 0.4→0.5 migration, no automatic v4→v5 migration, no
  dual-write, and no fallback to any legacy DB — none of these exist in the
  store's code, and none may be added by R0-B.

**Selected 0.5 DB path:** `/var/lib/hubinet-ops/authority.db` — the
canonical clean-install path on the rebuilt host. There is no legacy 0.4
database file to avoid on that host (it was never installed there), so
this is a clean naming choice, not a collision-avoidance one; R0-B may
choose a different exact filename as long as it is documented and stable.
R0-B configures this path through the R0 settings surface (§5), never
hardcodes it, and the store's own already-implemented fail-closed logic
(above) is the enforcement mechanism — it independently detects and
rejects a legacy-shaped database by content/marker even if a path were
ever mistakenly reused, so this is defense in depth beyond the clean-path
choice itself, not a substitute for it. R0-B adds no new validation of its
own, only wiring.

**Restart behavior on a non-empty authority DB:** governed entirely by
`_reject_unrecognized_existing_database`/`_validate_schema` above — a
matching schema-v5 database with the expected `backend_instance_id` (once
one has been created) opens normally and R0-B's startup recovery (§13)
proceeds from durable state. A schema-v5 database whose `backend_instance_
id` does not match an operator's expectation is not separately detected by
the store (it has no concept of an "expected" `backend_instance_id" — it
accepts any valid one) — this is intentional and correct: the *R0 process*
supplies the DB path, and a distinct backend needing a distinct DB gets a
distinct path/file, by construction, not by an in-DB identity check the
store must perform. R0-B's own settings/bootstrap layer never overwrites or
merges files; it either creates fresh at an empty path or fails to start on
any mismatch it can independently detect (§8, e.g. configured provider_kind
implying a source that does not durably exist for the current
`backend_instance_id`'s only permitted source — see §5).

**Filesystem ownership/permissions:** directory `/var/lib/hubinet-ops/`
owned by the R0 service's own dedicated system user/group (`hubinetops`,
matching the clean-install convention — there is no other Hubinet Ops
service account on this host to distinguish it from), mode `0750`;
`authority.db`/`authority.db-wal`/`authority.db-shm` mode `0640`. Systemd
`ReadWritePaths=/var/lib/hubinet-ops` only; `ReadOnlyPaths` covers the R0
`EnvironmentFile` directory and the R0 application code directory (§25).

## 5. Source bootstrap / configuration contract

**No static resource configuration, by design.** The R0 bootstrap surface
configures exactly one thing: how to identify and reach a Proxmox
*source*. It contains no configured list of VMIDs, LXC containers, QEMU
VMs, node membership, guest names, guest IP addresses, or resource types
per VMID — none of that exists in the config file this section defines,
and none of it is accepted by `InventoryAuthority.create_inventory_source`
either (its parameters are source-level only: `provider_kind`, `display_
name`, `credential_reference`, `transport_locator`, `freshness_duration_
seconds`, `provider_contract_version` — confirmed by direct inspection,
§1 item 5's evidence). After source bootstrap, every node, LXC resource,
QEMU resource, and their current node placement is discovered dynamically
through the already-implemented GET-only provider/discovery/reconciliation
chain (§11) — new resources appearing later are discovered automatically
on the next scheduled run (§12), and resources disappearing/reappearing/
being replaced follow ADR 0001/0002/0004 semantics exactly (§13/§15),
never a static configuration change. This mirrors the legacy 0.4 model's
static `resources:` VMID map (`config/config.example.yaml`) in exactly the
opposite direction — R0 deliberately has no equivalent of it.

**Minimum production source-bootstrap contract**, closed explicitly:

- **Configuration surface:** a small, R0-dedicated YAML file (e.g. `/etc/
  hubinet-ops/inventory.yaml`) plus an `EnvironmentFile` for secrets
  (`/etc/hubinet-ops/inventory.env`), read by a new, narrow R0 settings
  loader — **not** `app.config.load_settings`/`Settings` (that type's shape
  is defined by, and coupled to, the legacy mutation runtime: `executor`,
  `host_control`, `mqtt`, `resources`, `home_assistant.webhook_url`, none of
  which R0 needs or should parse). The R0 loader's own shape is an R0-B
  implementation detail, but its *content* is fixed by this section.
- **One source vs. multiple:** R0-A selects **exactly one statically-
  configured source for the initial R0-B implementation.** The durable
  authority already supports multiple sources (`InventoryAuthorityStore`/
  `InventoryAuthority` have no single-source assumption — `list_source_
  states()`, `create_inventory_source()` are all source-parameterized), so
  this is a scope decision for the *initial* R0-B package, not an
  architecture limitation. Multi-source bootstrap (a YAML list instead of a
  single source block) is a small, well-understood follow-up once one
  source is proven end-to-end; R0-B should not block on it.
- **Source display name:** required config field, passed through to
  `create_inventory_source(display_name=...)` unchanged (validated non-
  empty, ≤300 chars by the authority itself — no separate R0 validation
  needed beyond surfacing a clear startup error).
- **Provider kind:** fixed literal `"proxmox_ve"` (or an equivalently fixed
  string) for R0-B's only supported provider; passed through to
  `create_inventory_source(provider_kind=...)`.
- **Initial active endpoint:** the configured PVE transport locator (e.g.
  `https://pve.example.internal:8006`), canonicalized via `app.inventory.
  canonicalization.canonicalize_transport_locator` before comparison/use —
  this is the one and only case ADR 0002 already accepts creating an active
  endpoint directly (`create_inventory_source`'s atomic initial-endpoint
  insert, §1 item 5); R0-B must not invent a second such case (§6).
- **Configured freshness duration:** required integer seconds, passed to
  `create_inventory_source(freshness_duration_seconds=...)`
  (`InventoryAuthority` default is 300 if omitted — R0-B should require an
  explicit operator value rather than silently relying on the library
  default, for production clarity).
- **Provider contract version:** fixed to `app.inventory.provider.
  PROVIDER_CONTRACT_VERSION` (currently `1`); not operator-configurable —
  the authority itself rejects any other value (`create_inventory_source`
  raises `ValueError` if `contract_version != PROVIDER_CONTRACT_VERSION`).
- **Credential reference:** an **opaque, non-secret** string identifying
  *which* credential is currently in effect (e.g. a version tag, a KMS/
  secret-manager reference ID, or a stable hash-of-secret computed once at
  rotation time and never re-derived from the live secret at every
  startup) — never the PVE API token itself. This is the field
  `InventoryAuthority.create_inventory_source(credential_reference=...)`
  and `rotate_credential_reference(...)` already accept and store durably;
  R0-A does not invent a new field, it specifies what R0-B must put in the
  existing one (§7 closes the exact rotation contract).
- **Credential material loading:** the actual PVE API token is read only
  from the `EnvironmentFile` (`/etc/hubinet-ops/inventory.env`, e.g.
  `HUBINET_OPS_R0_PVE_TOKEN=...`) at process startup, held only in process
  memory, and passed directly to the production transport's HTTP client
  construction (§9) — never written to the authority database, never
  logged, never included in any discovery-run row, source-facts JSON, or
  published view (confirmed: `InventorySource.credential_reference` is the
  only credential-shaped authority field, and `InventoryPublication._
  source()` does not even project `credential_reference` into the published
  view at all — the HA-facing contract has no field for it whatsoever).
- **TLS verification policy:** mandatory strict verification against a
  configured trusted CA bundle for the PVE endpoint (§9/§10) — no
  operator-facing "skip verification" flag in R0-B's initial source-
  bootstrap config.
- **`transport_trust_revision` initialization:** entirely owned by
  `create_inventory_source`'s atomic initial-endpoint insert (`transport_
  trust_revision=1`, `canonicalization_contract_version=CANONICALIZATION_
  CONTRACT_VERSION`) — R0-B does not set this itself.
- **`source_attestation_epoch` initial state:** entirely owned by
  `_insert_initial_attestation_state` (`not_yet_attested`, epoch `0`) —
  confirmed already correct and untouched by R0 (§14).
- **Bootstrap behavior on an empty authority DB:** R0-B startup, after the
  store opens (§4) and finds zero rows in `inventory_sources`, calls
  `InventoryAuthority.create_inventory_source(...)` exactly once with the
  configured values above, then proceeds to discovery-run issuance (§13)
  as normal.
- **Restart behavior on a non-empty authority DB (source already exists):**
  R0-B startup finds exactly one existing `InventorySourceState` (single-
  source scope, this wave) and **does not** call `create_inventory_source`
  again. It instead compares the durable source's current configuration
  against the freshly-loaded R0 config (§8) and either proceeds unchanged,
  applies an explicitly-permitted controlled transition (credential
  rotation, §7; freshness-duration change via `configure_freshness_
  duration`), or fails closed (§8) if the drift is not one of those
  explicitly-permitted transitions.

## 6. Bootstrap is not endpoint failover

Initial source creation (§5) is the **only** allowed initial active-
endpoint exception ADR 0002 accepts. After a source durably exists, R0-B
must not:

```text
- replace the active endpoint because config changed;
- auto-create a new active endpoint;
- activate a candidate endpoint;
- reactivate a historical (retired/inactive) endpoint;
- fail over to another endpoint;
- select a different cluster member as the active endpoint;
- rewrite the endpoint URL in place (i.e. mutate canonical_transport_
  locator on the existing active SourceEndpoint row).
```

None of the durable authority's exposed methods perform any of the above
(`InventoryAuthority` has no `activate_endpoint`/`replace_endpoint`/
`failover` method at all — confirmed by the full method inventory in §1
item 5's evidence and the `authority.py` grep in this review) — so this
section is a *usage* constraint on R0-B, not a gap in the authority layer.

**Restart / config-drift handling — conservative expected behavior:**

```text
IF a durable source/active-endpoint identity already exists
AND the R0-B startup configuration's canonicalized transport locator
    does not exactly equal the durable active endpoint's
    canonical_transport_locator
THEN: FAIL CLOSED at startup with an explicit configuration_error-class
      log/exit — do not start discovery, do not silently adopt either
      value, do not create a second source or endpoint.
```

The only two configuration changes R0-B may apply automatically at
startup, because ADR 0002/0003 already define them as explicit controlled
transitions with their own durable authority methods, are: (a) credential
reference drift (§7, via `rotate_credential_reference`) and (b) freshness-
duration change (via `configure_freshness_duration`) — both require
`_require_no_active_run` first (§13 covers ensuring that precondition via
startup recovery), and both are visibly, durably audited as `controlled_
context_transition` health-origin events, never silent. Any other observed
drift (display name, provider kind, transport locator, provider contract
version) is **not** wired to an automatic transition in this design and
must fail closed; `rename_inventory_source` exists for display-name-only
changes but R0-B does not call it automatically from config drift — that
would blur "config drift" with "operator-intended rename," which is exactly
the ambiguity this section forbids resolving silently.

## 7. Credential rotation / `source_config_revision`

This is load-bearing, per the mission brief, and is now closed:

- **Durable value representing credential version/reference:** the existing
  `InventorySource.credential_reference` field (already implemented,
  already stored, already rotatable via `InventoryAuthority.rotate_
  credential_reference(inventory_source_id, credential_reference)`, which
  is a no-op if the value is unchanged and otherwise atomically updates the
  column, bumps `source_config_revision`, and marks `controlled_context_
  transition` — §1 item 8's evidence). No new field is introduced.
- **What startup compares:** the durable `credential_reference` (read from
  the existing source row) against the R0-B-computed reference derived from
  the *currently configured* credential material (§5's "credential
  reference" bullet — e.g. an operator-set version tag in the R0 config
  file, changed by the operator whenever they rotate the underlying
  secret in the `EnvironmentFile`). R0-B never derives the reference by
  hashing the live secret at every startup (that would make "same secret"
  vs. "rotated secret" indistinguishable from "restarted after no change"
  only by accident of hash determinism, and would put secret-derived data,
  even hashed, into a durable audit trail unnecessarily) — the reference is
  an **explicit, operator-controlled value**, set alongside the secret
  material itself, exactly as the mission's own suggested minimal contract
  proposes.
- **What happens when it differs:** R0-B startup calls `rotate_credential_
  reference` (after startup recovery has ensured no active run — §13),
  which atomically updates the stored value and bumps `source_config_
  revision`; the *next* discovery run naturally picks up the new revision
  as its `expected_source_config_revision` and the new secret material is
  used for the transport's authentication (§9) from that point on. No
  discovery run is issued, retried, or "continued" under the old revision
  with new secret material — the two are the same event, since only new
  runs happen after this startup-time reconciliation.
- **Does R0 support rotation at all?** Yes — via this exact restart-time
  mechanism. There is no live/in-band HTTP credential-update endpoint (the
  mission explicitly forbids one, and R0's HTTP API is read-only-only,
  §15) — rotation is an **operator restart-time procedure**: update the
  `EnvironmentFile` secret and the config-file credential reference
  together, then restart the R0 service. This is intentionally the
  smallest robust solution: it reuses an already-accepted, already-tested
  authority method with no new mutation-authority surface, at the cost of
  requiring a restart to rotate (an entirely acceptable cost for a read-
  only inventory service with no live traffic depending on zero-downtime
  credential swaps).
- **Fail-closed operator procedure if unsupported paths are attempted:**
  N/A for rotation itself (it is supported, as above); for any *other*
  drift (§6), the fail-closed startup error message must name the exact
  mismatched field so the operator can either revert their config change
  or perform the correct explicit procedure (rotation via restart, or — for
  anything else — accept that changing it requires a fresh source, which
  is an operator/product decision the current design does not automate,
  consistent with "bootstrap is not failover," §6).

## 8. Startup configuration-drift decision sequence

Consolidating §5–§7 into one exact startup order for R0-B:

```text
1. open the R0 authority DB (fail closed per §4 if invalid/mismatched);
2. if inventory_sources is empty: create_inventory_source per §5, done —
   proceed to step 5;
3. if inventory_sources has exactly one source: load its InventorySourceState;
4. perform startup discovery-run recovery (§13) BEFORE any configuration
   comparison, so _require_no_active_run-gated transitions (credential
   rotation, freshness change) can proceed;
   then compare durable state against configured state field-by-field:
     - canonical_transport_locator mismatch -> FAIL CLOSED (§6);
     - provider_kind / provider_contract_version mismatch -> FAIL CLOSED;
     - credential_reference mismatch -> rotate_credential_reference (§7);
     - freshness_duration_seconds mismatch -> configure_freshness_duration;
     - display_name mismatch -> FAIL CLOSED (not an automatic transition,
       per §6's own reasoning -- an operator who intends a rename can be
       given a distinct, explicit R0-B operator procedure later; this
       design does not silently rename on config drift);
5. start the discovery scheduler (§12).
```

`inventory_sources` containing more than one row is out of scope for the
initial R0-B package (§5, single-source decision) — if R0-B's own future
multi-source support is added, this sequence generalizes per-source with
no change to the per-source logic above.

## 9. Production PVE transport implementation strategy

**Selected: a narrow, synchronous `httpx.Client`-based adapter implementing
`app.inventory.provider.ReadOnlyProviderTransport` exactly** (the protocol
requires only `get(path, *, params=...)`, and `ProxmoxProviderV1.require_
get_transport` already actively rejects any transport object exposing a
callable `post`/`put`/`patch`/`delete`/`request` attribute — confirmed in
`provider.py:222-230` — so the adapter class must genuinely not define
those methods, not merely avoid calling them).

**`httpx` is already a pinned repository dependency** (`requirements.txt`:
`httpx==0.28.1`), so no new dependency is required. R0's adapter uses
`httpx.Client`, not `httpx.AsyncClient` — this is dictated entirely by
0.5's own `ReadOnlyProviderTransport` protocol shape (`get(path, *,
params=...)` is `def`, not `async def` — `app/inventory/provider.py:45-48`),
not by any precedent elsewhere in the repository: the adapter must be
synchronous to satisfy the protocol it implements.

**Sync-vs-async boundary — explicit, not casual.** The entire `app.
inventory` provider/discovery/authority contract is synchronous by design
(`ReadOnlyProviderTransport.get` is `def`, not `async def`; `InventoryAuthority`
methods are plain synchronous methods over a synchronous `sqlite3`
connection). R0-B must **not** rewrite this contract as async merely
because FastAPI/uvicorn are async-native. Instead:

- the discovery scheduler (§12) runs the entire synchronous call chain

  the initial single-source package), never on the asyncio event loop
  thread;
- the FastAPI read-only HTTP routes (§15) that need to call `Inventory
  Publication.read()` (also synchronous, over `sqlite3`) do so via
  `starlette.concurrency.run_in_threadpool` (or `anyio.to_thread.run_sync`)

## 10. PVE URL/TLS context vs. HA↔Hubinet Ops transport

These are explicitly two different trust relationships and must never be
conflated:

**PVE endpoint TLS** (§9): governed entirely by the source's own durable
`canonical_transport_locator` (canonicalized, HTTPS-only, no userinfo, no
path/query/fragment — `canonicalization.py`), `canonicalization_contract_
version`, and `transport_trust_revision`; every discovery run captures and
CAS-checks this exact context (§1 items 6–7). This is a machine-to-machine
(Hubinet Ops backend → Proxmox) relationship with its own credential (§9)
and its own certificate trust decision (§9's CA-bundle option).

**HA → Hubinet Ops API TLS**: the native integration already accepts
`base_url` + `api_token` + `verify_tls` as three independent config-flow
fields (`custom_components/hubinet_ops/const.py`: `CONF_BASE_URL`, `CONF_
API_TOKEN`, `CONF_VERIFY_TLS`, default `True`), entirely separate from
anything PVE-related — HA never sees a PVE URL, PVE credential, or PVE TLS
setting, by construction (the contract layer has no field for any of them,
confirmed in §16/§20's field-mapping table).

**R0-A's supported initial deployment shape decision:** R0-B's initial
target is Home Assistant running on a **separate host/VM on the same
trusted LAN** as R0 — this is the realistic default topology for a self-
hosted Proxmox environment (Home Assistant and Proxmox/CT110 are commonly
different machines), and R0-A treats it as the primary supported shape
rather than an edge case. A self-hosted read-only inventory backend
consumed by a single Home Assistant instance on the operator's own trusted
network does not need R0 itself to terminate TLS to be reasonably secure.
R0-A therefore selects, as an explicit, fully closed product/deployment
decision (not an accidental default and not deferred to R0-B):

```text
R0 listens on an address reachable from the HA host (SS25's default:
  0.0.0.0, i.e. all interfaces -- never hardcoded to loopback-only, since
  a loopback-only bind would make R0 unreachable from a separate HA host,
  which is exactly the supported topology above)

reachability is bounded by network/firewall policy, not by the bind
  address alone: inbound access to R0's listen port is restricted to the
  HA host/subnet by host or network firewall (SS26) -- this pairing
  (reachable bind address + restrictive firewall) is the one selected,
  internally consistent posture, not a menu of options

plain HTTP is the supported initial transport for R0's own listen socket,
  on a trusted LAN, exactly as originally decided -- R0 does not invent
  TLS termination for itself

an operator-added reverse proxy remains an OPTIONAL upgrade path for
  encrypted HA<->R0 transport, never a mandatory prerequisite for the
  initial supported deployment
```

`verify_tls` in the HA config flow governs trust of a reverse proxy's
certificate when one is added; it is a no-op (and should default to
matching the plain-`http://` `base_url`, §21) for the initial, directly-
reachable-over-LAN deployment. This matches the config flow's own
`TextSelectorType.URL` field, which already accepts either `http://` or
`https://` (`config_flow.py:82`, scheme restricted to `{"http", "https"}`)
with no code change required. If a future review decides R0 should
terminate TLS itself, that is a separate, explicit follow-up — not
silently assumed here. §25 (systemd unit), §26 (firewall requirement),
and §31 (Remaining UNKNOWNs) are all updated to agree with this exact
decision — none of them leaves the bind-address/topology choice open.

## 11. Discovery orchestrator — exact production call chain

```text
scheduler trigger (SS12)
  -> InventoryAuthority.issue_discovery_run(source_id, PROVIDER_CONTRACT_VERSION)
       [captures expected_source_config_revision, expected_endpoint_id,
        expected_canonical_transport_locator,
        expected_canonicalization_contract_version,
        expected_transport_trust_revision, expected_source_attestation_epoch;
        atomically claims active_discovery_run_id; allocates
        discovery_run_sequence]
  -> InventoryAuthority.mark_discovery_run_running(source_id, run_id)
  -> [OUTSIDE any DB transaction] production transport I/O:
       ProxmoxProviderV1.collect_boundary_baseline(transport, ...)
       ProxmoxProviderV1.collect_guest_baseline(...) (folded into the above)
       -> BoundaryBaselineResult
  -> NormalizedDiscoverySnapshot.from_provider_baseline(...)
       [pure construction/validation, no DB, no I/O]
  -> IF successful/COMPLETE:
       InventoryAuthority.finalize_successful_discovery_run(source_id, run_id, snapshot)
         [internally: InventoryReconciler.reconcile() inside the same
          transaction, health/freshness update, run completion, global
          revision bump -- SS1 item 15/16/18]
     IF failed/not COMPLETE:
       InventoryAuthority.finalize_failed_discovery_run(source_id, run_id,
         completion_evidence=DiscoveryRunCompletionEvidence.from_snapshot(
           snapshot_or_partial_evidence), reason=...)
  -> (read side, independent of the above, triggered by HTTP GET, SS17)
       InventoryPublication.read()
         [materializes due expiry in the same transaction, then assembles
          one consistent PublishedInventoryView]
```

No second reconciliation owner is introduced — `InventoryReconciler` inside
`finalize_successful_discovery_run` remains the **only** reconciliation
call site R0-B ever invokes. R0-B's scheduler module is a thin orchestrator
over this exact existing chain; it must not bypass `active_discovery_run_
id`/`last_issued_run_sequence`/`last_committed_run_sequence`/`source_
config_revision`/`endpoint_id`/canonical locator+version/`transport_trust_
revision`/`source_attestation_epoch` CAS at any point — all of that is
already enforced *inside* the authority methods above, so "not bypassing"
means simply: never touch `discovery_runs`/`inventory_sources`/`resource_
incarnations`/etc. tables directly from R0-B code; always go through
`InventoryAuthority`.

## 12. Scheduler

**Design: the smallest safe scheduler** — a single background thread (or,
if R0-B later needs true multi-source concurrency, one thread per source,
still each fully independent) driving the exact call chain in §11 on a
timer, with no framework beyond the standard library (`threading.Timer`/
`threading.Thread` + a stop `Event`) or, if preferred for readability,
`apscheduler`'s `BackgroundScheduler` — either is acceptable; R0-B should
pick whichever keeps the import surface smallest and avoids pulling in any
scheduler previously coupled to legacy mutation jobs (`app.service`'s
internal scheduler is explicitly **not** reused — different concern,
different failure domain, and reusing it would violate the composition-root
denylist in §2).

Requirements, closed:

```text
only read-only discovery                 -- the scheduler's only job body is
                                             SS11's chain; it never calls any
                                             mutation-shaped authority method
                                             (confirm_class_c_resource_
                                             removal, enroll_source_
                                             attestation, etc. -- SS14/SS15)
per-source single-flight                 -- already enforced durably by
                                             issue_discovery_run's CAS (SS1
                                             item 11); the scheduler additionally
                                             must not even attempt a second
                                             issuance for a source whose
                                             previous run it knows is still
                                             in flight (an in-process guard is
                                             a performance/clarity nicety, not
                                             the security boundary -- the
                                             durable CAS is)
independent multi-source scheduling      -- if/when multi-source is added
                                             (SS5), each source's timer/thread
                                             runs independently; a slow/failed
                                             source never blocks another
                                             source's schedule
no mutation jobs                         -- confirmed by SS2's import denylist
no maintenance scheduler                 -- not imported/reused (app.service's
                                             monitoring_scheduler is legacy-only)
no legacy monitoring scheduler           -- same
no MQTT scheduler                        -- R0 has no MQTT dependency at all
no endpoint failover                     -- confirmed by SS6
no attestation scheduler                 -- confirmed by SS14 (attestation
                                             remains fully manual/dormant)
no Class-C confirmed-removal automation  -- confirmed by SS15
```

**Timing decisions:**

- **initial discovery timing after startup:** immediately after the
  startup sequence in §8 completes (i.e. as soon as the source's active
  run is known-clear and any config-drift transition has been applied) —
  a short fixed delay (e.g. 5–10 seconds) is acceptable for orderly
  process warm-up but is not architecturally required;
- **periodic interval:** operator-configured per source (R0's own config
  surface, §5) — a single global default is acceptable for the initial
  single-source package, but the *authority-level* freshness contract
  (`freshness_duration_seconds`, already a per-source durable field) is
  the actual security-relevant timer; the scheduler's polling interval
  should be configured comfortably shorter than `freshness_duration_
  seconds` so successful discovery ordinarily keeps the source `fresh`
  (this is an operational tuning relationship, not a new invariant — the
  authority already fails closed to `stale` via `_materialize_due_expiry_
  in_transaction` regardless of what the scheduler does);
- **overlap behavior:** impossible to overlap for a given source by
  construction — `issue_discovery_run`'s CAS on `active_discovery_run_id`
  makes a second concurrent issuance for the same source fail with
  `AuthorityConflict`; the scheduler should catch and log that
  (extremely unlikely in a correctly single-threaded-per-source design,
  but must not crash the process if it somehow races);
- **shutdown behavior:** on SIGTERM, the scheduler stops issuing *new*
  runs; an in-flight run is allowed to reach its own natural finalize
  (success/failure) if that completes within a bounded shutdown grace
  period, otherwise the process exits and the run is picked up by startup
  recovery (§13) on next start — R0-B must not attempt to force-abandon a
  running discovery run mid-shutdown from a signal handler (that would
  race the run's own finalize path); relying on §13's already-designed
  recovery is simpler and equally correct;
- **exception handling:** any exception raised by the transport, provider,
  or authority layer during one scheduled cycle is caught, logged, and
  classified into the appropriate `finalize_failed_discovery_run` call
  where possible (transport/provider errors already map cleanly via
  `ProviderFailureKind`/`classify_provider_failure`); an exception that
  occurs *before* `issue_discovery_run` succeeds (e.g. the scheduler
  itself is misconfigured) is not a discovery-run failure at all — it is
  logged and the next scheduled attempt proceeds normally, since no run
  was issued to need finalizing;
- **manual read-only discovery trigger:** R0-A recommends **omitting** an
  HTTP-exposed manual-trigger route from the *initial* R0-B package. It is
  not required by any of the 40 tests in §19, it adds HTTP-API surface
  that must itself be reasoned about (auth, rate-limiting, idempotency),
  and the periodic scheduler already satisfies R0's purpose. If a future
  package adds one, it must (a) only ever call the exact same `issue_
  discovery_run` → ... → `finalize_*` chain in §11, never a shortcut, and
  (b) never bypass the durable single-flight CAS — a manual trigger racing
  the scheduler's own timer must cleanly lose (`AuthorityConflict`) exactly
  like two scheduler ticks would.

## 13. Crash / restart / abandoned-run recovery

Durable authority support already exists and is exercised by
`tests/test_inventory_run_authority.py` (§1 items 11/16): `DiscoveryRun
Lifecycle` = `issued`/`running`/`completed`/`abandoned`; `InventorySource.
active_discovery_run_id` durably names the exact current owner (or `NULL`);
`InventoryAuthority.abandon_discovery_run(source_id, run_id, reason=...)` is
the exact, already-implemented, one-time fence-and-release method (§1's
evidence, `authority.py:287-328`) — it requires exact ownership match
(`_require_exact_run_owner`) and only succeeds against a non-terminal run,
so it cannot double-abandon or abandon the wrong run.

**Exact R0-B startup recovery (step 4 of §8, expanded):**

```text
for the (single, this wave) configured source:
  read InventorySourceState via store.source_state(source_id)
  IF source.active_discovery_run_id is not None:
    run = store.discovery_run(source.active_discovery_run_id)
    IF run.lifecycle in {ISSUED, RUNNING}:
      InventoryAuthority.abandon_discovery_run(
        source_id, run.run_id, reason="r0_startup_recovery"
      )
    # if lifecycle is already COMPLETED/ABANDONED but active_discovery_
    # run_id is still set, that is an authority invariant violation the
    # store itself would already refuse to construct -- not a case R0-B
    # needs to additionally handle; _release_run/_complete_run always
    # clear active_discovery_run_id together with terminalizing the run
  # active_discovery_run_id is now guaranteed NULL for this source
  proceed to configuration-drift comparison (SS8) and then scheduling (SS12)
```

This satisfies every required property without any raw SQL or invented
mechanism:

- **stale active ownership never permanently bricks the source** —
  `abandon_discovery_run` unconditionally clears it (subject to owning the
  exact run, which startup always does since it read the source's own
  pointer);
- **old worker/result never becomes eligible again** — the abandoned run's
  `lifecycle` becomes `abandoned`, and every later authority method that
  checks `_require_nonterminal_run`/`_require_exact_run_owner` rejects any
  attempt to finalize it after the fact (an old, now-dead worker process
  that eventually *does* try to call `finalize_successful_discovery_run`
  for that same `run_id` after a restart already recovered it will get
  `AuthorityConflict` from `_require_exact_run_owner`, since the source's
  `active_discovery_run_id` no longer points at it);
- **sequence numbers are never reused** — `last_issued_run_sequence` only
  ever increments (`issue_discovery_run`'s CAS), and abandonment does not
  roll it back;
- **no fabricated successful observation** — `abandon_discovery_run` never
  calls `InventoryReconciler`/writes to `resource_incarnations`; it only
  terminalizes the run row;
- **no fabricated absence** — same reasoning; reconciliation (the only code
  path that can mark resources `missing`) never runs for an abandoned run;
- **no automatic confirmed removal** — confirmed separately and
  unconditionally in §15; abandonment has nothing to do with Class-C at
  all;
- **health/freshness outcome matches the accepted contract** —
  `abandon_discovery_run` does not touch `source_runtime_health` at all
  (confirmed: no `source_runtime_health` write in its body, §1's evidence)
  — the source's health/freshness simply remains whatever it durably was
  before the crash (likely already `stale`/`not_yet_observed` if this is
  the very first run, or the last successfully committed value otherwise);
  the *next* successful discovery run naturally refreshes it through the
  ordinary `finalize_successful_discovery_run` path.

No new durable authority behavior is required for this — it is 100%
already-implemented and tested; R0-B's job is exactly the eight-line
startup-recovery orchestration above, using only the public `Inventory
Authority`/`InventoryAuthorityStore` methods already listed in §1.

## 16. Blocker B during R0

ADR 0005 is **ACCEPTED** as the negative stock-PVE trust boundary. R0
provides **no** path to `security_continuity=trusted`, by construction, on
both sides of the boundary:

- **Backend/authority side:** `InventoryReconciler` (§1 item 10's evidence,
  `reconciliation.py:75-233`) hardcodes every newly created or replaced
  resource's `security_continuity` to the literal string `'unverified'` —
  there is no code path in `app.inventory` that writes `'trusted'`
  anywhere at all (confirmed by inspection of `reconciliation.py` in
  full — the only two `security_continuity` values ever written are
  `'unverified'` at creation and `'revoked'` at the various terminal/
  gap-return transitions). No future stronger-proof mechanism exists yet
  (ADR 0005 §13/§14), so this is not merely "R0 doesn't call it" — the
  *mechanism to call* does not exist in the codebase at all.
- **Publication side:** `InventoryPublication._resource` (§1 item 13's
  evidence) additionally, independently, hardcodes `retained_policy={}`,
  `effective_policy={}`, `policy_applicable=False`, `effective_
  capabilities=()` for every published resource, regardless of stored
  `security_continuity` — so even a hypothetical future durable `trusted`
  value would *still* publish zero effective capabilities until a
  separate, later, explicitly-reviewed policy/capability computation
  package exists. This is defense in depth beyond what ADR 0005 strictly
  requires of R0, and R0-B must not remove or "improve" it prematurely.
- **HA presentation side:** the contract's `SecurityContinuity` enum
  includes `TRUSTED` as a member (it must, to represent ADR 0001's full
  vocabulary structurally), but nothing in `coordinator.py`/`entity.py`/
  `sensor.py` computes or infers trust locally — every resource's
  `security_continuity` displayed in HA is whatever string the backend
  published, and (per the above) the backend never publishes `'trusted'`
  under R0. `resource_validation.py`'s state-matrix checks additionally
  ensure a malformed/self-contradictory combination (e.g. `trusted` paired
  with a state the matrix forbids) is rejected outright rather than
  silently displayed.

**Required R0-B tests** (§19 #27/#28): an end-to-end assertion that, across
the full discovery→reconciliation→publication→HTTP→HA round trip using a
realistic fixture (new resource, renamed resource, replaced resource,
resource returning from a gap), `security_continuity` is never observed as
anything other than `unverified`/`revoked`, and `effective_capabilities` is
always empty, at every layer of that pipeline.

## 18. HTTP GET may materialize local expiry — documented correctly

`InventoryPublication.read()` calls `InventoryAuthority._materialize_due_
expiry_in_transaction` for every source **before** assembling the returned
view (§1 item 19's evidence, `publication.py:60-75`). This means an
ordinary R0 HTTP `GET` request can cause an authorized **local** authority-
state transition — a source whose freshness deadline has silently elapsed
since the last discovery run is durably flipped from `fresh` to `stale`,
`health_origin='time_expiry'`, as part of servicing that very GET, before
the response is returned. This is entirely by design (§1 item 19) and must
be documented, not "fixed": R0-B must not move this materialization into
HA-side freshness calculation (that would violate the accepted "HA never
reconstructs backend-owned expiry" invariant, `hubinet-phase-boundary`
skill), and must not treat this write as evidence that R0 is somehow a
Proxmox-mutating runtime — it never touches Proxmox, never touches
`resource_incarnations`, and only ever transitions a source's own
`freshness`/`health_origin`/`health_reason` columns plus the two global
revision counters, exactly as ADR 0002's accepted freshness contract
requires. The backend remains the sole authority for this decision; R0-B's
HTTP route simply calls `InventoryPublication.read()` as-is.

## 19. Read-only HTTP API

**Exact versioned route table**, minimal, matching the mission's stated
minimum (HA logical equivalents of `validate_connection`, `fetch_backend_
information`, `fetch_resource_snapshot`):

```text
GET  /r0/v1/health              -- liveness only, see auth decision below
GET  /r0/v1/backend             -- BackendInformation (validate_connection
                                    AND fetch_backend_information share this
                                    one route/shape; "validate_connection"
                                    on the HA transport side is simply "call
                                    this route and require 2xx + a well-
                                    formed body" -- no separate backend
                                    behavior is needed for the two distinct
                                    HubinetOpsTransport methods)
GET  /r0/v1/snapshot            -- HubinetOpsSnapshot (the full published
                                    view, SS17/SS20)
```

The `/r0/v1/` prefix (or an equivalent explicit versioned prefix R0-B may
choose, e.g. `/api/inventory/v1/`) is selected purely on 0.5's own terms:
it names what the API actually is (a read-only inventory snapshot API,
distinct in kind from a future mutation/policy API this backend may
eventually add), and it carries an explicit version segment so a later,
incompatible 0.5 API revision has a clean place to land without breaking
this one. The choice is not, and does not need to be, justified by any
relationship to the legacy `/api/v1/` prefix `app.main` uses — 0.5 has no
active 0.4 route to avoid colliding with, and no shared reverse-proxy
deployment between an active 0.4 and 0.5 backend is part of this design
(§0/§3).

**No mutation verbs anywhere in the R0 app.** The R0 FastAPI application
must define no `POST`/`PUT`/`PATCH`/`DELETE` route of its own. FastAPI's
own framework-internal behaviors (e.g. automatic `OPTIONS`/`HEAD` for
defined `GET` routes, the `/docs`/`/openapi.json` introspection routes) are
not "mutation routes" and may remain, but R0-B should still disable
`/docs`/`/redoc` in production (`docs_url=None, redoc_url=None`) as a
minimal-surface hardening choice matching AGENTS.md's minimal-exposure
posture, distinct from — and not required by — the mutation-verb ban
itself.

**Required R0-B test** (§19 test #2 below): an application-level test that
enumerates every route FastAPI has registered on the R0 app instance
(`app.routes`, checking `route.methods`) and asserts the only HTTP methods
present anywhere are `GET`/`HEAD`/`OPTIONS` (and, if `/docs` is left enabled
in a non-production test build only, its own internal routes) — never
`POST`/`PUT`/`PATCH`/`DELETE`.

**Health/liveness route decision:** `GET /r0/v1/health` is **unauthenticated**
and returns the smallest possible body proving the process is alive and the
authority DB is reachable — e.g. `{"status": "ok"}` on success, non-2xx
otherwise. It must **not** include `backend_instance_id`, revision numbers,
source names, or any other fact from the published view (that all lives
behind the authenticated `/r0/v1/backend` and `/r0/v1/snapshot` routes) —
this keeps the one intentionally-unauthenticated route's information
content to the bare minimum needed for a load-balancer/systemd health probe.

## 20. Backend API auth

**Design, distinct from the PVE API token (§9) — never mixed:**

- **Secret source:** a bearer token read once at startup from R0's own
  `EnvironmentFile` (e.g. `HUBINET_OPS_R0_API_TOKEN=...`) — an independent
  0.5 secret, never the PVE token (§9) and never derived from or shared
  with any other system.
- **Minimum format/length:** operator-generated, required non-empty,
  recommended minimum 32 bytes of entropy (documented in the R0 config
  guidance; mechanical enforcement of exact entropy is not required for
  this design to be sound, since the credential is opaque and operator-
  controlled either way).
- **Constant-time compare:** `hmac.compare_digest(authorization_header,
  f"Bearer {expected_token}")` — a standard, generic constant-time bearer-
  check pattern (four lines, no framework/library dependency beyond the
  stdlib `hmac` module), written fresh for R0 rather than imported from
  `app.main` (denylisted, §2) or any other module.
- **Which routes require authentication:** `/r0/v1/backend` and `/r0/v1/
  snapshot` — every route that returns any published fact. `/r0/v1/health`
  does not (§19).
- **Token rotation behavior:** identical shape to §7's credential-rotation
  answer — restart-time only; no live token-update HTTP route exists
  (adding one would itself be a mutation-shaped API, out of scope and
  explicitly not required).
- **Logging/redaction:** the `Authorization` header value is never logged;
  FastAPI/uvicorn's default access-log format does not include header
  values by default, and R0-B must not add custom request logging that
  does. This mirrors the existing diagnostics redaction discipline already
  proven on the HA side (§17's evidence from `diagnostics.py`), applied
  here to the backend's own process logs instead of HA diagnostics.

## 21. Home Assistant concrete transport

**Design:**

- **Module/class:** a new module, e.g. `custom_components/hubinet_ops/
  transport_http.py`, exporting a `HttpHubinetOpsTransport` class
  implementing the existing `HubinetOpsTransport` Protocol (`api.py:44-55`)
  exactly — no change to the Protocol itself — plus an `http_api_factory`
  function matching the existing `HubinetOpsApiFactory` Protocol shape
  (`api.py:89-95`), registered in place of `phase_zero_api_factory` via
  `hass.data[DOMAIN][DATA_API_FACTORY]` (the existing injection point,
  `__init__.py:34-42` — already designed for exactly this swap, no change
  needed there).
- **HTTP client:** Home Assistant's own shared `aiohttp` client session via
  `homeassistant.helpers.aiohttp_client.async_get_clientsession(hass,
  verify_ssl=verify_tls)` — the HA-native mechanism, not a bespoke `httpx`/
  `aiohttp` instance, matching the pattern the `0.5-foundation.md`-
  referenced `proxmoxve` vendored integration itself uses and what HA core
  review expects.
- **Route mapping:** `validate_connection`/`fetch_backend_information` →
  `GET {base_url}/r0/v1/backend`; `fetch_resource_snapshot` → `GET
  {base_url}/r0/v1/snapshot`.
- **Bearer auth:** `Authorization: Bearer {api_token}` header on every
  request (the R0 API token from config-entry data, §20 — never the PVE
  token, which HA never possesses at all).
- **Timeout:** a bounded `aiohttp.ClientTimeout` (e.g. total ~10–15s,
  tunable) — never unbounded.
- **TLS/`verify_tls` behavior:** passed straight through to `async_get_
  clientsession(hass, verify_ssl=verify_tls)`; per §10's deployment
  decision, the initial supported shape is plain HTTP on a trusted LAN
  (`verify_tls` is then moot / should default `True` but is a no-op for a
  non-TLS `base_url`), with HTTPS-via-reverse-proxy as the documented
  upgrade path.
- **Exception mapping:**

```text
HTTP 401/403                          -> HubinetOpsInvalidAuth
connection refused / DNS failure /
  aiohttp.ClientConnectorError /
  timeout                             -> HubinetOpsCannotConnect
non-2xx other than 401/403            -> HubinetOpsCannotConnect
  (treat as a transient/backend-side failure, not an auth failure)
invalid JSON body                     -> HubinetOpsInvalidResponse
JSON that fails typed construction
  (missing field, enum construction
  failure per SS17's mapping, or a
  contract dataclass __post_init__
  ValueError)                         -> HubinetOpsInvalidResponse
```

- **`backend_instance_id` validation:** the transport itself only fetches
  and returns `BackendInformation`/`HubinetOpsSnapshot` — the existing,
  already-correct wrong-backend rejection lives in `config_flow.py` (setup/
  reauth/reconfigure, §22) and `coordinator.py:221-227` (every refresh);
  the transport does not need to duplicate that check, only to construct a
  faithful `BackendInformation.backend_instance_id` from the response.
- **Snapshot typed construction/validation:** the transport is responsible
  for the full JSON→dataclass construction described in §17's mapping
  table (enum coercion, frozenset conversion) — any `ValueError`/`TypeError`
  raised by a contract dataclass's own `__post_init__` validation during
  that construction is caught and re-raised as `HubinetOpsInvalidResponse`,
  never allowed to propagate as an unhandled exception into the
  coordinator.
- **No PVE credentials in HA** — confirmed structurally impossible: the
  contract has no field carrying one (§17), and this transport never reads
  or references PVE configuration.
- **No write methods** — `HttpHubinetOpsTransport` implements exactly the
  three `HubinetOpsTransport` Protocol methods and nothing else; it must
  not gain a `post`/`update`/`mutate`-shaped method even for convenience.
- **Fake transport injection preserved** — `hass.data[DOMAIN][DATA_API_
  FACTORY]` remains the injection seam existing tests already use (`tests/
  test_hubinet_ops_integration.py` and the contract test suites); R0-B adds
  `HttpHubinetOpsTransport` as a new, additional implementation, without
  touching the seam itself or any existing fake.
- **No dependency on `app.inventory` internals** — `Http
  HubinetOpsTransport` only ever parses JSON over HTTP; it must not import
  anything from `app.*` at all (that would violate the HA↔backend process
  boundary even more fundamentally than the R0 composition-root denylist,
  §2, since HA and the backend are different processes/hosts entirely).

entry's reconfigure flow at a *different* R0 deployment (a different
`backend_instance_id`, e.g. a freshly bootstrapped R0 DB per §4/§5) is

## 23. Diagnostics / secret redaction

**Confirmed reusable unchanged for the fields already in the contract.**
`diagnostics.py` (full file read) already recursively redacts any key
matching `_REPOSITORY_SECRET_KEYS`/`_REPOSITORY_SECRET_SUFFIXES` — which
already includes `token`, `password`, `secret`, `credential`,
`canonical_transport_locator`, `authorization`, `webhook_url`, and any
`*_token`/`*_secret`/`*_credential`/`hubinet_ops_*_url` pattern — applied
via `_redact_repository_secrets` over the entire `config_entry.as_dict()`
plus `_snapshot_diagnostics(...)` output. Since (§17) the published/HTTP/HA
contract carries no PVE-token-shaped field at all, and the config entry
itself only ever holds the R0 API bearer token (already covered by the
`token`/`CONF_API_TOKEN` key match) and `base_url` (already covered by
`CONF_BASE_URL`), **no PVE secret ever reaches this code path to redact in
the first place** — the strongest possible form of "no disclosure."

**Required R0-B tests** (§19 #33): rather than a redesign, R0-B adds
regression tests proving the *negative* directly against a realistic R0
fixture: construct a `config_entry` with a real-shaped R0 API token and a
`HubinetOpsSnapshot` whose `sources[].facts`/`resources[].state` payloads
include representative PVE-shaped keys an operator might plausibly see
echoed back from discovery facts (e.g. a `ssh_fingerprint`-shaped key, if
ever added to `facts`) and assert `async_get_config_entry_diagnostics`
never emits the raw value for any of them. This closes the residual risk
that a *future* facts payload might carry an unanticipated secret-shaped
key that isn't yet in `_REPOSITORY_SECRET_KEYS` — an ongoing regression
test, not a design gap today.

## 25. Systemd / deployment design (not applied in R0-A)

No deployment file is edited in R0-A; this document does not touch
`deploy/hubinet-ops.service` (the 0.4 artifact, a different runtime with a
different threat model) or any other existing deployment file. This
section specifies what R0-B's future **final, sole** production unit for
the rebuilt host should contain, with every hardening flag independently
justified from what this specific process actually does — one HTTPS
egress connection to a configured PVE endpoint, inbound read-only HTTP,
and local SQLite I/O, nothing else — not copied from any other unit's flag
list:

```text
[Unit]
Description=Hubinet Ops Agent (0.5, read-only inventory)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=hubinetops
Group=hubinetops
EnvironmentFile=/etc/hubinet-ops/agent.env
WorkingDirectory=/opt/hubinet-ops
ExecStart=/opt/hubinet-ops/.venv/bin/uvicorn app.inventory_runtime:app --host 0.0.0.0 --port 8787
Restart=on-failure
RestartSec=5

NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=yes
ReadWritePaths=/var/lib/hubinet-ops
ReadOnlyPaths=/etc/hubinet-ops /opt/hubinet-ops
RestrictSUIDSGID=yes
LockPersonality=yes
MemoryDenyWriteExecute=yes

[Install]
WantedBy=multi-user.target
```

This unit is installed once, on the rebuilt host, as the only Hubinet Ops
service — its file path, unit name, user/group, environment file, and data
directory are the clean-install canonical values (§3/§4), chosen on their
own merits for this fresh deployment.

**Hardening flags, each independently justified:**

- `NoNewPrivileges`/`RestrictSUIDSGID`/`LockPersonality`/`MemoryDenyWrite
  Execute` — R0 is a pure Python/uvicorn/httpx process; it never needs to
  gain privilege, execute newly-written memory, or manipulate personas —
  standard minimal-privilege posture for any such process, justified by
  what R0 does, not by any other unit's example;
- `PrivateTmp`/`ProtectSystem=strict`/`ProtectHome` — R0 writes only to its
  own data directory (§4) and reads only its own config/code directories;
  it has no legitimate reason to touch `/tmp` shared state, system
  directories, or user home directories;
- `--host 0.0.0.0` — closed by §10: the supported initial topology places
  Home Assistant on a separate host/VM from R0, so a loopback-only bind
  would make R0 unreachable from its one legitimate inbound consumer and
  is not an option here. Binding all interfaces is safe specifically
  *because* it is paired with the mandatory firewall requirement in §26,
  not because the port is assumed harmless on its own — the compensating
  control is the firewall restricting inbound access to the HA host/
  subnet, not the bind address;
- `ProtectKernelTunables=yes`, `ProtectKernelModules=yes`,
  `ProtectKernelLogs=yes`, `ProtectControlGroups=yes` — R0 has no
  conceivable need to read or alter kernel state or cgroup configuration;
  safe, independently-justified additions;
- `PrivateNetwork=no` — R0 genuinely needs real network egress to PVE and
  ingress from HA, so this stays permissive; noted explicitly so a future
  reviewer doesn't assume it was overlooked;
- `SystemCallFilter=@system-service` (a standard systemd allow-list
  profile) as an additional layer, evaluated but left as an R0-B tuning
  decision rather than mandated here, since it requires empirical
  validation against the actual Python/uvicorn/httpx syscall footprint to
  avoid breaking the service.

## 26. Network boundary

```text
R0 needs network only for:
  - outbound HTTPS (§9) to the configured active PVE endpoint(s)
  - inbound HA -> R0 read-only HTTP (§19/§21) from the HA host/subnet

R0 needs no network access for:
  - SSH (no pct/qm mutation, no hostd -- R0 has no host-control dependency
    at all, confirmed by SS2's denylist)
  - MQTT (no dependency, confirmed by SS3/SS12)
  - arbitrary guest network access (discovery is PVE-API-mediated only,
    never a direct connection to a guest)
```

**Required firewall policy, paired with §25's `0.0.0.0` bind (not
optional, not left to R0-B to decide whether to apply — the exact rule
syntax/tool is a deployment-time implementation detail, but the policy
itself is a closed part of this design):** allow egress from the R0 host
to the PVE endpoint's HTTPS port (typically 8006); allow ingress to R0's
own listen port from the HA host/subnet only; deny everything else R0
might otherwise reach by default network policy (no special allowance
needed since R0 does not initiate any other outbound
connection class).
