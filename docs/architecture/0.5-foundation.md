# Hubinet Ops 0.5 — fundament architektury

Status: decyzje architektoniczne Phase 0 dla clean install 0.5.0.

Projekt inventory identity i discovery jest obecnie przedmiotem osobnego review:

- [ADR 0001: identity zasobu i incarnation](adr/0001-resource-identity-incarnation.md) — `PROPOSED`;
- [ADR 0002: read-only discovery i reconciliation](adr/0002-proxmox-discovery-reconciliation.md) — `PROPOSED`;
- [konceptualny inventory model](0.5-inventory-model.md) — `PROPOSED`.

Proponowane ADR wymagają przed Phase 1 zmiany kontraktu `ResourceIdentity` oraz
snapshot presence/detail/node availability Phase 0; pełny zakres opisuje
`PHASE 0 AMENDMENT REQUIRED` w ADR 0001. Do akceptacji ADR poniższy model
pozostaje zapisem decyzji Phase 0, a nie zatwierdzonym modelem VMID reuse.

## Zakres i clean break

Hubinet Ops 0.5 jest nowym systemem. Nie zachowuje kompatybilności
konfiguracyjnej ani runtime z 0.4. Nie powstaną migratory starego `config.yaml`,
bazy SQLite, encji Home Assistant ani MQTT Discovery, warstwy zgodności,
aliasy, fallbacki, upgrade zachowujący instalację ani automatyczny purge 0.4.
Operator usuwa starą instalację osobno i ręcznie.

Phase 0 definiuje kontrakty oraz read-only frontend Home Assistant. Nie obejmuje
maintenance, APT, lifecycle, snapshotów, rollbacku, self-update, break-glass,
MQTT ani produkcyjnego discovery Proxmoxa.

## Źródła prawdy i przepływ danych

Backend jest właścicielem inventory, policy i stanu operacji. SQLite jest
autorytatywnym trwałym stanem backendu. Home Assistant prezentuje stan i — w
późniejszych fazach — przekazuje wyłącznie kontrolowane, typowane wejście.

Docelowy przepływ inventory:

```text
Proxmox
  ↓
Hubinet Ops backend discovery
  ↓
persistent inventory
  ↓
Hubinet Ops API
  ↓
Home Assistant coordinator
```

Home Assistant nigdy nie odkrywa Proxmoxa i nie przechowuje jego credentials.
Discovery opisuje fakty; nie przyznaje uprawnień.

## Granica zaufania mutacji

Każda przyszła mutacja przechodzi pełną ścieżkę:

```text
Home Assistant
→ Hubinet Ops API
→ backend policy
→ plans/jobs/locks/audit
→ typed host-control
→ hostd/forced-command
→ Proxmox
```

Nie wolno skracać tej ścieżki ani traktować capability widocznego w HA jako
autoryzacji. Backend ponownie waliduje typ akcji, identity, policy, plan,
preconditions i idempotency key. Host-control przyjmuje tylko zamknięty zbiór
typowanych operacji. `hostd`/forced-command stanowi niezależną, fail-closed
granicę mutacji i ponownie waliduje akcję oraz host policy. Maintenance zawsze
wymaga ręcznego zatwierdzenia planu, a operacje destrukcyjne są idempotentne.

## Poziomy stanu zasobu

Poziomy są rozłączne semantycznie i nie tworzą automatycznej drabiny uprawnień:

- `discovered` — backend zna identity i podstawowe fakty z discovery;
- `observed` — backend ma wiarygodne obserwacje runtime;
- `managed` — jawna user policy pozwala backendowi zarządzać zasobem;
- `maintenance` — jawna policy i zatwierdzony plan dopuszczają konkretną
  operację maintenance;
- `break-glass` — osobna ścieżka recovery, credentials, policy i audyt; nie jest
  fallbackiem normalnego backend control.

Automatyczne discovery może utworzyć albo zaktualizować wyłącznie fakty na
poziomie `discovered`. Nie może samo nadać `managed`, `maintenance` ani
`break-glass`.

## Effective capabilities

Frontend nie wylicza i nie zakłada permissions. Backend zwraca effective
capabilities jako wynik przecięcia:

```text
resource facts
∩ user policy
∩ executor readiness
∩ host policy
∩ runtime preconditions
```

Capability jest chwilowym faktem backendowym, a nie trwałą cechą urządzenia.
HA może go wyświetlić, lecz przyszła akcja i tak wymaga ponownej autoryzacji i
walidacji przez backend. Brak capability oznacza brak pozwolenia; nie stosujemy
optymistycznych fallbacków.

## ResourceIdentity i wiele instancji

Backend nadaje każdej niezależnej instancji/klastrowi Proxmox niezmienne,
niezależne od adresu i nazwy `instance_id` (docelowo losowy UUID zapisany w
trwałym inventory). Identity VM/LXC jest złożonym kluczem:

```text
(instance_id, resource_type, vmid)
```

`resource_type` jest zamkniętym typem (`qemu` albo `lxc`), a `vmid` dodatnią
liczbą przypisaną przez daną instancję. Krotka jest przechowywana strukturalnie;
format tekstowy używany w HA jest tylko deterministyczną serializacją.

Nazwa zasobu, URL backendu, adres Proxmoxa i node nie są częścią identity.
`node_id` jest bieżącą relacją/lokalizacją zasobu. Migracja VM/LXC między
node'ami aktualizuje `node_id` i relację `via_device_id`, zachowując ten sam
rekord inventory, Device Registry identifier i entity `unique_id`. Node ma osobną
identity `(instance_id, node_id)`; backend powinien dostarczyć stabilne
`node_id`, a nie wymuszać użycie display name.

Ponowne użycie tego samego VMID po potwierdzonym usunięciu wymaga w przyszłym
kontrakcie inventory jawnej decyzji o generacji/incarnation. Phase 0 nie usuwa
rekordów i nie rozstrzyga automatycznie, że nowo zaobserwowany VMID jest tym
samym fizycznym workloadem. To ryzyko musi zostać zamknięte przed produkcyjnym
reconciliation.

## Snapshot API dla Home Assistant

Integracja konsumuje jeden logiczny, typowany snapshot backendu zawierający:

- informacje backendu i `instance_id`;
- node'y;
- zasoby wraz z `ResourceIdentity`, bieżącym `node_id`, jawnym
  `last_known_node_id` i nazwą;
- resource state level oraz availability/presence;
- policy do prezentacji;
- effective capabilities obliczone przez backend.

Phase 0 definiuje transportowy interfejs `validate_connection`,
`fetch_backend_information` i `fetch_resource_snapshot`. Nie zamraża ścieżek
HTTP przed uzgodnieniem API 0.5 i testuje interfejs fake transportem. Klient
przyjmuje tylko base URL, bearer API token i TLS verification; nie zna
credentials ani SDK Proxmoxa.

Snapshot jest value object, nie widokiem na mutowalne dane transportu. `facts`,
`policy` i `state` są rekurencyjnie zamrażane: mappings stają się read-only,
sequences stają się tuples, a wartości spoza kontraktu JSON-like są odrzucane.

`presence=present` wymaga bieżącego `node_id`, który istnieje w tym samym
snapshotcie, oraz zabrania równoczesnego `last_known_node_id`. Dla
`temporarily_unavailable`, `node_unavailable`, `missing` i `confirmed_removed`
`node_id` musi być `null`, a `last_known_node_id` jawnie zachowuje ostatnią
znaną lokalizację. Last-known node nie musi nadal występować w bieżącym
snapshotcie inventory.

## Dynamiczny model Home Assistant

Jedna config entry posiada jeden `DataUpdateCoordinator` i jeden request
logicznego snapshotu na refresh. Sensor platform rejestruje callbacki nowych
node'ów i zasobów. Nowa identity z kolejnego snapshotu powoduje dodanie urządzeń
i encji bez reloadu integracji. Wartości VMID, nazwy i node'y pochodzą wyłącznie
z backendu.

Device Registry identifier zasobu serializuje wyłącznie trwałą
`ResourceIdentity`. Nazwa urządzenia może się zmienić bez zmiany `unique_id`.
Zasób wskazuje aktualny lub last-known node przez `via_device_id`; migracja
zmienia relację, nie identity. Integracja rejestruje node devices przed child
devices i rozwiązuje identifier parenta do konkretnego Device Registry ID.

## Stale, missing i removal

Pojedynczy brak w odświeżeniu nie jest dowodem usunięcia. Backendowy model
rozróżnia:

- `temporarily_unavailable` — zasób znany, ale chwilowo nieobserwowalny;
- `node_unavailable` — brak obserwacji wynika ze stanu node'a;
- `missing` — discovery nie zwróciło zasobu, przyczyna niepotwierdzona;
- `confirmed_removed` — backend zakończył reconciliation i trwale potwierdził
  usunięcie.

W Phase 0 coordinator zachowuje ostatni rekord nieobecnego zasobu, oznacza go
`missing`, przenosi jego `node_id` do `last_known_node_id` i ustawia
`available=false`, a integracja nie usuwa jego urządzenia ani encji.
Jawny `confirmed_removed` również nie uruchamia jeszcze automatycznego purge;
bezpieczny lifecycle Device/Entity Registry wymaga osobnej decyzji wraz z
retencją, audytem i ochroną przed przejściowymi błędami discovery. Jest to
celowo ostrożniejsze niż natychmiastowe usuwanie w referencji `proxmoxve`.

## Target Home Assistant i pochodzenie wzorców

Produkcyjnym targetem kompatybilności jest Home Assistant Core `2026.8.1`,
wymagający Python `>=3.14.2`. Izolowany fixture harness musi przypinać dokładnie
`homeassistant==2026.8.1`; starszy harness nie stanowi dowodu zgodności.

Wzorce config flow, coordinator, dynamicznych callbacków, Device Registry i
diagnostics przeanalizowano na podstawie Home Assistant Core `proxmoxve` z
tagu `2026.8.1`, commit
`53998d7710b4ac280658511c24a2a3e2651f9873`. Referencja pozostaje w
`vendor/home-assistant-core/` na licencji Apache-2.0. Integracja Hubinet Ops nie
importuje jej w runtime i nie kopiuje mutacyjnych `press_action`.
