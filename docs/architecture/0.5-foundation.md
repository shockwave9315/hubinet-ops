# Hubinet Ops 0.5 — fundament architektury

Status: **ACCEPTED** — decyzje architektoniczne Phase 0 dla clean install 0.5.0.

Review architektury inventory identity i discovery został zakończony:

- [ADR 0001: identity zasobu i incarnation](adr/0001-resource-identity-incarnation.md) — `ACCEPTED`;
- [ADR 0002: read-only discovery i reconciliation](adr/0002-proxmox-discovery-reconciliation.md) — `ACCEPTED`;
- [konceptualny inventory model](0.5-inventory-model.md) — `ACCEPTED`; materializuje
  zaakceptowane decyzje obu ADR-ów.

Phase 0 Amendment wyrównał typowany snapshot i natywną prezentację Home
Assistant z accepted ADR 0001/0002: workload identity używa backendowego
`resource_id`, VMID jest source-local locatorem, osie resource state są
rozdzielone, a source health/freshness i published revisions są jawną częścią
kontraktu. Amendment nie implementuje persistent inventory ani backendowych
transaction/CAS/fencing/expiry owners opisanych dla Phase 1+.

## Zakres i clean break

Hubinet Ops 0.5 jest nowym systemem. Nie zachowuje kompatybilności
konfiguracyjnej ani runtime z 0.4. Nie powstaną migratory starego `config.yaml`,
bazy SQLite, encji Home Assistant ani MQTT Discovery, warstwy zgodności,
aliasy, fallbacki, upgrade zachowujący instalację ani automatyczny purge 0.4.
Operator usuwa starą instalację osobno i ręcznie.

Phase 0 definiuje kontrakty oraz read-only frontend Home Assistant. Nie obejmuje
maintenance, APT, lifecycle, snapshotów, rollbacku, self-update, break-glass,
MQTT ani produkcyjnego discovery Proxmoxa.

## Źródła prawdy i przepływ danych

Backend jest właścicielem inventory, policy i stanu operacji. SQLite jest
autorytatywnym trwałym stanem backendu. Home Assistant prezentuje stan i — w
późniejszych fazach — przekazuje wyłącznie kontrolowane, typowane wejście.

Docelowy przepływ inventory:

```text
Proxmox
  ↓
Hubinet Ops backend discovery
  ↓
persistent inventory
  ↓
Hubinet Ops API
  ↓
Home Assistant coordinator
```

Home Assistant nigdy nie odkrywa Proxmoxa i nie przechowuje jego credentials.
Discovery opisuje fakty; nie przyznaje uprawnień.

## Granica zaufania mutacji

Każda przyszła mutacja przechodzi pełną ścieżkę:

```text
Home Assistant
→ Hubinet Ops API
→ backend policy
→ plans/jobs/locks/audit
→ typed host-control
→ hostd/forced-command
→ Proxmox
```

Nie wolno skracać tej ścieżki ani traktować capability widocznego w HA jako
autoryzacji. Backend ponownie waliduje typ akcji, identity, policy, plan,
preconditions i idempotency key. Host-control przyjmuje tylko zamknięty zbiór
typowanych operacji. `hostd`/forced-command stanowi niezależną, fail-closed
granicę mutacji i ponownie waliduje akcję oraz host policy. Maintenance zawsze
wymaga ręcznego zatwierdzenia planu, a operacje destrukcyjne są idempotentne.

## Poziomy stanu zasobu

Poziomy są rozłączne semantycznie i nie tworzą automatycznej drabiny uprawnień:

- `discovered` — backend zna identity i podstawowe fakty z discovery;
- `observed` — backend ma wiarygodne obserwacje runtime;
- `managed` — jawna user policy pozwala backendowi zarządzać zasobem;
- `maintenance` — jawna policy i zatwierdzony plan dopuszczają konkretną
  operację maintenance;
- `break-glass` — osobna ścieżka recovery, credentials, policy i audyt; nie jest
  fallbackiem normalnego backend control.

Automatyczne discovery może utworzyć albo zaktualizować wyłącznie fakty na
poziomie `discovered`. Nie może samo nadać `managed`, `maintenance` ani
`break-glass`.

## Effective capabilities

Frontend nie wylicza i nie zakłada permissions. Backend zwraca effective
capabilities jako wynik przecięcia:

```text
resource facts
∩ user policy
∩ executor readiness
∩ host policy
∩ runtime preconditions
```

Capability jest chwilowym faktem backendowym, a nie trwałą cechą urządzenia.
HA może go wyświetlić, lecz przyszła akcja i tak wymaga ponownej autoryzacji i
walidacji przez backend. Brak capability oznacza brak pozwolenia; nie stosujemy
optymistycznych fallbacków.

## Identity, locator i wiele sources

`backend_instance_id` jest trwałą identity instalacji Hubinet Ops i exact
identity ConfigEntry. Każde operatorowo zdefiniowane środowisko Proxmox ma
osobny backendowy `inventory_source_id`. URL, nazwa klastra i adresy nie są
identity żadnego z tych obiektów.

Każda inventory incarnation workloadu ma opaque, backend-generated
`resource_id`. VMID jest wyłącznie slot locatorem
`(inventory_source_id, vmid)`, a `resource_type` (`qemu` albo `lxc`) immutable
property occupanta, nie namespace VMID. Active `binding_id` wskazuje current
incumbenta locatora, `locator_generation` porządkuje accepted handoffs, a
`resource_continuity_revision` jest osobnym monotonicznym security/concurrency
tokenem. Żadna z tych wartości nie jest wyliczana z nazwy, VMID, type ani node'a.

Published view może równocześnie zawierać starą incarnation A, VMID 101,
generation 4, `not_current/retired/replaced`, oraz successor B, VMID 101,
generation 5, `present/active`. Kolekcja jest keyed przez `resource_id`; current
occupant wynika wyłącznie z active binding, nigdy z kolejności records albo mapy
`resources_by_vmid`.

Nazwa i node są zmiennymi facts/relations. Rename zachowuje resource identity.
Migracja zmienia `current_node_id` i HA `via_device_id`, lecz zachowuje
`resource_id`, Device Registry identifier i entity `unique_id`.

## Snapshot API dla Home Assistant

Integracja konsumuje jeden logiczny, typowany snapshot backendu zawierający:

- informacje backendu i `backend_instance_id`;
- `sources[]` z `inventory_source_id`, current health/freshness, origin/reason,
  run provenance, fixed last-success/reference/deadline oraz exact current i
  committed source/endpoint/canonicalization/transport-trust context;
- source-namespaced node records;
- identity-keyed `resources[]` z `resource_id`, VMID locatorem, active binding,
  `locator_generation`, `resource_continuity_revision` i node relation;
- canonical `presence`, `lifecycle`, `observational_continuity`,
  `security_continuity`, osobne `detail_status` i `node_availability`;
- retained/effective policy presentation oraz effective capabilities obliczone
  przez backend, bez frontendowej derivation;
- globalne `inventory_revision`, `published_state_revision` i fixed
  `published_at` jednego spójnego immutable view.

Phase 0 definiuje transportowy interfejs `validate_connection`,
`fetch_backend_information` i `fetch_resource_snapshot`. Nie zamraża ścieżek
HTTP przed uzgodnieniem API 0.5 i testuje interfejs fake transportem. Klient
przyjmuje tylko base URL, bearer API token i TLS verification; nie zna
credentials ani SDK Proxmoxa.

Snapshot jest value object, nie widokiem na mutowalne dane transportu. `facts`,
`policy` i `state` są rekurencyjnie zamrażane: mappings stają się read-only,
sequences stają się tuples, a wartości spoza kontraktu JSON-like są odrzucane.

`presence=present` może mieć resolved `current_node_id` z availability
`available|unavailable` albo unresolved relation z `current_node_id=null` i
opcjonalnym `last_known_node_id`. `missing`, `confirmed_removed` i `not_current`
nie mają current node i używają `detail_status=not_applicable`. Każdy non-null
current lub last-known node wskazuje retained node record w tym samym snapshotcie
i tym samym source; dangling `via_device` jest odrzucane. Last-known node jest
wyłącznie presentation/history hint, nigdy mutation route.

## Dynamiczny model Home Assistant

Jedna config entry posiada jeden `DataUpdateCoordinator` i jeden request
logicznego snapshotu na refresh. Sensor platform rejestruje callbacki nowych
node'ów i zasobów. Nowa identity z kolejnego snapshotu powoduje dodanie urządzeń
i encji bez reloadu integracji. Wartości VMID, nazwy i node'y pochodzą wyłącznie
z backendu.

Device Registry i Entity Registry workloadu serializują wyłącznie
`backend_instance_id + resource_id + entity key`. Source i node devices używają
odpowiednio backendowego `inventory_source_id` i `node_id`. Integracja rejestruje
source, potem node, potem resource devices i rozwiązuje parent identifiers do
konkretnego HA `via_device_id`. Nie wykonuje automatic purge.

## Presence, detail, source freshness i retencja

Coordinator nie jest reconcilerem i nie syntetyzuje `missing` z różnicy dwóch
refreshy. Każdy snapshot jest kompletnym authoritative published view backendu;
fake transporty również przekazują już reconciled states. Zniknięcie recordu z
backendowego view nie upoważnia HA do zachowania, usunięcia ani zmiany jego
physical presence.

Canonical presence to `present|missing|confirmed_removed|not_current`.
`temporarily_unavailable|error` należą do `detail_status`, a niedostępność node'a
do `node_availability`; present locator pozostaje present przy obu failure
overlay. Absence/terminal states wymagają `detail_status=not_applicable`.

Source health/freshness jest niezależne od resource presence. Osiągalny backend
może zwrócić fresh, stale, degraded, unavailable albo configuration-error source
razem z retained last committed resources. HA zachowuje identity i history
facts, udostępnia source diagnostics, a encje wymagające current detail/node
facts fail closed jako unavailable. Source failure nie tworzy `missing`.

Phase 0 implementuje shape, deep immutability, cross-reference/state/revision
validation oraz HA presentation. Persistent reconciliation, transactional
active-binding handoff, global revision allocation, source run CAS/fencing i
scheduler-independent materializacja `time_expiry` wymagają durable backend
ownera i pozostają Phase 1+. HA nie emuluje tych security invariants lokalnie.

## Target Home Assistant i pochodzenie wzorców

Produkcyjnym targetem kompatybilności jest Home Assistant Core `2026.8.1`,
wymagający Python `>=3.14.2`. Izolowany fixture harness musi przypinać dokładnie
`homeassistant==2026.8.1`; starszy harness nie stanowi dowodu zgodności.

Wzorce config flow, coordinator, dynamicznych callbacków, Device Registry i
diagnostics przeanalizowano na podstawie Home Assistant Core `proxmoxve` z
tagu `2026.8.1`, commit
`53998d7710b4ac280658511c24a2a3e2651f9873`. Referencja pozostaje w
`vendor/home-assistant-core/` na licencji Apache-2.0. Integracja Hubinet Ops nie
importuje jej w runtime i nie kopiuje mutacyjnych `press_action`.
