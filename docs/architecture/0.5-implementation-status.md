## COMPLETE

The following are implemented on `main` and covered by repository/CI tests.

### Canonical Phase 0 snapshot contract

- backend identity uses canonical `backend_instance_id` UUID;
- inventory sources use backend-generated `inventory_source_id` UUIDs;
- resources use opaque backend-generated `resource_id` UUIDs;
- VMID is a source-local locator slot, never durable resource identity;
- `resource_type` is an immutable occupant property;
- active binding identity, locator generation, and `resource_continuity_revision` are distinct concepts;
- source/node/resource references use canonical lower-case hyphenated non-NIL UUID text where the contract requires UUID identity;
- unsupported enum values and malformed security-sensitive canonical values fail closed;
- published mappings/sequences are recursively frozen or rejected when outside the JSON-like contract;
- top-level snapshot collections are detached from caller-owned mutable lists.

### Structural Phase 0 contract layer

- the canonical Phase 0 contract is split into explicit enum, model, primitive,
  source/resource/snapshot/transition validation, and projection modules under
  `custom_components/hubinet_ops/contract/`;
- `custom_components/hubinet_ops/api.py` is a thin API/client/transport
  compatibility facade;
- existing production imports through `.api` remain supported through exact
  object-identity re-exports;
- the split has zero intended semantic change and retains the existing
  accepted/rejected snapshot contract tests.

### Resource state and retained identity

Canonical resource state is split into independent axes:

- presence;
- lifecycle;
- observational continuity;
- security continuity;
- detail status;
- node availability;
- state level.

Implemented constraints include:

- at most one current/active occupant for one `(inventory_source_id, vmid)` slot;
- retained terminal/non-current incarnations coexist with a current successor under distinct `resource_id` values;
- retained locator generations are unique and consecutive within retained history, while retained history need not begin at generation 1;
- current reuse of a retained locator must use the exact next generation;
- active binding IDs cannot be reassigned to another resource after observed ownership/closure;
- terminal resources cannot reopen or silently change immutable identity;
- direct replacement retains old lineage and publishes a distinct successor;
- successor lineage is historical provenance, not a permanent requirement that the successor remain in its initial live state;
- source/node/resource records previously published cannot disappear from a later accepted Phase 0 snapshot;
- node/resource ownership cannot move across inventory sources under the same retained identity;
- same-source rename/runtime/node-presentation changes preserve resource identity;
- terminal and absent resources remain retained but their HA entities are unavailable as required by the accepted presentation contract.

### Security continuity, state level, policy and capabilities

Implemented fail-closed presentation/contract checks include:

- `discovered`, `observed`, `managed`, `maintenance`, and `break_glass` remain semantically distinct;
- normal `policy_applicable=True` is accepted only for otherwise eligible `MANAGED` or `MAINTENANCE` resources;
- `BREAK_GLASS` does not use the normal policy-applicability path;
- `policy_applicable` must be an actual runtime `bool`; malformed truthy values such as strings/integers are rejected;
- non-applicable policy cannot publish effective capabilities;
- effective capabilities are presentation facts from the backend, never frontend-derived authority;
- observed security/continuity/lifecycle/state-level transitions that affect mutation eligibility require a strictly newer `resource_continuity_revision`;
- no `+1` adjacency is required for continuity revisions;
- previously observed trusted/revoked security lower bounds are preserved according to the accepted polling contract;
- `UNVERIFIED -> REVOKED` remains legal because HA may have skipped an intermediate trust/revocation publication.

### Source health, freshness and run provenance

Phase 0 publishes and validates:

- current source health/freshness and origin/reason;
- issued/completed/applied-health/committed run sequence maxima;
- completion and applied-health outcomes;
- fixed last-success/freshness timestamps/deadline;
- exact current and committed source/endpoint/canonicalization/transport-trust context;
- monotonic source config/trust/run provenance visible to HA.

Implemented invariants include:

- `last_committed_run_sequence <= last_health_run_sequence <= latest_completed_run_sequence <= last_issued_run_sequence`;
- health provenance requires completion provenance;
- every published successful applied-health outcome names the exact committed run;
- every published successful completion outcome names the exact committed run;
- an exact committed run carries successful applied-health/completion provenance when those maxima point to it;
- a fresh source requires healthy authoritative discovery-run provenance bound to the exact committed run and committed context;
- `TIME_EXPIRY` is stale and remains fenced to the exact committed run/context;
- reversing an observed expiry back to fresh requires a newer authoritative commit;
- same-token completed/health outcomes and committed success provenance are immutable across accepted snapshots;
- optional durable maxima cannot disappear back to `None` after HA has observed them;
- a newly committed run cannot be retroactively selected from the range of runs a previous accepted snapshot had already observed as finalized;
- polling gaps remain legal: no run-sequence or published-revision adjacency is inferred;
- every successful authoritative inventory reconciliation commit advances `inventory_revision`, including commits with unchanged resource facts;
- other API-visible derived/source-health transitions may advance only `published_state_revision` when the accepted inventory projection is unchanged.

### Source context and endpoint presentation contract

Implemented Phase 0 validation includes:

- provider kind is immutable for an existing source identity;
- current endpoint identity cannot silently change for an existing source;
- endpoint identities cannot be shared across different source identities in one published namespace;
- canonical locator is immutable for the same endpoint/canonicalization contract version;
- controlled canonicalization-version migration may change the canonical locator only under the accepted higher-version/config-revision rules;
- source config/trust revisions remain monotonic without being treated as source identity or physical source-continuity proof.

This is presentation/contract validation only. It is not the Phase 1 endpoint activation/source-binding procedure.

### Home Assistant integration boundary

Implemented and tested:

- one coordinator consumes one logical backend snapshot per refresh;
- backend instance identity binds the config entry;
- foreign backend identity is rejected before publication/registry callbacks;
- resource Device/Entity Registry identity is based on backend/resource UUIDs, never VMID/name/node;
- source -> node -> resource topology is represented through Device Registry parent relations;
- rename and node migration preserve resource identity;

- config flow reauth/reconfigure preserves backend identity checks;
- diagnostics recursively redact repository secret classes, including camelCase names and namespaced `*_headers` containers, with negative over-redaction controls.

0.5 authority databases and, since merged WAVE R0-B, by the R0 production

exposes it; Home Assistant's `HttpHubinetOpsTransport` consumes it
through that HTTP API; the R0Scheduler background thread invokes it on a

runtime is untouched and structurally excluded from the R0 composition

runtime activation gate below were satisfied before WAVE R0-B wired this
subsystem in; "runtime-activated" here means implemented and
constructible in the repository, not deployed to a real host.

- `app.inventory` is an independently instantiable 0.5 authority namespace;
  legacy `OpsService` and legacy `Database` are not owners or dependencies;
- a fresh SQLite authority database uses explicit marker
  `hubinet_ops_0_5_authority`, monotonic schema version `5`, foreign keys, WAL,
  busy timeout, and `BEGIN IMMEDIATE` write transactions; legacy 0.4, dormant
  0.5 schema v1/v2/v3/v4, and unknown non-empty databases are rejected
  without migration or reset (schema v5 is the current version; see
  "Source-binding/attestation durable authority" and "Confirmed removal
  durable authority" below for what WAVE C1 and WAVE A1 added on top of
  v3/v4, each without an in-place migration);
- one persistent backend instance owns a stable canonical UUID plus global
  `inventory_revision` and `published_state_revision` initialized to `0` and
  `1` respectively;
- atomic initial source creation persists one backend-generated source UUID,
  one initial active endpoint, one initial non-fresh runtime-health record,
  source configuration revision `1`, transport trust revision `1`, and only a
  credential reference;
- canonicalization contract version `1` supports the accepted HTTPS DNS/IPv6,
  default-port, explicit non-default-port, and root-path normalization while
  rejecting unsupported or ambiguous locators;
- source display rename preserves identity, provider kind, configuration
  revision, endpoint, and active run context while advancing both global
  revisions;
- durable discovery-run issuance captures exact source/endpoint/
  canonicalization/trust context, allocates strictly increasing per-source
  sequence values, establishes one active owner, and advances only the global
  published revision;
- exact issued/running ownership survives restart; same-source concurrent
  issuance has one winner, different sources may own runs concurrently, and a
  controlled one-time abandon fence releases ownership without invented
  observation, completion, health, or commit provenance.

### Phase 1B read-only inventory backend — implemented and runtime-activated (read-only)

Phase 1B extends only the independently instantiated `app.inventory` subsystem.
Since merged WAVE R0-B it is present in application (R0) startup,
production provider invocation, the R0 scheduler, and R0's own HTTP/HA
wiring; it remains absent from mutation authority and legacy 0.4
dependencies (neither exists for R0).

- provider contract v1 is an injected, GET-only PVE 9.x contract with an exact
  baseline/detail endpoint matrix, upstream effective-permission comparison,
  ACL/permission boundary hashing, cluster baseline, and explicit standalone
  QEMU+LXC fallback;
- immutable normalized discovery snapshots reject wrong source/context,
  malformed facts, unsupported type, duplicate locator, duplicate node, and
  incomplete security evidence before reconciliation;
- successful run finalization is one `BEGIN IMMEDIATE` transaction covering
  exact owner/context CAS, durable completion, reconciliation, nodes/resources/
  bindings, source health, committed provenance, revisions, and owner release;
- non-success completion is write-once, never changes inventory, and cannot
  overwrite health from a newer context;
- schema v5 (originally introduced as v3 for this Phase 1B inventory shape;
  WAVE C1 extended it to v4 for source attestation; WAVE A1 extended it to
  v5 for confirmed removal, see below) durably owns nodes, resource
  incarnations, locator bindings, consecutive source-local generations,
  retained terminal history/lineage, and canonicalization migration
  provenance; schema v1/v2/v3/v4 are rejected rather than migrated, per
  the clean-break design's own no-migration contract — this holds
  regardless of runtime-activation status;
- reconciliation preserves identity across facts/name/node changes, derives
  `missing` only from a complete boundary-valid baseline, quarantines gaps,
  performs atomic positive QEMU/LXC direct replacement, and never itself
  produces polling-only `confirmed_removed` — that terminal transition is
  owned exclusively by the separate, explicit Class-C authority operation
  (WAVE A1, below), never by reconciliation;
- discovery never grants trust, management, maintenance, policy applicability,
  or destructive capability;
- freshness uses observation time as anchor, materializes stale-on-arrival and
  time expiry durably, and uses run/deadline/context CAS against old workers and
  timers;
- the canonical publication assembler materializes due expiry and reads the
  backend, sources, nodes, resources, and both revisions in one SQLite read
  transaction; serialized output is accepted by the Phase 0 snapshot oracle.

**G8 (standalone/cluster `baseline_mode` ambiguity) is resolved against the
accepted model, with regression coverage.** `baseline_mode` is per-run
observed provenance recorded on each completed `discovery_runs` record
(`InventorySource` has no durable mode field); reconciliation keys
replacement only off a `resource_type` change for the same
`(inventory_source_id, vmid)` slot and never inspects `baseline_mode`.
`tests/test_inventory_reconciliation.py` locks, for both transition
directions, that a legitimate standalone↔cluster transition alone never
changes `inventory_source_id`, never bumps `source_config_revision`, and
never replaces/quarantines/marks-missing the same VMID/resource_type
incarnation, while node/topology facts may still legitimately change with
observed topology. `tests/test_inventory_discovery_snapshot.py` adds a
malformed-boundary witness (mismatched provider node-scope mode vs.
declared `baseline_mode` fails closed at snapshot construction).
`tests/test_inventory_provider_contract.py::test_caller_expectation_cannot_override_observed_mode`
already covered the provider-layer fail-closed guard against a caller
overriding the observed mode; no production behavior changed.

### Source-binding/attestation durable authority (WAVE C1) — implemented but dormant

WAVE C1 extends only the independently instantiated `app.inventory`
subsystem, on schema version **4** (the version-3 marker/objects from
Phase 1A/1B are rejected without migration, exactly like v1/v2 before them;
there is no in-place v3→v4 data migration policy and none was authorized).
The durable schema/tables this wave added live in the same schema-v5
authority database the merged R0 composition root now opens at startup,
but no attestation-shaped method (`enroll_source_attestation`,
`reattest_source`, `accept_source_attestation_anchor_change`,
`revoke_source_attestation`, `check_candidate_attestation`) is ever
called by R0's own call surface — enforced by an adversarial regression
test (`tests/test_inventory_scheduler.py`) that spies every such method
across a full discovery cycle and asserts zero calls. Attestation remains
functionally dormant: no HA/MQTT wiring exposes it, and mutation
authority does not exist for R0 at all.

- `source_attestation_state`: one durable current-state row per source,
  starting explicitly `not_yet_attested` at `source_attestation_epoch = 0`;
  a monotonic `source_attestation_epoch` token, independent of
  `source_config_revision`/`transport_trust_revision`/
  `resource_continuity_revision`, gates every attestation-relevant
  security-context change; a schema trigger fails closed if
  `attestation_status`/enrolled-anchor fields ever changed without the
  epoch also advancing in the same write, so the epoch reliably proxies
  "the security context changed" for every CAS check that relies on it;
- `source_attestation_events`: an immutable, retained (delete-blocked)
  audit trail of every explicit attestation attempt/outcome
  (match/mismatch/unavailable/malformed/stale_cas/accepted/rejected),
  structurally separate from current state — current authority is never
  derived from "the latest audit event";
- explicit, operator-driven `InventoryAuthority` methods implement ADR
  0003 §12/§16/§19a/§20 literally: `enroll_source_attestation` (initial
  enrollment, `not_yet_attested`/N → `attested`/N+1 — N is normally 0, but
  a source re-enrolling after revocation carries its epoch forward rather
  than resetting), `reattest_source` (same-anchor reconfirmation is
  audit-only; a differing anchor is recorded as a mismatch and never
  silently accepted), `accept_source_attestation_anchor_change` (the
  separate explicit decision that deliberately accepts a new anchor,
  exact N→N+1), and `revoke_source_attestation` (explicit reset,
  `attested`/N → `not_yet_attested`/N+1, no remote evidence read). Every
  remote-evidence-consuming operation follows the §19a three-phase
  pattern literally: a short read-only phase-1 capture of the exact
  expected context, the trusted-reader call entirely outside any DB write
  transaction, and a phase-3 write transaction that re-validates every
  captured field by CAS before accepting any transition — a context
  change in between is audited `stale_cas` and accepts nothing;
- a durable `SourceAttestationRelationshipGate` (`clear` /
  `mismatch_pending_reattestation`, ADR 0003 §17), deliberately separate
  from `attestation_status` so a mismatch is never conflated with
  enrollment state: a mismatch (source-level or candidate-level) sets the
  gate pending without touching epoch/anchor; only an accepted anchor
  change or an explicit revocation clears it; a same-anchor
  reconfirmation never clears an already-pending mismatch; the gate never
  gates ordinary read-only discovery;
- `SourceAttestationEvidenceReader` (`app/inventory/attestation.py`) is the
  sole trusted boundary for remote evidence, injected everywhere it is
  needed; no authority method accepts a raw caller-supplied
  `tier2_verified` boolean or any other unverified evidence value. Tier 1
  (asserted PVE root-CA fingerprint, self-reported API data) and tier 2
  (cryptographic TLS-peer-chain-to-enrolled-CA verification, only ever
  produced by the trusted reader) are recorded as structurally distinct,
  durable classes (`AttestationEvidenceTier` +
  `TierTwoEvaluationStatus.not_evaluated/failed/verified`); a tier-1 match
  never becomes tier 2 by association, and a failed/unevaluated tier-2
  result never erases an independently valid tier-1 acceptance. **No
  production PVE network/TLS reader implementation exists** — the
  boundary is real and typed, but every test supplies a deterministic
  fake; concrete cryptographic chain verification against real PVE
  endpoints remains future runtime-integration work, deliberately kept
  outside this dormant wave;
- discovery-run issuance/completion/freshness provenance is fenced by
  `source_attestation_epoch` exactly like every other expected-context
  field ADR 0002 already defines (`source_config_revision`, endpoint
  identity/locator/canonicalization version, `transport_trust_revision`):
  `NormalizedDiscoverySnapshot.expected_source_attestation_epoch` must
  match the issuing run's own captured epoch; a successful completion's
  CAS additionally requires the run's expected epoch to equal the
  *current* durable epoch (read from `source_attestation_state`, never
  audit history) before reconciling anything; a failed run's health
  application uses the identical CAS, so a stale-epoch failure can never
  overwrite current health authority; every successful applicable
  completion records `committed_source_attestation_epoch`, and current
  freshness (`source_is_fresh_for_future_mutation`, expiry materialization)
  requires it to exactly equal the current epoch, alongside the existing
  committed-context fields. `attestation_status` and `relationship_gate`
  never gate ordinary read-only discovery — `not_yet_attested`/epoch 0 and
  a pending mismatch both remain fully legal, indefinitely, for base
  discovery;
- `candidate_attestation_bindings`: epoch-scoped, retained prerequisite
  evidence for a possible future endpoint-activation/failover ADR (ADR
  0003 §14/§15) — **necessary, never sufficient**, and this wave
  implements no activation, promotion, active-endpoint replacement, or
  failover of any kind. `check_candidate_attestation` requires the source
  to already be `attested` with `relationship_gate = clear`, requires the
  target endpoint to belong to the exact source and be in exact
  `lifecycle = 'candidate'` admissibility, and follows the identical
  §19a three-phase pattern against the *candidate's* own endpoint/locator
  (never the active endpoint's) — a candidate retired or otherwise made
  ineligible while the reader is in flight is caught by the same CAS and
  produces no binding. A successful match persists one immutable binding
  row scoped to the exact source/endpoint/epoch/evidence-tier/
  candidate-lifecycle/locator/canonicalization-version/transport-trust
  context, atomically with its originating event, and changes nothing
  else — no epoch bump, no anchor change, no health/freshness write, no
  resource reconciliation, no active-endpoint change, no discovery-run
  fencing. Two schema triggers add defense-in-depth beyond the
  application-layer CAS: the originating event must match the binding's
  full duplicated provenance field-for-field (not merely "some accepted
  candidate_check event exists"), and a new binding may only be inserted
  while the source's *live* current state is itself eligible under the
  exact binding epoch — both are insert-time-only checks; neither
  retroactively invalidates an already-retained binding after the source's
  epoch later advances. A binding is authority-ineligible once the live
  epoch moves past the epoch it was scoped to, but it remains physically
  retained, unmodified, and readable as historical evidence — no purge/
  retention policy exists or is authorized (ADR 0003 leaves that
  unresolved).

### Confirmed removal durable authority (WAVE A1) — implemented but dormant

WAVE A1 extends only the independently instantiated `app.inventory`
subsystem, on schema version **5** (the version-4 marker/objects from
WAVE C1 are rejected without migration, exactly like v1/v2/v3 before
them; there is no in-place v4→v5 data migration policy and none was
authorized). The durable schema/tables this wave added live in the same
schema-v5 authority database the merged R0 composition root now opens at
startup, but `InventoryAuthority.confirm_class_c_resource_removal` is
never called by R0's own call surface — enforced by the same adversarial
spy-based regression test referenced under WAVE C1 above, which also
covers this method. Confirmed removal remains functionally dormant: no
HA/MQTT wiring exposes it, and mutation authority does not exist for R0
at all.

- `resource_absence_pointers`: current sampled-absence provenance (ADR
  0004 §12 retention shape A) — one bounded, durable, mutable-current row
  per currently-`missing` resource, identifying the exact successful
  complete-baseline discovery run that most recently sampled that
  resource's slot absent. Overwritten (never appended) on each
  reconfirming run; deleted once the slot becomes present again, once a
  replaced resource retires, or once its witness is consumed by an
  accepted Class-C decision. Never immutable and never authority by
  itself — a schema trigger requires the referenced run to be a
  successful, complete-baseline, exact-same-source run (or, for the one
  legitimate in-flight case, the exact run currently being finalized by
  the very same reconciliation transaction), making it schema-impossible
  to attach a pointer to a foreign source's run even via direct SQL;
- `resource_removal_authorities` / `resource_absence_attestations`: two
  structurally separate immutable evidence tables implementing ADR 0004's
  two mandatory operator artifacts — Class-C positive removal authority
  (§9: "I am confirming removal of this exact retained resource
  incarnation") and the operator authoritative-absence attestation (§10:
  "this exact old incarnation is no longer the current occupant, and I am
  explicitly authorizing terminal closure on that administrative basis").
  Neither is ever merged into the other or inferred from it; both share
  one backend-generated decision id, and a schema trigger requires the
  attestation row to match its removal-authority row field-for-field
  (identical discipline to WAVE C1's candidate-binding-provenance
  trigger). Both tables are update-blocked and delete-blocked;
- `resource_terminations` (the existing tombstone table, reused as the
  single terminal/tombstone owner — no second tombstone concept was
  introduced) gained a nullable `class_c_decision_id` linkage column and a
  CHECK requiring exactly one of the existing `reason='replaced'` shape
  (non-null successor, null decision link) or the new
  `reason='confirmed_removed'` shape (null successor, non-null decision
  link, and a trigger requiring the linked evidence to match
  resource/binding/generation/run-sequence exactly). `run_sequence`
  continues to mean observation provenance only (ADR 0004 §20) — for
  `confirmed_removed` it is the sampled-absence witness run, never the
  timing of the Class-C decision, which instead lives on the linked
  evidence records' own `actor`/`decided_at`;
- `InventoryAuthority.confirm_class_c_resource_removal`: the explicit,
  dormant, operator-driven authority operation implementing ADR 0004's
  full atomic terminal decision (§9-§24). No remote I/O. Requires two
  independently, strictly-typed boolean assertions
  (`confirms_removal`/`attests_absence`, both must be exactly `True` --
  never a truthy string/int, never inferred from each other) plus exact
  targeting by `resource_id`/`binding_id`/`vmid`/`locator_generation`/
  `resource_continuity_revision`/witness run — there is no VMID-only entry
  point. One `BEGIN IMMEDIATE` transaction re-validates by exact CAS: no
  active discovery owner; source `attested` with `relationship_gate=
  clear`; the resource `missing`/`quarantined` with its exact binding/
  generation/revision still current and not already terminal; the current
  sampled-absence pointer references a witness run that is a genuinely
  successful, complete, boundary-consistent, available baseline, whose
  sequence exactly equals the source's *current* `last_committed_run_
  sequence` and whose committed `source_attestation_epoch` exactly equals
  the source's current epoch; and current source health/freshness/
  committed-context equality (reusing the same expiry-materialization-
  first pattern as `source_is_fresh_for_future_mutation`). Any mismatch
  writes nothing. On success: both evidence records persist; the active
  binding closes with `closure_reason='confirmed_removed'` and
  `valid_to_run_sequence` set to the *witness run's* sequence (observation
  provenance only); the resource reaches the full terminal state ADR
  0001's canonical matrix requires (`presence=confirmed_removed`,
  `lifecycle=retired`, `trusted -> revoked`, preserved last meaningful
  `observational_continuity`, preserved `last_known_node_id`); the
  tombstone is written linked to the decision; each of
  `resource_continuity_revision`/`inventory_revision`/
  `published_state_revision` advances exactly once; every source sequence/
  revision/health field is left completely untouched (no discovery run is
  fabricated); the consumed pointer is deleted; no successor is created.
  Later reappearance of the same slot (even with identical type/name/
  config/node) is handled entirely by the existing, unmodified
  unknown-VMID reconciliation path (ADR 0001/0002) — no new
  reconciliation branch was needed — and always produces a brand-new
  `resource_id`/`locator_generation`/`binding_id` with no inherited trust,
  evidence, or policy of any kind.

- **Real-PVE precheck notes -- effective-permission JSON contract**
  (sixth corrective pass): a real-host read-only precheck against
  **Proxmox VE 9.2.3** disproved an assumption this bootstrap's
  effective-permission verifier had made about the shape of
  `pveum user token permissions`'s JSON output.

  Target: PVE 9.2.3.
  Observed command:
  `pveum user token permissions ha@pve ha-token --path / --output-format json`
  Observed structural result: `{"/":{}}`.
  (No credential or secret is recorded here or anywhere in this repository
  -- only the JSON structural shape.)

  This proves the command returns a **path-keyed** object -- for a token
  actually holding privileges at `/`, the real shape is
  `{"/": {"Sys.Audit": 1, "VM.Audit": 1}}` -- never the flat object of
  privilege names directly at the top level
  (`{"Sys.Audit": 1, "VM.Audit": 1}`) `deploy/lib/bootstrap-identity.sh`'s
  `_verify_effective_permissions` and `tests/_bootstrap_fake_pve.py`'s
  fake had both (independently, wrongly) assumed. Under the old flat-
  object assumption, real PVE 9.2.3's actual path-keyed response would
  have made `actual_keys` come back empty every time (the top-level `"/"`
  value is an object, never truthy `1`/`true`), deterministically failing
  phase 6's exact-set check on every real deployment even when the token
  was correctly configured -- fail-safe (an empty set never equals the
  required nonempty set), but for the wrong reason, on a supported real
  path.

  Fixed: a new `bootstrap-common.sh::_json_truthy_keys_sorted_at_path
  <file> <path>` requires the top level to be an object, the exact
  requested path (`"/"`) to be present, and its value to itself be an
  object -- privilege names are read only from that nested object, never
  flattened in from any other path. Any other shape (missing path, `"/"`
  present but not an object, non-object top level, malformed JSON) is an
  explicit STOP with a message naming the expected path-keyed shape,
  never silently reinterpreted as "zero privileges" for an unrelated
  reason. `tests/_bootstrap_fake_pve.py`'s `pveum user token permissions`

  new regression coverage (both a local-safe pure-helper test class and
  an end-to-end smoke test class) proves: the real observed `{"/":{}}`
  empty-grant shape is schema-valid (and still correctly fails the
  exact-set comparison, on a correctness basis, not a schema basis);
  reordered keys, a missing required privilege, and an unexpected extra
  privilege are each handled correctly; a missing path key, a non-object
  value at `"/"`, a non-object top level, and -- explicitly -- the OLD
  flat-object shape are all rejected, so this cannot silently regress
  back to the invented flat contract. Exact-set semantics

  **P3 -- exception-graph traversal only followed one edge per node,
  then (round 2) was bounded the wrong way.**
  `app/inventory_pve_transport.py::_exception_chain` originally used
  `current.__cause__ or current.__context__`, which silently discards
  `__context__` whenever `__cause__` is also set -- but Python preserves
  both independently (`raise X from Y` sets `__cause__` without clearing
  whatever `__context__` the runtime had already recorded), so a real
  `ssl.SSLCertVerificationError` reachable only through the discarded
  `__context__` edge on a node that also happened to have an unrelated
  `__cause__` would never be found. Round 1 rewrote this as a breadth-
  first walk of both edges from every node, bounded (as first written)
  by total queue *pops* rather than unique nodes visited, reasoning this
  was needed to keep a duplicate-heavy graph from doing unbounded work.
  Round 2's review found that reasoning incorrect: every push onto the
  queue happens only as a direct result of visiting a genuinely NEW
  node, and each such node pushes at most two references, so bounding
  UNIQUE visits at 20 already caps total pushes at 40 (and total pops at
  41) for ANY graph shape -- with no safety benefit from bounding pops
  instead, and a real correctness cost: a genuinely distinct cert error
  within the first 20 unique ancestors could be missed simply because
  earlier duplicate references exhausted a pops-based budget first.
  Final HEAD bounds `_exception_chain` by **20 unique visited nodes**
  (via a `collections.deque`-based BFS and a visited-identity `seen`
  set for cycle-safety), not raw queue pops. Regression tests cover: a
  cert error reachable only through `__context__` while a different,
  non-cert `__cause__` is also set (both as a standalone helper test
  and end to end through `transport.get()`); a duplicate-heavy chain
  (every node's cause and context pointing to the same previous node)
  where a cert error 10 unique hops away is still found DESPITE the
  duplication; and the same shape with the cert error 25 unique hops
  away (beyond the bound) correctly not found.
