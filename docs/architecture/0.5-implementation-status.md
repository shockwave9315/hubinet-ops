## COMPLETE

The following are implemented on `main` and covered by repository/CI tests.

### Canonical Phase 0 snapshot contract

- backend identity uses canonical `backend_instance_id` UUID;
- inventory sources use backend-generated `inventory_source_id` UUIDs;
- resources use opaque backend-generated `resource_id` UUIDs;
- VMID is a source-local locator slot, never durable resource identity;
- `resource_type` is an immutable occupant property;
- active binding identity, locator generation, and `resource_continuity_revision` are distinct concepts;
- source/node/resource references use canonical lower-case hyphenated non-NIL UUID text where the contract requires UUID identity;
- unsupported enum values and malformed security-sensitive canonical values fail closed;
- published mappings/sequences are recursively frozen or rejected when outside the JSON-like contract;
- top-level snapshot collections are detached from caller-owned mutable lists.

### Structural Phase 0 contract layer

- the canonical Phase 0 contract is split into explicit enum, model, primitive,
  source/resource/snapshot/transition validation, and projection modules under
  `custom_components/hubinet_ops/contract/`;
- `custom_components/hubinet_ops/api.py` is a thin API/client/transport
  compatibility facade;
- existing production imports through `.api` remain supported through exact
  object-identity re-exports;
- the split has zero intended semantic change and retains the existing
  accepted/rejected snapshot contract tests.

### Resource state and retained identity

Canonical resource state is split into independent axes:

- presence;
- lifecycle;
- observational continuity;
- security continuity;
- detail status;
- node availability;
- state level.

Implemented constraints include:

- at most one current/active occupant for one `(inventory_source_id, vmid)` slot;
- retained terminal/non-current incarnations coexist with a current successor under distinct `resource_id` values;
- retained locator generations are unique and consecutive within retained history, while retained history need not begin at generation 1;
- current reuse of a retained locator must use the exact next generation;
- active binding IDs cannot be reassigned to another resource after observed ownership/closure;
- terminal resources cannot reopen or silently change immutable identity;
- direct replacement retains old lineage and publishes a distinct successor;
- successor lineage is historical provenance, not a permanent requirement that the successor remain in its initial live state;
- source/node/resource records previously published cannot disappear from a later accepted Phase 0 snapshot;
- node/resource ownership cannot move across inventory sources under the same retained identity;
- same-source rename/runtime/node-presentation changes preserve resource identity;
- terminal and absent resources remain retained but their HA entities are unavailable as required by the accepted presentation contract.

### Security continuity, state level, policy and capabilities

Implemented fail-closed presentation/contract checks include:

- `discovered`, `observed`, `managed`, `maintenance`, and `break_glass` remain semantically distinct;
- normal `policy_applicable=True` is accepted only for otherwise eligible `MANAGED` or `MAINTENANCE` resources;
- `BREAK_GLASS` does not use the normal policy-applicability path;
- `policy_applicable` must be an actual runtime `bool`; malformed truthy values such as strings/integers are rejected;
- non-applicable policy cannot publish effective capabilities;
- effective capabilities are presentation facts from the backend, never frontend-derived authority;
- observed security/continuity/lifecycle/state-level transitions that affect mutation eligibility require a strictly newer `resource_continuity_revision`;
- no `+1` adjacency is required for continuity revisions;
- previously observed trusted/revoked security lower bounds are preserved according to the accepted polling contract;
- `UNVERIFIED -> REVOKED` remains legal because HA may have skipped an intermediate trust/revocation publication.

### Source health, freshness and run provenance

Phase 0 publishes and validates:

- current source health/freshness and origin/reason;
- issued/completed/applied-health/committed run sequence maxima;
- completion and applied-health outcomes;
- fixed last-success/freshness timestamps/deadline;
- exact current and committed source/endpoint/canonicalization/transport-trust context;
- monotonic source config/trust/run provenance visible to HA.

Implemented invariants include:

- `last_committed_run_sequence <= last_health_run_sequence <= latest_completed_run_sequence <= last_issued_run_sequence`;
- health provenance requires completion provenance;
- every published successful applied-health outcome names the exact committed run;
- every published successful completion outcome names the exact committed run;
- an exact committed run carries successful applied-health/completion provenance when those maxima point to it;
- a fresh source requires healthy authoritative discovery-run provenance bound to the exact committed run and committed context;
- `TIME_EXPIRY` is stale and remains fenced to the exact committed run/context;
- reversing an observed expiry back to fresh requires a newer authoritative commit;
- same-token completed/health outcomes and committed success provenance are immutable across accepted snapshots;
- optional durable maxima cannot disappear back to `None` after HA has observed them;
- a newly committed run cannot be retroactively selected from the range of runs a previous accepted snapshot had already observed as finalized;
- polling gaps remain legal: no run-sequence or published-revision adjacency is inferred;
- every successful authoritative inventory reconciliation commit advances `inventory_revision`, including commits with unchanged resource facts;
- other API-visible derived/source-health transitions may advance only `published_state_revision` when the accepted inventory projection is unchanged.

### Source context and endpoint presentation contract

Implemented Phase 0 validation includes:

- provider kind is immutable for an existing source identity;
- current endpoint identity cannot silently change for an existing source;
- endpoint identities cannot be shared across different source identities in one published namespace;
- canonical locator is immutable for the same endpoint/canonicalization contract version;
- controlled canonicalization-version migration may change the canonical locator only under the accepted higher-version/config-revision rules;
- source config/trust revisions remain monotonic without being treated as source identity or physical source-continuity proof.

This is presentation/contract validation only. It is not the Phase 1 endpoint activation/source-binding procedure.

### Home Assistant integration boundary

Implemented and tested:

- one coordinator consumes one logical backend snapshot per refresh;
- backend instance identity binds the config entry;
- foreign backend identity is rejected before publication/registry callbacks;
- resource Device/Entity Registry identity is based on backend/resource UUIDs, never VMID/name/node;
- source -> node -> resource topology is represented through Device Registry parent relations;
- rename and node migration preserve resource identity;
- unresolved/last-known node relations fail closed without inventing mutation routing;
- source freshness, resource detail availability, node availability and resource presence are separate availability gates;
- coordinator does not synthesize `missing` by diffing refreshes;
- config flow reauth/reconfigure preserves backend identity checks;
- diagnostics recursively redact repository secret classes, including camelCase names and namespaced `*_headers` containers, with negative over-redaction controls.

### Phase 1A persistent authority core

- `app.inventory` is an independently instantiable 0.5 authority namespace;
  legacy `OpsService` and legacy `Database` are not owners or dependencies;
- a fresh SQLite authority database uses explicit marker
  `hubinet_ops_0_5_authority`, monotonic schema version `1`, foreign keys, WAL,
  busy timeout, and `BEGIN IMMEDIATE` write transactions; legacy 0.4 and unknown
  non-empty databases are rejected without migration or reset;
- one persistent backend instance owns a stable canonical UUID plus global
  `inventory_revision` and `published_state_revision` initialized to `0` and
  `1` respectively;
- atomic initial source creation persists one backend-generated source UUID,
  one initial active endpoint, one initial non-fresh runtime-health record,
  source configuration revision `1`, transport trust revision `1`, and only a
  credential reference;
- canonicalization contract version `1` supports the accepted HTTPS DNS/IPv6,
  default-port, explicit non-default-port, and root-path normalization while
  rejecting unsupported or ambiguous locators;
- source display rename preserves identity, provider kind, configuration
  revision, endpoint, and active run context while advancing both global
  revisions;
- durable discovery-run issuance captures exact source/endpoint/
  canonicalization/trust context, allocates strictly increasing per-source
  sequence values, establishes one active owner, and advances only the global
  published revision;
- exact issued/running ownership survives restart; same-source concurrent
  issuance has one winner, different sources may own runs concurrently, and a
  controlled one-time abandon fence releases ownership without invented
  observation, completion, health, or commit provenance.

## CONTRACT-ONLY

The accepted architecture defines the following concepts, and Phase 0 publishes/validates enough shape for HA presentation, but their durable backend owners are not implemented yet:

- persistent resource incarnations;
- persistent resource locator bindings/tombstones;
- durable node bindings/attestations;
- provider-derived discovery completion/reconciliation history beyond the
  Phase 1A issued/running/abandoned ownership records;
- source endpoint lifecycle and accepted source-binding/activation procedure;
- successful/failed provider finalization, health application, and commit CAS;
- transactional reconciliation;
- scheduler-independent freshness expiry materialization;
- enrollment/continuity proof;
- stored policy revisions and effective-capability computation;
- maintenance approvals/plans/jobs/locks/audit;
- typed mutation authorization against current identity/binding/revisions;
- durable operation/restart reconciliation;
- final 0.5 break-glass/self-host recovery binding.

Do not treat the existence of Phase 0 fields/validators as proof that these backend mechanisms exist.

## NOT IMPLEMENTED

The following are not implemented as production 0.5 features:

- production Proxmox discovery provider feeding the accepted reconciliation model;
- normalized provider snapshots and provider-derived completion/health finalization;
- source creation/endpoint activation/source-binding UI/API backed by durable 0.5 state;
- production persistent reconciliation engine;
- persistent resource incarnation, locator-binding, generation, and tombstone owner;
- production 0.5 published snapshot/API wiring to the authority database;
- enrollment/trust workflow;
- resource selection/management policy workflow;
- 0.5 policy/plans/jobs/locks/audit and mutation authority;
- production effective-capability engine;
- maintenance/update planning and execution using the 0.5 identity model;
- snapshot/rollback/restore flows bound to the 0.5 resource/binding/revision model;
- restart/crash reconciliation for 0.5 jobs;
- native HA mutation controls for the 0.5 backend path;
- production 0.5 self-update;
- final 0.5 break-glass design;
- independent destructive end-to-end validation of the complete 0.5 mutation path;
- 0.5 public release.

The existing stable 0.4 runtime/recovery mechanisms remain legacy behavior and must not be mistaken for implementation of the clean-break 0.5 contracts above.

## DEFERRED / PHASE 1+

These guarantees require backend/SQLite durable ownership and must not be recreated opportunistically in Home Assistant:

- provider-derived completion history and successful/failed finalization beyond
  the Phase 1A abandon fence;
- CAS/fencing against concurrent source configuration or trust changes;
- atomic resource incarnation creation and binding handoff;
- durable generation/binding allocation;
- source endpoint attestation/activation/failover proof;
- persistent trust/enrollment history;
- policy/approval/job/lock authority;
- scheduler-independent expiry materialization;
- mutation execution and reconciliation after process/host restart;
- final break-glass security model.

A Phase 0 validation proposal that needs any of these is a Phase 1/backend requirement, not a reason to add hidden authority or durable history to HA.
