# Hubinet Ops 0.5 — konceptualny inventory model

Status: **ACCEPTED**

Ten dokument materializuje zaakceptowane decyzje z:

- [ADR 0001: identity zasobu i incarnation](adr/0001-resource-identity-incarnation.md);
- [ADR 0002: read-only discovery i reconciliation](adr/0002-proxmox-discovery-reconciliation.md).

Jest zaakceptowanym modelem architektonicznym, nie schema SQL, migracją ani
kontraktem endpointu. Phase 0 Amendment materializuje jego published snapshot i
HA presentation boundary; persistent ownerzy transaction/reconciliation/
freshness pozostają wymagani w Phase 1. Hubinet Ops 0.5 tworzy nową bazę od zera
i nie importuje SQLite 0.4.

## Identities i relacje

```text
backend_instance
  └─ inventory_sources
       ├─ source_endpoints
       ├─ nodes
       │    ├─ node_bindings
       │    └─ node_attestations
       ├─ discovery_runs
       ├─ source_runtime_health (current 1:1; history via discovery_runs)
       └─ resource_incarnations
            ├─ resource_locator_bindings
            ├─ resource_observations
            ├─ continuity_evidence
            ├─ resource_termination/tombstone (optional 1:1)
            └─ resource_policies + policy revisions (optional, retained)
```

## Encje

### `backend_instance`

- primary identity: losowy `backend_instance_id` UUID;
- immutable: ID, `created_at`;
- mutable: schema/application metadata;
- canonical published-view concurrency: global monotonic `inventory_revision`
  dla committed inventory changes oraz global monotonic
  `published_state_revision` dla każdej API-visible committed transition;
- authoritative: tożsamość instalacji Hubinet Ops;
- retention: cały czas życia nowej bazy;
- constraint: dokładnie jeden aktywny record w jednej bazie.

URL/IP nie jest identity. Clean reinstall bez przywrócenia tej samej bazy tworzy
nową instalację i nowe ID.

### `inventory_sources`

- primary identity: backendowy `inventory_source_id` UUID;
- relacja: należy do `backend_instance_id`;
- immutable: ID, provider kind, `created_at`;
- mutable presentation/observed: display name oraz cluster/standalone facts;
- controlled mutable source configuration: lifecycle/configuration state
  istotny dla discovery, provider/discovery settings, credential/secret
  reference, active discovery-route lifecycle oraz wymagane provider contract
  parameters;
- monotonic concurrency contract: `source_config_revision`, inkrementowany
  atomowo przy każdej zmianie controlled source configuration wpływającej na
  znaczenie lub dopuszczalność discovery runu; revision nigdy nie jest source
  identity i nie jest cofany ani ponownie używany;
- monotonic issuance state: `last_issued_run_sequence`, zwiększany atomowo przed
  każdym fetch i nigdy niecofany ani reused;
- monotonic committed-run fence: `last_committed_run_sequence`, aktualizowany
  atomowo wyłącznie przy udanym reconciliation commit; jest osobny od
  `last_issued_run_sequence`, niezależny od `source_config_revision` i nie jest
  source identity ani samodzielny proof kolejności physical observations;
- durable single-flight ownership: nullable `active_discovery_run_id` albo
  równoważny fencing token wskazujący jedyny run uprawniony do provider I/O i
  późniejszej finalization/reconciliation dla tego source;
- canonical ownership: `inventory_sources` jest jedynym durable source of truth
  dla `source_config_revision`, `last_issued_run_sequence` i
  `last_committed_run_sequence` oraz active-run ownership; published source view
  może je agregować, ale `source_runtime_health` nie przechowuje drugiej
  authoritative kopii;
- constraints: source ID unikalny w backendzie; nazwa klastra nie jest unique
  identity;
- authoritative: operatorowa definicja granicy jednego Proxmox environment;
- retention: trwała; po usunięciu source pozostaje historyczny record.

Credentials są przechowywane poza observation/audit payloads. Record zawiera
secret reference, nie jawny token. Rotacja credential material/version — także
pod tym samym secret reference — zmiana samego reference, provider/discovery
settings, discovery-relevant lifecycle/configuration state albo wymaganych
contract parameters — w tym configured freshness duration — zwiększa
`source_config_revision`. To samo dotyczy
controlled transition lub canonicalization migration zmieniającej active
discovery route. Zmiana wyłącznie display label, inert candidate metadata albo
zapis nowych observed facts nie zwiększa revision, ponieważ nie zmienia
interpretacji bieżącego runu.

Source configuration mutation i reconciliation commit muszą serializować się w
jednej backendowej concurrency boundary. Run zapisuje expected revision pobrany
przed fetch. Commit jest dozwolony wyłącznie, gdy bieżąca wartość nadal jest
równa expected; mismatch oznacza invalid/stale run, bez reconciliation i bez
publikacji snapshotu. Oddzielne exact checks endpointu, canonical locatora,
canonicalization version i TLS trust revision pozostają obowiązkowe.

Phase 1 stosuje **per-source single-flight discovery**: dla jednego
`inventory_source_id` najwyżej jeden run może posiadać active ownership, wykonywać
provider I/O i pozostawać eligible do późniejszej finalization/reconciliation.
Różne sources mogą wykonywać discovery równolegle. Issuance wymaga braku active
ownera i w jednej trwałej transaction atomowo inkrementuje
`last_issued_run_sequence`, utrwala exact expected source/endpoint/
canonicalization/transport-trust context wraz z provider contract/version,
zapisuje **issued** `discovery_runs` record z otrzymaną wartością oraz wyłącznie
znanymi issuance fields i ustawia jego `run_id` jako active discovery owner.
Ponieważ `last_issued_run_sequence` jest publikowane, ta sama transaction
zwiększa globalny `published_state_revision`; dopiero po commit rozpoczyna się
pierwsze provider I/O.
Ta issuance/context transaction serializuje się z controlled source/endpoint/
transport mutation, aby expected context nie był mieszanką revisions.
Allocation jest unique i strictly increasing per `inventory_source_id`, przeżywa
restart/crash i nie używa wall clock ani `last_committed_run_sequence + 1`.
Nieudany/crashed run zostawia dozwoloną lukę; następna alokacja zawsze zwraca
wartość większą od poprzednio wydanej. Gdy dwa triggery tego samego source
konkurują o wolny ownership, dokładnie jeden może atomowo issue run i rozpocząć
I/O; drugi nie alokuje overlapping eligible runu i może być później
queued/coalesced/rejected zgodnie z osobnym scheduling contract.

### `source_endpoints`

- primary identity: `endpoint_id` UUID;
- relacja: wiele endpointów do jednego source;
- immutable w zwykłym lifecycle: ID, `inventory_source_id`, stored canonical
  HTTPS URL/transport locator i `canonicalization_contract_version`, która go
  wytworzyła; initial pair pozostaje w creation provenance/audit, a każda
  controlled migration dopisuje immutable old/new provenance;
- mutable operational: health/availability i non-identity metadata;
- controlled mutable: lifecycle status (`active`, `candidate`, `inactive`,
  `retired`) oraz TLS policy/fingerprint metadata wraz z monotonic
  `transport_trust_revision`, wyłącznie przez audytowane state transitions;
  nadanie `active` nie jest direct field assignment;
- constraints:
  - dokładnie jeden endpoint ma status `active` dla aktywnego source;
  - candidate/inactive endpoints nie uczestniczą w discovery, retry ani
    automatic failover;
  - operatorowa zmiana URL nie może zmodyfikować istniejącego record; nowy URL
    tworzy nowe `endpoint_id` jako `candidate`; jedynym wyjątkiem zmiany stored
    canonical pair jest controlled version migration opisana niżej;
  - `(inventory_source_id, canonical_transport_locator)` jest unikalne w
    retained endpoint history; retire/recreate tego samego URL używa historii
    istniejącego record, a reactivation nadal podlega source-binding gate;
    `canonicalization_contract_version` nie tworzy alternatywnego namespace dla
    tego constraint;
  - endpoint record nigdy nie zmienia `inventory_source_id`;
  - direct candidate/inactive → active, direct active replacement oraz
    delete/recreate-as-active wymagają accepted source-binding procedure;
  - historyczny active endpoint i jego relation/provenance nie są hard-deleted,
    więc recreation nie zeruje gate;
  - retire active endpointu wyłącza discovery source i nie pozwala bezpośrednio
    wskazać zastępstwa;
  - disable/re-enable source nie przywraca initial-creation exception;
- authoritative: operatorowa konfiguracja transportu, nie identity source;
- retention: historyczne bindings zachowane w audit.

Canonical transport locator powstaje przed zapisem przez jedną
deterministyczną, wersjonowaną canonicalization function. Raw user URL nie jest
kluczem equality ani history lookup. Contract normalizuje HTTPS scheme, casing
DNS, canonical IPv6/brackets, brak portu względem jawnego `:443`, non-default
port, root/trailing slash; fail-closed odrzuca userinfo, query, fragment oraz
ambiguous/invalid URL. Brak portu nie oznacza automatycznie PVE `:8006`; direct
PVE wymaga jawnego portu. Reverse-proxy subpaths nie są wspierane bez późniejszego
contract/evidence.

Dwa teksty URL dające ten sam canonical locator wskazują tę samą retained
endpoint history i nie mogą utworzyć niezależnych identities. Reactivation albo
alias istniejącego locatora nadal podlega source-binding gate. Implementacja
wymaga wersjonowanych positive/negative canonicalization contract tests.
Przykładowo `https://PVE.EXAMPLE/` i `https://pve.example:443` są jednym
locatorem, lecz `https://pve.example:8006/` jest odrębnym non-default locatorem.

### Lifecycle wersji canonicalization

Stored pair `(canonical_transport_locator,
canonicalization_contract_version)` nie jest po cichu reinterpretowana po
upgrade backendu. Zmiana algorytmu/version wymaga explicit, audytowanej
schema/data migration albo równoważnej controlled migration procedure. Tylko ta
procedura może atomowo zastąpić stored canonical pair, zachowując immutable
historię wartości przed/po; nie jest to zwykła mutacja endpointu.

Migration musi:

- zachować `endpoint_id` i immutable relation do `inventory_source_id`;
- zachować pełne source-binding, activation i retained-history gates;
- deterministycznie przeliczyć cały retained endpoint namespace, nie tylko
  active records;
- wykryć textual aliases i collisions między wszystkimi retained endpointami;
- fail-closed zatrzymać migration przy ambiguity/collision, bez automatycznego
  merge historii, stworzenia drugiej endpoint identity albo nadania `active`;
- zachować audyt starej i nowej canonical pair oraz migration provenance.

Canonicalization version nie tworzy osobnego uniqueness namespace. Nowy raw URL
po upgrade nie może ominąć retained-history/source-binding gate przez zapis pod
nowszą wersją. Przed endpoint create/reactivation backend musi mieć zakończoną i
jednoznaczną migration retained namespace albo równoważny, jawnie zaakceptowany
cross-version lookup contract. Przy braku możliwości honorowania starej wersji
lub kolizji operacja jest `configuration_error`/blocked; nie powstaje nowy
record. Implementacja wymaga positive/negative contract tests dla version
upgrade, cross-version alias i collision.

Nieudana migration jest atomowa: pozostawia stare canonical pairs i wersje bez
zmian. Discovery istniejącego endpointu może być kontynuowane tylko wtedy, gdy
backend nadal potrafi wykonać i zweryfikować zapisany stary contract; w
przeciwnym razie source ma `configuration_error`. Create/reactivation pod nowym
contractem pozostaje zablokowane do jednoznacznego resolution.

Atomowe initial source creation tworzy nowy `inventory_source_id`, dokładnie
jeden initial active endpoint, initial non-fresh `source_runtime_health` oraz
zwiększa globalny `published_state_revision`. Po commit tej transaction source
jest existing; każda późniejsza zmiana transport targetu tworzy inert candidate.
Niedostępność active endpointu daje `source_unavailable`; backend nie próbuje
candidate endpointu.

Aktywacja candidate, replacement active endpointu albo multi-endpoint failover
wymaga późniejszego zaakceptowanego source-binding/attestation contract. Dopóki
go nie ma, operator potrzebujący innego endpointu tworzy nowy
`inventory_source_id`. Cluster name, node membership, VMIDs, hostname, IP, DNS,
TLS certificate/fingerprint i URL nie wystarczają samodzielnie do związania
endpointu z istniejącym source.

Stable URL nie jest proof physical source continuity: DNS/reverse-proxy change
lub rebuild może skierować ten sam locator do innego environment. To świadoma
observational limitation read-only Phase 1, nigdy podstawa destructive trust.
Security-sensitive TLS configuration ma monotonic
`transport_trust_revision` albo równoważną wersję contractu. Każda zmiana jest
explicit, audytowana i kontrolowana; discovery run wiąże exact `endpoint_id`,
canonical locator i expected trust revision. Zmiana revision w trakcie runu
unieważnia commit wyniku pod poprzednim contractem. Broadening/replacement CA
roots, pin/fingerprint albo verification policy wymaga revalidation i nie nadaje
source identity ani nie omija activation gate. Normalne CA-valid certificate
renewal przy niezmienionej configured trust policy jest peer-observation change;
rotation exact pin jest security-sensitive transition. TLS trust revision nigdy
nie jest source-binding proof, a pełny rotation/attestation protocol pozostaje do
security review.

### `nodes`

- primary identity: backendowy `node_id` UUID;
- relacja: należy do source;
- immutable: ID, source, first seen;
- mutable: display name, presentation presence i `last_seen`; external node name
  należy do wersjonowanego `node_binding`, nie jest swobodnie nadpisywanym polem;
- constraints: security routing nigdy nie używa samego `node_id` ani nazwy;
- authoritative: backend dla internal identity; discovery dla current facts;
- retention: historyczna identity nie jest natychmiast usuwana.

Node name i Corosync nodeid są evidence/locator facts. Bez oficjalnej globalnej
immutable gwarancji nie zastępują backendowego `node_id`.

`node_id` może zachować HA presentation continuity po operatorowym potwierdzeniu,
ale samo zachowanie `node_id` nie zachowuje mutation trust.

### `node_bindings`

- primary identity: `node_binding_id` UUID;
- relacja: należy do `node_id` i `inventory_source_id`;
- immutable: external node name, binding generation, `valid_from`, enrollment
  provenance;
- mutable: `valid_to`, trust state (`unverified`, `trusted`, `revoked`) i
  monotonic `binding_revision`;
- constraints:
  - co najwyżej jeden aktywny binding dla `(inventory_source_id,
    external_node_name)`;
  - co najwyżej jeden aktywny trusted binding dla `node_id`;
  - każda zmiana security-relevant evidence zwiększa revision albo zamyka
    binding;
- authoritative: backendowa decyzja, który obserwowany host może być mutation
  target;
- retention: historia bindingów bezterminowo.

Binding jest minimalnym odpowiednikiem node incarnation dla granicy wykonawczej,
bez przesądzania, że presentation `node_id` zawsze musi zmieniać się przy
reinstall. Nowy host używający starej nazwy nigdy nie przejmuje active trusted
binding automatycznie.

### `node_attestations`

- primary identity: `attestation_id` UUID;
- relacja: należy do dokładnego `node_binding_id` i revision;
- immutable: typ evidence, fingerprint/public-key identity lub inny później
  zaakceptowany proof, provenance, `verified_at`;
- mutable: validity/revocation metadata;
- authoritative: backend dla statusu trust; zewnętrzne certificates/keys są
  evidence, nie backendową identity;
- retention: bezterminowo dla każdego bindingu użytego do mutacji.

Konkretny attestation protocol pozostaje unresolved. Certyfikat TLS endpointu
discovery, PVE node certificate, SSH host key i hostd identity nie mogą być
zamiennie traktowane jako ten sam proof.

### `resource_incarnations`

- primary identity: `resource_id` UUID — trwała backendowa inventory identity;
  dla `unverified` nie jest proof fizycznej incarnation;
- relacja: należy do source;
- immutable: ID, source, `resource_type`, `first_seen`;
- mutable: lifecycle (`active`, `quarantined`, `retired`), observational
  continuity (`consistent`, `uncertain`, `replaced`), security continuity
  (`unverified`, `trusted`, `revoked`), published presence (`present`, `missing`,
  `confirmed_removed` albo terminalne `not_current`), reconciled
  `detail_status`, `node_availability`, `last_seen`, enrollment state/revision i
  monotonic `resource_continuity_revision`;
- constraints: resource ID nie jest wyliczany z VMID/nazwy/node'a;
- authoritative: backendowa identity inventory record; physical
  incarnation dopiero po zaakceptowanym security continuity proof;
- retention: bezterminowa w audit/history.

Taxonomy i valid-state matrix są kanonicznie zdefiniowane w
[ADR 0001](adr/0001-resource-identity-incarnation.md#kanoniczny-model-stanu-i-continuity).
`retired` jest lifecycle, nigdy observational continuity. Confirmed removal
zachowuje ostatnie znaczące observational `consistent|uncertain`; direct
replacement ustawia old resource na `not_current`/`retired`/`replaced`.

`resource_continuity_revision` zaczyna od jawnej initial revision i zwiększa się
przy `consistent→uncertain`, wejściu/wyjściu z quarantine, zmianie
`security_continuity`, enrollment/proof/anchor revision, trust revocation,
accepted terminal transition i każdej przyszłej security-relevant continuity
decision. Rename, runtime/detail/display facts ani zwykły config change bez
continuity decision nie zwiększają revision. Token nie jest identity,
`locator_generation`, policy revision ani node `binding_revision`.

Nie wprowadzamy osobnego „logical service ID” w tej fazie. Jeśli przyszły
product model będzie łączył kolejne incarnations tej samej usługi, lineage jest
osobną, operatorową relacją i nie może przenosić destructive policy.

Zgodne kompletne polling observations mogą zachować `resource_id` resource'u
`unverified` dla UX/HA. Niewidoczny delete/recreate może być nierozróżnialny i
również zachować tę read-only identity. Dlatego `resource_id` bez
`security_continuity=trusted` nigdy nie autoryzuje mutacji.

Observable gap albo continuity ambiguity bez positive replacement proof i bez
wcześniejszego `confirmed_removed` również zachowuje istniejący `resource_id`
oraz active locator binding. Resource może wrócić do `presence=present`, ale ma
observational continuity=`uncertain`, lifecycle=`quarantined`, security
continuity=`revoked`/`unverified`, policy applicability=false oraz effective
destructive/maintenance capabilities=`none`. Stored policy/history pozostają;
`resource_continuity_revision` zwiększa się i unieważnia wcześniejsze
approvals/jobs, lecz `binding_id` i `locator_generation` nie zmieniają się. Nie
powstaje provisional identity.

### `resource_locator_bindings`

- primary identity: `binding_id` UUID;
- relacja: jedna incarnation ma co najmniej jeden historyczny binding;
- slot locator: `(inventory_source_id, vmid)`;
- immutable: binding ID, locator, `locator_generation`, `valid_from` oraz
  optional `opened_at_resource_continuity_revision` jako provenance;
- controlled mutable przy closure: `valid_to`, closure reason;
- constraints:
  - jeden aktywny binding na `(inventory_source_id, vmid)`, niezależnie od
    `resource_type`;
  - jeden aktywny primary binding na resource;
  - unique `(inventory_source_id, vmid, locator_generation)`;
- authoritative: backendowy wynik reconciliation;
- retention: bezterminowa historia slotu.

Phase 0 polling consumer odrzuca reassignment `binding_id`, którego ownership
był widoczny w jego poprzednim zaakceptowanym snapshotcie. Ponieważ terminalny
published resource view nie publikuje zamkniętych binding IDs, HA nie
rekonstruuje lokalnie kompletnej lifetime uniqueness. Persistent
`resource_locator_bindings` w Phase 1 jest authoritative dla globalnej,
bezterminowej gwarancji ownership `binding_id`.

Locator binding nie przechowuje „expected continuity revision” jako bieżącego
security tokenu. Authorization zawsze sprawdza current
`resource_continuity_revision` na resource. Closure niezależnie wymaga exact
active `binding_id`, active state i expected `locator_generation`.

`locator_generation` rośnie dla nowego bindingu wyłącznie przy atomic direct
replacement z positive replacement evidence albo gdy locator wraca po
prawidłowym `confirmed_removed`. Nierozstrzygnięta luka/ambiguity nie zamyka
bindingu i nie zwiększa generation. Licznik nie jest identity ani samodzielnym
dowodem replacement.
Dla nowego bindingu po retained terminal history tego samego locatora wartość
wynosi dokładnie `max(retained locator_generation) + 1`; reuse, regresja ani
arbitralne pominięcie generation nie jest legalnym published handoffem.
W kompletnym retained published history posortowane istniejące generations dla
jednego `(inventory_source_id, vmid)` są kolejnymi wartościami bez luk pomiędzy
minimum i maximum. Minimum nie musi wynosić `1`; Phase 0 waliduje spójność
opublikowanej historii, lecz nie alokuje generation.
`resource_type` pozostaje immutable w `resource_incarnations` i opisuje occupant
slotu. Schema zabrania jednoczesnego aktywnego LXC101 i QEMU101 w jednym source.

Direct replacement nie wymaga pustego slotu. Jedna reconciliation transaction
weryfikuje exact old `resource_id`, active `binding_id`, `locator_generation`,
current `resource_continuity_revision` i positive replacement evidence, zamyka
stary binding z `closure_reason=replaced`, zwiększa `locator_generation` oraz
tworzy successor `resource_id` i dokładnie jeden nowy active binding dla tego
samego slotu. Old resource może być dowolnym nonterminal resource z exact active
bindingiem, w tym `present/active`, `present/quarantined` albo
`missing/quarantined`; ambiguity sama nie jest replacement evidence. Unique
active-slot constraint obowiązuje przez cały commit; żaden stan z dwoma active
bindings nie może zostać zapisany ani opublikowany.
`closure_reason=confirmed_removed` jest zarezerwowane dla ścieżki z
authoritative absence proof i nie zastępuje `replaced`.

Stan początkowy successora (`unverified`/`discovered`, bez odziedziczonej policy,
approvals, jobs ani locks) jest invariantem atomowej transakcji reconciliation,
której canonical ownerem będzie persistent backend Phase 1. Retained lineage
`old → successor` jest natomiast trwałym faktem historycznym: w późniejszych
published views successor może niezależnie przejść enrollment, quarantine,
removal albo kolejne replacement, bez przepinania historycznego wskaźnika old.
Phase 0 polling consumer może pominąć dowolną liczbę published revisions, więc
nie próbuje retrospektywnie dowodzić chwilowego initial handoff state pomiędzy
dwoma zaobserwowanymi snapshotami; waliduje wyłącznie retained lineage i te
transition invariants, które pozostają prawdziwe mimo takiej luki.
Dotyczy to również transient security path poprzednika: consumer nie rekonstruuje
pośrednich enrollment, trust i revocation z pominiętych published revisions.
Zachowuje jednak znaną historyczną dolną granicę we wszystkich później
obserwowanych stanach tego samego `resource_id`: zaobserwowane `trusted` albo
`revoked` nie może wrócić do `unverified`. `Revoked -> trusted` pozostaje
reprezentowalne, jeśli przyszły accepted enrollment contract i bieżąca macierz
stanu na to pozwalają. Wcześniejsze `unverified` może przejść bezpośrednio do
`revoked`, ponieważ polling consumer mógł pominąć enrollment i revocation.
Terminalnie znane `trusted`/`revoked` wymaga `revoked`; exact replacement
revocation pozostaje invariantem atomowej transakcji reconciliation należącej
do persistent backendu Phase 1.

### `discovery_runs`

- primary identity: `run_id` UUID;
- relacja: należy do source;
- issuance fields, immutable od utworzenia: `run_id`, `inventory_source_id`,
  monotonic per-source `discovery_run_sequence`, issued/start timestamp,
  expected `source_config_revision`, exact expected `endpoint_id`, expected
  canonical transport locator i `canonicalization_contract_version`, expected
  `transport_trust_revision` oraz provider contract/version potrzebny do
  interpretacji runu;
- completion/finalization fields, początkowo unset i zapisywane dokładnie raz
  przez kontrolowaną terminal transition: finish/completed timestamp,
  `observed_at` lub observation interval, fetch/outcome classification,
  `baseline_completeness`, covered/failed baseline scopes, optional provider
  cursor range, canonical ACL topology snapshot/hash BEFORE i AFTER, effective
  per-path permission snapshot/hash BEFORE i AFTER, derived permission coverage,
  boundary consistency, optional interval-wide evidence reference,
  `detail_error_count`, failed detail scopes, normalized snapshot hash,
  commit-observed source/endpoint/canonicalization/transport-trust context —
  tylko jeśli run osiągnął reconciliation transaction — oraz terminal/failure
  reason i redacted errors;
- lifecycle: minimalnie `issued`/`running`/`completed`/`abandoned` albo
  równoważny zamknięty kontrakt; `issued`/`running` może pozostać incomplete po
  crash, a `abandoned` nie wymaga wymyślonych observation/completion danych;
- single-flight constraints: issuance wymaga braku active ownera i ustanawia
  `inventory_sources.active_discovery_run_id=run_id`; każda terminal finalization
  wymaga zarówno nonterminal run record, jak i exact current active ownership,
  po czym atomowo zwalnia ownership; commit dodatkowo wymaga
  `discovery_run_sequence > inventory_sources.last_committed_run_sequence` oraz
  `discovery_run_sequence > source_runtime_health.last_health_run_sequence`, po
  czym atomowo aktualizuje canonical commit token i successful health outcome;
  sequence może mieć luki po failed/crashed runs; `(inventory_source_id,
  discovery_run_sequence)` jest unique, a issued run record powstaje w tej samej
  durable transaction co issuance; finalization jest compare-and-set z unset do
  terminal values dokładnie raz, a druga lub sprzeczna finalization jest
  odrzucana; po finalization completion fields są immutable/audit-retained;
- authoritative: audit tego, co provider faktycznie odczytał;
- retention: długoterminowa; payload może podlegać bezpiecznej kompakcji, ale
  decyzje continuity/termination muszą zachować provenance.

`baseline_completeness` opisuje wyłącznie source-wide locator enumeration i jej
wymagane prerequisites. `detail_error_count` oraz failed detail scopes są
osobną osią diagnostyczną. Błąd detail jednego resource nie może zmienić
`baseline_completeness=complete` na `partial`.

Incomplete issued run nie jest sztucznie uzupełniany outcome, snapshot hash ani
observation/finish timestampem. Przed issue kolejnego runu restart recovery albo
timeout/cancel path musi w jednej controlled transaction one-time
terminalizować osieroconego ownera jako `abandoned`/`cancelled` z rzeczywistym
reason i terminalization timestampem, pozostawić niezaobserwowane completion
fields unset, zapisać completion audit i — jeśli outcome jest applicable —
fail-closed zaktualizować health/freshness oraz published revision bez resource
reconciliation, a następnie zwolnić ownership. Sequence pozostaje zużyty. Late
worker po fence nie może ponownie finalizować runu, reconcile inventory,
aktualizować health ani publikować zmian.

Successful reconciliation finalizuje run i zwalnia jego exact active ownership
w tej samej atomic transaction co inventory commit. Newest applicable
failed/partial/unavailable/invalid run analogicznie wymaga exact ownership i
finalizuje się wyłącznie w jednej atomic transaction razem z completion-audit
max update, ponowną walidacją current context, health CAS,
mutation-freshness invalidation, `published_state_revision` update i zwolnieniem
ownership. Run nieapplicable do current context może zostać
sfinalizowany/audytowany i zwolnić ownership tylko jeśli nadal jest exact active
ownerem; nie może zmienić current health. Jeśli controlled transition wcześniej
go fenced/terminalized, późniejszy worker nie wykonuje żadnej drugiej
finalization. Run zakończony przed reconciliation pozostawia commit-observed
fields unset.

Mismatch `source_config_revision`, endpoint/canonicalization provenance albo
transport trust revision klasyfikuje run jako invalid/stale i uniemożliwia
reconciliation/published snapshot commit. Exact active ownership oraz committed/
health sequence guards odrzucają także late albo stale worker. Sam wyższy
`discovery_run_sequence` dowodzi późniejszego issuance, nie późniejszej physical
observation. Ordering eligible observations w Phase 1 wynika z per-source
single-flight: run N terminalizuje się i zwalnia ownership przed pierwszym
provider I/O runu N+1. Wall-clock timestamp nie jest concurrency authority.
Redacted audit failed run może zostać zapisany osobno; nie staje się committed
inventory observation.

### `source_runtime_health`

To conceptual durable state oddzielający last committed inventory, run-derived
health provenance oraz current health/freshness, które może także wynikać z
initial state albo controlled context transition:

- primary identity: dokładnie jeden current record na `inventory_source_id`;
- completion audit: `latest_completed_run_sequence` i redacted
  `latest_completed_outcome`, wybierane według najwyższego completed sequence,
  nie wall-clock completion time;
- applied run-health provenance: `last_health_run_sequence` jest najwyższym
  sequence, którego run-derived health outcome został kiedykolwiek skutecznie
  zastosowany, a `last_run_health_outcome` opisuje ten run; exact context należy
  do powiązanego immutable `discovery_runs` recordu i nie musi być bieżącym
  source/transport contextem;
- current presentation: current source health/freshness oraz jawne
  `current_health_origin` i `current_health_reason`; origin rozróżnia co najmniej
  `discovery_run(sequence)`, `controlled_context_transition`, `time_expiry` i
  `initial/not_yet_observed`;
- successful inventory/freshness provenance: fixed
  `last_successful_observed_at`, observation-derived `freshness_reference_at`,
  fixed `freshness_valid_until`/`fresh_until`, committed run sequence oraz exact
  context tego commitu:
  `committed_source_config_revision`, `committed_endpoint_id`, canonical
  transport locator/version i `committed_transport_trust_revision`; deadline
  należy do tego exact run/contextu i nie przesuwa się przy API read;
- current health/freshness może obejmować np. `healthy/fresh`, `stale`,
  `source_unavailable`, `partial/degraded`, `configuration_error`, invalid
  current-context observation albo `not_yet_observed`; finalny enum pozostaje
  implementation contract, lecz fresh jest dozwolone wyłącznie po
  authoritative successful applicable commit i przed jego fixed freshness
  deadline;
- constraints: health update jest CAS-chronione i dozwolone tylko, gdy
  `run.discovery_run_sequence > last_health_run_sequence` oraz run zachowuje
  exact active ownership; late/fenced worker nie może nadpisać health, nawet gdy
  sequence check sam byłby spełniony; completion-audit token ma analogiczny
  monotonic max-sequence guard, lecz sam nie zmienia current health;
- authoritative: backendowa ocena aktualnej jakości/freshness obserwacji source,
  nie resource presence ani physical removal;
- retention: current state oraz historyczne run/audit provenance; last committed
  inventory pozostaje oddzielnie zachowany.

`source_runtime_health` jest jedynym canonical durable ownerem
`latest_completed_run_sequence/outcome`, `last_health_run_sequence`,
`last_run_health_outcome`, current health/freshness/origin/reason oraz
last-successful/deadline/context metadata. `last_issued_run_sequence` i
`last_committed_run_sequence` są wyłącznie własnością `inventory_sources`;
published source view jedynie agreguje obie encje.

Agregowany published view zachowuje partial order provenance:

```text
last_committed_run_sequence
  <= last_health_run_sequence
  <= latest_completed_run_sequence
  <= last_issued_run_sequence
```

Optional token nie może pozostawić wymaganej przez siebie wcześniejszej warstwy
provenance jako unset: commit wymaga applied health, a applied health wymaga
completion. Completion-only run i
applied failed health bez commitu są legalne; sekwencje nie muszą być adjacent.

Jeżeli committed context istnieje, bieżący context nie może być historycznie
starszy: current config, transport-trust i canonicalization revisions są większe
lub równe committed revisions. Current i committed context wskazują ten sam
`endpoint_id` w obecnym Phase 0 source-binding contract. Przy tej samej
canonicalization version locator jest identyczny; wyższa current version może
zmienić locator wyłącznie jako controlled canonicalization migration z wyższym
`source_config_revision`.

„Applicable” oznacza zgodność runu z current context sprawdzoną **wewnątrz tej
samej transaction**, która miałaby zastosować run-derived health. Transaction
ponownie weryfikuje expected `source_config_revision`, exact active
`endpoint_id`, canonical locator/version i `transport_trust_revision`; check
przed transaction nie jest wystarczający. Run ze starym contextem może zostać
sfinalizowany/audytowany i podnieść `latest_completed_run_sequence/outcome`, ale
nie nadpisuje current health nowego contractu.

Controlled zmiana source config/active route/canonicalization/TLS contractu w
jednej atomic transaction aktualizuje odpowiedni context/revision, ustawia
current health jako stale, `current_health_origin=controlled_context_transition`
i jawny reason, unieważnia mutation freshness oraz zwiększa
`published_state_revision`. Serializuje się z issuance, successful
reconciliation i failed-run health application. Gdy source ma active run,
implementation albo czeka na jego terminal finalization/release, albo w tej
controlled boundary atomowo terminalizuje i fences run z rzeczywistym reason,
zwalnia ownership, a dopiero potem może issue run nowego contextu. Nie wolno
rozpocząć nowego provider I/O równolegle ze starym eligible observation window.
Sama context transition bez fencing nie zmienia run-derived provenance. Jeżeli
ta sama controlled transaction terminalizuje active run, może zgodnie z
one-time-finalization contract zaktualizować prawdziwy completion audit i
published revision, lecz nie tworzy fake observation ani successful run-health
outcome; current health origin pozostaje `controlled_context_transition`.
Żadna ścieżka nie cofa sequence. Current inventory pozostaje not mutation-fresh
do pierwszego udanego commitu pod nową revision; wtedy origin zmienia się na
`discovery_run(sequence)`.

Initial source creation atomowo tworzy source, dokładnie jeden initial active
endpoint oraz wymagany `source_runtime_health` record z origin
`initial/not_yet_observed`, jawnie non-fresh state i unset last-success
oraz freshness-reference/deadline provenance, unset active discovery ownership
oraz zwiększa `published_state_revision`, ponieważ source pojawia się w API.
Origin `initial/not_yet_observed` nie może zawierać applied run-health ani commit
provenance. Może zawierać issued-only albo completion-only audit, jeżeli żaden
run-derived health outcome nie został zastosowany.
Przed pierwszym udanym inventory commit `last_committed_run_sequence` jest
unset/null (lub używa
jednoznacznego initial sentinel zgodnego z allocator contract), a effective
destructive capabilities są `none`. Monotonic sequence nie są resetowane przez
zmianę health ani contextu.

Successful authoritative run używa jednej atomic transaction obejmującej:
exact active ownership check, one-time finalization i completion provenance,
ponowną exact current-context validation, inventory reconciliation, canonical
`inventory_sources.last_committed_run_sequence`, health/freshness i
last-successful provenance wraz z observation-derived `freshness_reference_at`
i nowym fixed freshness deadline należącym do exact run/contextu,
`inventory_revision` oraz
`published_state_revision` oraz release ownership. Failed, partial, unavailable
albo invalid newest applicable run używa jednej atomic transaction obejmującej:
exact active ownership check, one-time finalization,
`latest_completed_run_sequence/outcome` max update, exact applicability
validation, `last_health_run_sequence` CAS,
`last_run_health_outcome`, current health/freshness/origin/reason,
mutation-freshness invalidation, `published_state_revision` oraz release
ownership. Nie wykonuje resource reconciliation ani
identity/presence/missing/removal/replacement transitions. W obu ścieżkach
wszystko commit albo nic commit; nie ma stanu „failed run finalized, health nadal
fresh” ani „run finalized, ownership nadal active”.

Dla prostych fail-closed semantics successful inventory commit również wymaga,
aby żaden wyższy `last_health_run_sequence` nie był już zapisany. Single-flight
normalnie wyklucza nowszy eligible outcome przed terminalizacją active runu;
sequence/CAS i exact ownership pozostają defense-in-depth przeciw late workerowi
po fence albo niespójnemu stanowi i nigdy nie uprawniają overlapping I/O.

Każdy newest applicable outcome, który nie jest authoritative successful
inventory commit i podważa current-state confidence — w tym
`source_unavailable`, partial/degraded, `configuration_error` oraz invalid
current-context run z naruszeniem schema, uniqueness lub boundary contract —
ustawia inventory jako not mutation-fresh. Audit-only invalid run ze starym
contextem nie jest applicable i nie nadpisuje current health. Security gate nie
może zależeć od przypadkowej nazwy enumu: fresh istnieje wyłącznie od udanego
applicable commitu do najwcześniejszego z fixed deadline, controlled context
transition albo nowszego applicable outcome, który tę pewność unieważnia.

### Controlled freshness expiry

Każdy provider contract definiuje wersjonowany sposób wyznaczenia fixed
`freshness_reference_at` z faktycznie accepted observation window/provider
observation. Anchor musi być konserwatywny względem wszystkich wymaganych facts
tworzących authoritative inventory snapshot: nie może być późniejszy niż
najstarsza freshness-relevant obserwacja, chyba że oficjalnie zweryfikowany
provider contract dowodzi wspólnego authoritative snapshot time. Gdy provider
nie daje takiego timestampu, contract wybiera równoważny, nie mniej
konserwatywny boundary z observation window. Reconciliation commit time, API
read time ani timer execution time nigdy nie są tym anchorem.

Successful applicable commit wylicza według jawnego freshness-duration contract
`freshness_valid_until = freshness_reference_at + configured duration` albo
wcześniejszy, bardziej konserwatywny deadline i utrwala oba fixed pola w tej
samej transaction co inventory, health, capabilities oraz oba global revisions.
Exact duration/TTL pozostaje do późniejszego configuration/operation review, ale
nie może oznaczać bezterminowego fresh ani być dopisywana dopiero przez
scheduler. Opóźnienie fetch/reconciliation/DB commit nie może odmłodzić danych.
Odczyt API nie przesuwa deadline; kolejny successful applicable run może
ustanowić nowy anchor i deadline.
Zmiana configured duration jest controlled discovery-relevant configuration
transition zwiększającą `source_config_revision`; nie przelicza wstecz ani nie
wydłuża deadline poprzedniego commitu.

Successful reconciliation sprawdza deadline we własnej atomic commit boundary.
Jeżeli w chwili commitu `current time >= freshness_valid_until`, inventory może
zostać committed jako nowy last-known successful inventory, z odpowiednią zmianą
`inventory_revision`, ale ten sam commit publikuje od razu non-fresh/stale state,
`current_health_origin=time_expiry`, reason
`freshness_deadline_elapsed_before_commit` (albo równoważny jawny reason) oraz
freshness-dependent capabilities `none/ineligible`. Powstaje jeden spójny
published view i jedna odpowiadająca mu zmiana `published_state_revision`; nie ma
przejściowego committed `fresh` ani późniejszej osobnej expiry transaction dla
tego samego już przeterminowanego commitu.

Przekroczenie current deadline jest rzeczywistą controlled state transition:

```text
healthy/fresh
→ stale/non-fresh
current_health_origin = time_expiry
current_health_reason = freshness_deadline_elapsed
mutation freshness = false
freshness-dependent destructive/maintenance capabilities = none/ineligible
inventory_revision unchanged
published_state_revision++
```

Od chwili deadline poprzednia revision może istnieć wyłącznie jako historyczny
committed view z fixed facts; nie jest już dopuszczalnym authoritative current
fresh state. Jeżeli materialized expiry transition nie została jeszcze wykonana,
każda granica publikacji lub użycia musi wykonać ją przed zwróceniem/oceną state.

Transaction nie reconciliuje resources, nie zmienia ich presence/identity ani
retained policy/history. Ponownie wyprowadza effective capabilities i publikuje
je z health zmianą w jednym committed view. Powrót do fresh wymaga nowego
authoritative successful applicable inventory commit z nowym deadline; API read,
timer retry ani cofnięcie zegara nie przywracają freshness.

Expiry jest CAS/fenced exact provenance. W tej samej transaction backend
sprawdza co najmniej expected `last_committed_run_sequence`, expected current
deadline oraz committed/current `source_config_revision`, endpoint, canonical
locator/version i `transport_trust_revision`. Spóźniony timer dla runu N jest
no-op, jeśli run N+1 ustanowił już nowy commit/deadline albo context się zmienił.
Expiry serializuje się z successful/failed finalization i controlled context
transitions.

Timer/expiry worker może zapewniać terminową publikację, ale nie jest correctness
boundary. Przed zwróceniem authoritative published source freshness lub effective
capabilities backend sprawdza deadline; jeśli minął, najpierw commit expiry
transition, a dopiero potem składa consistent published snapshot. Każda przyszła
destructive/maintenance eligibility decision wykonuje ten sam check niezależnie
od wcześniejszego API/HA read i fail closed przed użyciem state. Nie wolno użyć
expired inventory tylko dlatego, że polling albo timer przestał działać. Jeśli
expiry commit nie może zostać wykonany, API nie zwraca state jako authoritative
fresh, a mutation eligibility odmawia operacji.

Wall-clock-derived display age nie jest security authority. Wykryta anomalia
czasu uniemożliwiająca bezpieczną ocenę deadline nie może przedłużyć mutation
freshness: backend przechodzi lub traktuje state jako non-fresh zgodnie z
fail-closed implementation contract. Raz committed expiry nie jest cofane przez
backward clock change.

### `resource_observations`

- primary identity: `observation_id` UUID albo `(run_id, resource_id)` po
  jednoznacznym reconciliation;
- relacje: run, resource, binding i optional current node, gdy relacja jest
  wiarygodnie resolved;
- immutable: normalized facts, status, name, observed config metadata, presence
  input, `observed_at`, per-resource `detail_status` (`ok`,
  `temporarily_unavailable`, `error`) i detail read result;
- constraints: JSON-like schema/version, deep immutable input;
- authoritative: source dla zaobserwowanych facts; nie dla policy;
- retention: pełne recent history plus kompakcja starszych facts; first/last,
  evidence i audit decisions bezterminowo.

`resource_observations.detail_status` opisuje provider read dla locatora obecnego
w current baseline i dlatego używa wyłącznie `ok`, `temporarily_unavailable`
albo `error`. Reconciled/published resource ma rozszerzony zamknięty vocabulary:

```text
presence=present
  → detail_status ∈ {ok, temporarily_unavailable, error}

presence∈{missing, confirmed_removed, not_current}
  → detail_status=not_applicable
```

`not_applicable` oznacza brak current detail read w absence/terminal state, nie
failure ani brak retained last-known facts. Validator odrzuca `not_applicable`
w normalized provider entry obecnym w current baseline oraz odrzuca inną wartość
dla reconciled absent/terminal resource.

### `continuity_evidence`

- primary identity: `evidence_id` UUID;
- relacje: source, run, locator binding oraz resource lub resources, których
  dotyczy evidence; relacja old/successor istnieje dopiero dla accepted direct
  replacement decision;
- immutable: kind, value/hash, provenance, timestamp, confidence class,
  supports/refutes oraz optional covered cursor;
- authoritative: fakt o evidence; ostateczna decision należy do reconciler;
- retention: bezterminowo dla evidence użytego do enrollment, replacement lub
  removal.

`digest`, `vmgenid`, `meta.ctime`, name i fingerprints muszą zachować swój typ;
nie wolno ich promować do immutable identity przez sam fakt zapisania tutaj.

### `resource_terminations` / `resource_tombstones`

- primary identity: `resource_id` starej incarnation;
- relacje: ostatni binding, termination evidence/run, optional successor
  `resource_id`/lineage;
- immutable po utworzeniu: source, slot VMID, occupant type, generation,
  first/last seen, `terminated_at`, `termination_reason`
  (`confirmed_removed`, `replaced` albo przyszły jawnie zaakceptowany terminal
  reason), continuity/evidence digest i provenance;
- authoritative: backendowa pamięć zajęcia i zakończenia slotu;
- retention: bezterminowo w audit history; automatyczny purge nie jest częścią
  projektu.

Terminal history musi odróżniać autorytatywnie usuniętego occupanta pustego slotu
od occupanta pozytywnie zastąpionego przy nadal zajętym slocie. Absence-specific
`removed_at`/proof może istnieć tylko dla `termination_reason=confirmed_removed`;
direct replacement nie zapisuje fałszywego removal. Tombstone uniemożliwia
traktowanie powracającego locatora jako „pierwszego widzenia” bez historii. Nie
rezerwuje VMID w Proxmox i nie nadaje permissions.

`quarantined` resource nie jest zakończony i nie ma terminal/tombstone record
wyłącznie z powodu ambiguity. Zachowuje `resource_id`, active binding, generation
i observation history dla read-only reconciliation. Terminal record powstaje
tylko z accepted `termination_reason`, w szczególności `confirmed_removed` albo
`replaced`.

### `resource_policies`

- primary identity: backendowy policy record/revision identity; foreign
  identity zawsze wskazuje dokładny `resource_id`, nigdy sam locator;
- immutable: attachment do resource ID, enrollment/continuity context, revision
  provenance i audit origin;
- mutable przez nowe revisions: jawne ustawienia operatora; historycznych
  revisions nie nadpisujemy;
- retained state: stored policy i revision history pozostają po `uncertain`,
  revocation trust, replacement, retirement i tombstone transition;
- derived applicability: backend wylicza osobno `active`, `suspended` albo
  `inapplicable` wraz z reason na podstawie current continuity/enrollment,
  exact active `binding_id`, `locator_generation`, current
  `resource_continuity_revision`, lifecycle i operation-specific gates;
- constraints: brak policy dla samego locatora; optimistic revision check;
- constraints bezpieczeństwa: obecność retained policy nie nadaje permission ani
  capability; dla `unverified`/`revoked` effective destructive policy=false,
  maintenance permission=none i effective destructive capabilities=none;
- authoritative: backend/SQLite, nigdy discovery ani HA;
- retention: historia revisions i audit bezterminowo zgodnie z polityką audytu.

Policy applicability wymaga przecięcia:

```text
stored policy allows operation
∩ policy applicability
∩ trusted security continuity
∩ backend capability
∩ exact resource_id/active binding_id/locator_generation/resource_continuity_revision
∩ sufficiently fresh committed inventory under current source/transport contract
∩ operation-specific preconditions
= operation eligible
```

Flagi takie jak `automatic_rollback`, `manual_rollback_allowed` i
`manual_snapshot_restore_allowed` pozostają granularnymi policy gates, ale
żadna flaga sama nie autoryzuje rollback/restore. Po trust loss nie tworzymy
nowych destructive approvals/jobs, a istniejące active destructive operations
są fail-closed blokowane/przerywane według późniejszego audytowanego contract.

Po replacement stary resource zachowuje stored policy/history, ale
`policy_applicability=false`, effective destructive capabilities i maintenance
permission są `none`, a active destructive operations są fail-closed
blokowane/przerywane według późniejszego contract. Successor `resource_id` nie
dziedziczy stored policy, approvals, jobs ani locks i zaczyna jako
`security_continuity=unverified`/`discovered`. Ewentualne przyszłe „copy
settings” musi być osobną, jawną, audytowaną operacją tworzącą nową policy dla
successor resource.

### Przyszłe plans/jobs/locks/audit

Nie są implementowane w tej fazie. Każdy destructive plan/approval/job musi
zapisać expected `resource_id`, active `binding_id`, `locator_generation` i
`resource_continuity_revision`. Executor nie może przyjąć samego VMID. Dla host
routing zapisuje również expected `node_binding_id`, node `binding_revision` i
`attestation_id`. Mismatch któregokolwiek exact tokenu oznacza fail closed, brak
execution oraz konieczność ponownego planowania/autoryzacji.
Nie wolno tworzyć ani pozostawiać wykonywalnego destructive approval/job dla
resource bez `security_continuity=trusted`; utrata trust natychmiast blokuje lub
przerywa execution według przyszłego audytowanego kontraktu. Rekord operacji i
jego wynik pozostają retained dla audytu.

Mutation eligibility wymaga również sufficiently fresh committed inventory pod
bieżącym `source_config_revision`, endpoint/canonicalization contract i
`transport_trust_revision`, przed fixed `freshness_valid_until` oraz bez nowszego
applicable outcome — w tym unavailable, partial/degraded, configuration error
albo invalid current-context run — unieważniającego current-state assumptions.
Backend sprawdza deadline wewnątrz przyszłej mutation eligibility boundary;
jeśli minął, najpierw wykonuje CAS-fenced expiry transition i odmawia użycia
starego state niezależnie od schedulera lub wcześniejszego API read. Zmiana
revision, expiry albo każdy nowszy non-authoritative applicable source outcome
podważający confidence pozostawia stare inventory jako last-known presentation
data, nie mutation-fresh evidence. Exact source freshness duration oraz
dodatkowy operation-specific TTL pozostają przyszłym jawnym, fail-closed
contract; silniejsza niezależna live attestation może być wyjątkiem tylko po
osobnym accepted operation-specific security review.

### Host routing invariant

```text
resource current node fact
∩ trusted node binding revision
∩ valid node/hostd attestation
∩ executor readiness
∩ host policy
= eligible typed host route
```

HA `via_device` korzysta z presentation `node_id`, ale nie uczestniczy w
wyborze route. Backend bezpośrednio przed każdą mutacją ponownie rozwiązuje
resource location i sprawdza exact binding/revision/attestation. Po reinstall
node'a pod tą samą nazwą stary binding jest revoked, nowy zaczyna `unverified`,
a wszystkie zależne destructive capabilities są `none` do jawnej re-attestation.
TLS rotation discovery endpointu ani przyszły, osobno zaakceptowany endpoint
failover nie przywracają hostd trust.

## Autorytatywność danych

| Dane | Source of truth |
| --- | --- |
| observational locator presence (`present`/`missing`) i baseline completeness | boundary-valid discovery run |
| per-resource detail facts/status | konkretna `resource_observation`; błąd nie degraduje baseline |
| raw/normalized Proxmox facts | udany odczyt odpowiedniego baseline/detail scope |
| boundary permission coverage/completeness | zgodne canonical `GET /access/acl` topology snapshots oraz zgodne per-path upstream effective permission results na obu granicach discovery window |
| interval-wide consistency/absence | osobno zaakceptowany proof; **UNKNOWN** dla stockowego polling discovery |
| internal resource/node/source identity | backend + SQLite |
| locator binding/generation | transactional reconciliation |
| discovery run issuance/ordering | `inventory_sources` jako jedyny owner durable atomic `last_issued_run_sequence`, `last_committed_run_sequence` i active-run ownership; per-source single-flight tworzy non-overlapping eligible observation windows, a sequence pozostaje issuance/audit tokenem, nie samodzielnym proof physical observation order |
| run completion i current source health/freshness | one-time-finalized `discovery_runs` plus `source_runtime_health` jako jedyny owner completion/health/reference/deadline provenance; current origin może być applicable run, controlled context transition, time expiry albo initial state |
| API-visible change ordering | globalne `backend_instance.inventory_revision` i `published_state_revision`; każdy published-field commit atomowo zwiększa drugi token, a inventory commit także pierwszy |
| consistent published snapshot | jeden DB read snapshot/transaction wiążący revision i wszystkie publikowane dane; bez torn view między revisions |
| terminal occupancy (`not_current`/`confirmed_removed`) oraz continuity/termination decision | reconciler + odpowiednia klasa trwałego evidence/audit |
| stored policy/revision history i enrollment | backend + SQLite, trwale przypięte do `resource_id` |
| policy applicability/suspended reason | backendowa derivation z current trust, binding, lifecycle i operation gates |
| effective capabilities | backendowa derivation committed razem z odpowiednim inventory/health/expiry state; przed odczytem lub operacją deadline guard wymusza revisioned fail-closed source freshness transition |
| HA device/entity state | prezentacja committed backend snapshotu |

Discovery opisuje rzeczywistość. Policy opisuje pozwolenie. Żadna wartość ze
snapshotu discovery nie awansuje automatycznie resource do `managed`.

`complete` nie może wynikać z samej odpowiedzi `/cluster/resources`, ponieważ
ACL filtering może po cichu pominąć guest. Sam `GET /access/permissions` także
nie dowodzi braku restrictive descendant ACL: effective permission map może nie
zawierać ścieżki, na której `NoAccess` wyzerował inherited privileges.

Boundary consistency musi otoczyć discovery window dwoma rodzajami odczytu:

```text
canonical ACL topology BEFORE
+ per-path effective permissions BEFORE
→ source-wide baseline i required facts
→ canonical ACL topology AFTER
+ per-path effective permissions AFTER
```

`GET /access/acl` enumeruje security-relevant descendant paths wymagające
kontroli. Dla każdego odpowiedniego path backend zleca Proxmox obliczenie
effective permissions przez `GET /access/permissions?path=<path>` albo
równoważny oficjalnie zweryfikowany kontrakt. Hubinet Ops sprawdza wynik względem
wymaganego `VM.Audit`/`Sys.Audit` coverage, ale nie implementuje własnej kopii
semantyki inheritance, deeper-path replacement, user/group precedence, token
privilege separation, `NoAccess` ani propagation. Ewentualny własny recursive
ACL evaluator wymagałby osobnego ADR i dowodu zgodności z upstream.

Obie pary BEFORE/AFTER muszą być identyczne. Odczyt pełnej topologii przez
`GET /access/acl` wymaga `Sys.Audit` na `/access`. Jest to read-only, lecz
zwiększa zakres widocznych metadanych ACL i stanowi jawny security tradeoff
boundary-complete discovery.

Jeżeli pełnej topologii nie można odczytać lub jednoznacznie ocenić, run jest
`partial`/`configuration_error` i nie uruchamia absence/removal transitions.
Per-VM/per-pool visibility nie zastępuje source-wide coverage. Dokładna finalna
endpoint/ACL matrix pozostaje przedmiotem późniejszego implementation/contract
review.

Matching boundary snapshots nie wykluczają zmiany ACL `A → B → A` podczas
pobierania baseline. Potwierdzają stan wyłącznie na próbkowanych granicach:

```text
boundary-consistent snapshot != interval-wide ACL proof
boundary-consistent complete snapshot != authoritative absence proof
```

Monotonic ACL/config revision albo cursor pokrywający cały interval pozostaje
**UNKNOWN**. Boundary-complete snapshot może ustawić widoczny resource na
`present`; brak wcześniej znanego locatora może dać observational `missing` i
`uncertain`. Nie wystarcza do `confirmed_removed`, physical removal,
absence-based security-sensitive closure incarnation ani nadania/przeniesienia
destructive authority. Nie blokuje to osobnej atomic direct-replacement path,
jeżeli istnieje positive evidence innego current occupanta. Polling-only
automatic `confirmed_removed` pozostaje wyłączone do zaakceptowania
authoritative absence proof.

## Terminal history, tombstones i retention

Terminal/tombstone record oraz minimalna historia locator bindings pozostają
bezterminowo,
ponieważ ich rozmiar jest mały, a utrata otwiera ryzyko VMID reuse po długiej
przerwie. Szczegółowe observations można kompaktować według późniejszej policy,
ale trzeba zachować:

- resource/source identity;
- wszystkie generacje locatora;
- first/last seen, `terminated_at`, `termination_reason` oraz optional
  absence-specific `removed_at`;
- evidence i decyzje użyte do continuity/removal/replacement;
- policy/enrollment revisions;
- plan/job/audit references.

Purge source, tombstone albo HA device nie jest automatycznym skutkiem
discovery. Osobny retention/purge design może powstać później, ale nie może
usuwać referencji wymaganych do security/audit.

## Published inventory view

API i HA otrzymują wyłącznie widok po commit:

```text
backend_instance_id
sources[] {
  inventory_source_id,
  health/availability,
  current_health_origin/reason,
  last_issued_run_sequence,
  latest_completed_run_sequence/outcome,
  last_health_run_sequence/last run health outcome,
  last_committed_run_sequence,
  last_successful_observed_at,
  freshness_reference_at,
  freshness_valid_until,
  current source_config_revision/transport trust context,
  committed inventory source_config_revision/endpoint/canonicalization/transport trust context
}
nodes[] {node_id, inventory_source_id, facts, availability}
resources[] {
  resource_id,
  inventory_source_id,
  resource_type,
  vmid,
  active_binding_id (nullable dla terminal resource),
  locator_generation,
  resource_continuity_revision,
  current_node_id | last_known_node_id,
  display_name,
  presence,
  lifecycle,
  detail_status,
  node_availability,
  observational_continuity,
  security_continuity,
  termination_reason (optional),
  successor_resource_id (optional),
  enrollment/state level,
  retained_policy/history (optional),
  policy_applicability,
  effective_policy,
  suspended_reason,
  read-only facts,
  effective capabilities
}
inventory_revision
published_state_revision
published_at
```

Source health/freshness jest publikowane niezależnie od resource presence.
Osiągalny Hubinet backend może więc jawnie pokazać świeży inventory albo stale,
`source_unavailable`, degraded/partial czy `configuration_error` Proxmox source.
Applicable invalid source run również może oznaczać non-fresh/degraded state.
Failed/partial/unavailable/invalid source run nie zmienia retained `resources[]` na
`missing` i nie usuwa devices; last-known facts mogą pozostać widoczne jako
stale/historyczne, a encje wymagające current facts stają się unavailable albo
jawnie stale według source-health overlay.

`last_successful_observed_at`, `freshness_reference_at`,
`freshness_valid_until`, committed health/origin/reason i `published_at` są fixed
facts revisioned view. Canonical backend snapshot nie zawiera wall-clock-mutating
`inventory_freshness/age`. HA/UI może wyliczyć
display-only age jako `now - last_successful_observed_at`, ale wynik nie należy do
equality/immutability contract `published_state_revision=N`, nie jest backendowym
source of truth i nigdy nie uczestniczy w capability ani mutation decision.

`inventory_revision` zmienia się przy committed zmianie inventory. Niezależny,
monotoniczny `published_state_revision` zmienia się przy **każdej** API-visible
committed transition i zmianie dowolnego publikowanego pola. Obejmuje to m.in.
completion/health sequence i outcomes, last-success timestamp, health
origin/reason, fixed freshness reference/deadline, current/committed source context,
initial/context/time-expiry transition, inventory/resource/node/policy oraz
derived effective capabilities. Health-only
CAS update nie wymaga nowego `inventory_revision`, lecz musi atomowo zwiększyć
`published_state_revision` także wtedy, gdy health enum pozostaje taki sam — np.
`seq11 source_unavailable → seq12 source_unavailable` zmienia publikowane
provenance. Old-context finalized run podnoszący publikowane
`latest_completed_run_sequence/outcome` również zwiększa
`published_state_revision`, mimo że current health się nie zmienia.

`inventory_revision` i `published_state_revision` są durable, atomic, strictly
increasing i never reused. Ich przydział jest globalnie serializowany; dwa
równoległe commity sources A/B nie mogą otrzymać tego samego resulting
`published_state_revision`. Każda transaction zmieniająca published view
zwiększa globalny token dokładnie w tej samej transaction co dane, które
publikuje. Dzięki temu HA, cache i push-refresh consumer nie pomijają
`healthy → source_unavailable/stale`, także gdy źródłem zmiany jest wyłącznie
upływ fixed deadline. Globalny `published_at` ani globalny
observation timestamp nie zastępuje per-source `last_successful_observed_at`,
run sequence ani committed context provenance.
Oba globalne tokeny mają jednego canonical durable ownera w
`backend_instance`; source i health records nie przechowują ich niezależnych
authoritative kopii.

`published_state_revision=N` identyfikuje jeden logicznie spójny committed
backend view. API składa snapshot w consistent DB read transaction/snapshot
albo równoważnej granicy: revision i wszystkie `sources[]`, `nodes[]`,
`resources[]`, policy oraz derived capabilities muszą należeć do tego samego
committed stanu. Torn view — odczyt revision N, następnie części danych sprzed i
części po concurrent commit N+1, zwrócony jako N — jest zabroniony. Consumer
otrzymuje kompletne N albo kompletne N+1; nie projektuje to HTTP caching.

```text
source unavailable != resource missing
Hubinet backend reachable != Proxmox inventory fresh
```

`resources[]` jest identity-keyed przez `resource_id`; VMID nie jest unique key
tej kolekcji. Po direct replacement albo po
`confirmed_removed → późniejszy new occupant` published/history view może
zawierać kilka rekordów z tym samym `(inventory_source_id, vmid)`, ale różnymi
`resource_id`, `locator_generation` i terminal/current state. Na przykład:

```text
resource_id=A, vmid=101, locator_generation=4,
presence=not_current, lifecycle=retired

resource_id=B, vmid=101, locator_generation=5,
presence=present, lifecycle=active
```

Invariant „najwyżej jeden active locator binding/current incumbent na
`(inventory_source_id, vmid)`” nie oznacza „najwyżej jeden retained resource
record z tym VMID”. API, Coordinator i backend nie mogą używać
`resources_by_vmid[vmid] = resource` jako identity map. Current occupant jest
rozwiązywany wyłącznie przez active locator binding/backend relation. Wymagane są
API/HA/Device Registry contract tests dla old i successor o tym samym VMID.

API może pokazać retained policy/history, ale osobno publikuje derived
applicability/effective policy, suspended reason i capabilities; normalized
discovery snapshot nie zawiera żadnej z tych wartości. HA nie wylicza
applicability z istnienia policy record.

Docelowa relacja node jest zgodna z [ADR 0002](adr/0002-proxmox-discovery-reconciliation.md#node-relation-i-ha-availability):
`present` może mieć znany `current_node_id` przy node `available` albo
`unavailable`, a przy nierozstrzygniętej current relation ma
`current_node_id=null` i opcjonalny `last_known_node_id`. Detail failure nie
zmienia presence. `missing`/`confirmed_removed` oraz terminalne `not_current` po
direct replacement nie mają current node i zachowują last-known presentation
relation, jeśli była znana. `not_current` nie twierdzi, że slot jest absent:
successor jest osobnym `resource_id` z `presence=present` i własną current node
relation. `last_known_node_id` nigdy nie jest mutation route.

Każde non-null `current_node_id` lub `last_known_node_id` wskazuje node record
obecny w tym samym published snapshot. Phase 1 nie purguje node recordu, dopóki
referuje go jakikolwiek published current albo last-known resource; offline lub
history node może pozostać retained. Validator odrzuca dangling node/
`via_device` relation. Future node purge wymaga osobnego atomowego
reference/HA-lifecycle contract.

## HA Device Registry

Rekomendowane identyfikatory są opaque i wersjonowane w serializacji:

```text
backend device: backend_instance_id
source device:  backend_instance_id + inventory_source_id
node device:    backend_instance_id + node_id
resource:       backend_instance_id + resource_id
entity:         backend_instance_id + resource_id + entity_description_key
```

HA Coordinator success oznacza tylko, że Hubinet backend odpowiedział. Source
device/entity publikuje osobno health, `last_successful_observed_at`,
`freshness_reference_at` i fixed `freshness_valid_until`; opcjonalny display age
wylicza lokalnie i nie
traktuje go jako canonical/security state. Przy
stale/degraded/unavailable/time-expired source integracja zachowuje
Device Registry entries oraz last-known state z jawnym stale/history markerem;
encje wymagające current facts są unavailable. Nie generuje to resource
`missing`, nie zmienia identity i nie uruchamia purge.

`via_device_id` resource wskazuje Device Registry ID current node'a, gdy relacja
jest resolved. Po migracji relacja się zmienia bez zmiany resource/entity unique
ID. Przy znanym, lecz niedostępnym node pozostaje przy current node. Przy
nierozstrzygniętej relacji, `missing`, `confirmed_removed` i terminalnego
`not_current` integracja zachowuje last-known presentation relation, dopóki
backend nie poda lepszego committed faktu. Nie ma to znaczenia dla host routing.

Rename aktualizuje display name. `confirmed_removed` oznacza unavailable, nie
delete z registry. Przy direct replacement stara incarnation przechodzi do
terminalnego `not_current`/`replaced`/`retired`; jej HA device/entities i
last-known relation pozostają w historii jako unavailable bez automatic purge.
Successor dostaje nowe `resource_id`, HA device/entity identity i current
presentation state, bez kopiowania starej identity. Niewidoczne replacement
pomiędzy pollingami może zachować read-only HA identity, ale nigdy destructive
authority.

Po observable gap z ambiguous continuity bez accepted terminal proof istniejące
HA device/entity identity pozostają. Resource może ponownie prezentować read-only
facts jako `presence=present`, lecz pozostaje `uncertain`/`quarantined`, a backend
publikuje brak effective destructive policy/capabilities. Nie powstaje drugi
active/provisional HA device ani automatyczny tombstone.

## Warunki wejścia do implementacji Phase 1

Przed implementacją obowiązują następujące bramki:

1. ADR 0001 i ADR 0002 pozostają `ACCEPTED` jako normatywny kontrakt
   architektury;
2. cały Phase 0 contract zostaje zmieniony zgodnie z `PHASE 0 AMENDMENT
   REQUIRED`: identity, osobne osie locator presence/detail status/node
   availability, semantyka current/last-known node, Coordinator/entity
   availability oraz snapshot/Device Registry validators i tests;
3. endpoint/ACL matrix, w tym delegowanie per-path effective permission
   evaluation do Proxmox, oraz supported PVE versions są jawne;
4. transaction invariants i schema zostają przełożone na testowalny kontrakt,
   który z góry klasyfikuje baseline prerequisites i dowodzi, że per-resource
   detail failure nie degraduje `baseline_completeness`;
5. atomowe initial source creation ustanawia dokładnie jeden initial active
   endpoint, initial non-fresh `source_runtime_health` i globalną published
   revision; dla existing source URL/relation endpoint record są immutable, a
   replacement, candidate/inactive activation i automatic failover pozostają
   wyłączone do accepted source-binding contract;
6. jedna deterministic/versioned endpoint canonicalization function oraz jej
   positive/negative contract tests zamykają textual alias/history bypasses;
7. controlled `transport_trust_revision` wiąże każdy discovery run, a zmiana
   revision w locie uniemożliwia commit snapshotu starego trust contract;
8. monotonic `source_config_revision` i transaction/CAS tests dowodzą, że każda
   discovery-relevant source mutation serializuje się z reconciliation commit;
9. lifecycle `canonicalization_contract_version`, controlled namespace
   migration oraz negative alias/collision tests zapobiegają obejściu retained
   history po upgrade;
10. atomic direct-replacement contract i tests weryfikują positive replacement
    evidence dla dowolnego eligible nonterminal old resource, exact old
    `binding_id`, generation i `resource_continuity_revision`, zamknięcie
    `replaced`, nową generation oraz brak dwóch active bindings bez wymagania
    pustego slotu; ambiguity/gap/ACL-only missing tests zachowują istniejący
    ID/binding/generation w quarantine i dowodzą, że nowa current identity
    powstaje tylko po direct replacement albo powrocie po `confirmed_removed`;
11. per-source single-flight contract i concurrency tests dowodzą, że issuance
    atomowo ustanawia jednego `active_discovery_run_id`, drugi trigger nie
    rozpoczyna provider I/O, terminal finalization zwalnia exact ownership, a
    controlled abandon/fence oraz restart recovery blokują late worker; durable
    `last_issued_run_sequence` pozostaje unique, strictly-increasing i
    never-reused, lecz sam nie jest proof physical observation ordering;
12. normalized snapshot negative tests odrzucają wrong source, unsupported type,
    duplicate locator (w tym LXC/QEMU dla jednego VMID) i duplicate external node
    name bez reconciliation/publish;
13. published API/Coordinator/Device Registry tests traktują `resource_id` jako
    identity key, poprawnie utrzymują old i successor z tym samym VMID, rozwiązują
    current occupant przez active binding i zabraniają dangling node references;
14. detail validators rozróżniają provider status dla present locatora od
    reconciled `not_applicable` dla `missing`/`confirmed_removed`/`not_current`;
15. durable source health/freshness i CAS/fencing tests dowodzą, że failed active
    owner w jednej transaction finalizuje audit, ponownie sprawdza exact current
    context, aktualizuje completion/health/freshness provenance i published
    revision bez resource reconciliation oraz zwalnia ownership; late albo
    old-context worker nie przywraca fresh health ani nie publikuje inventory;
    successful commit utrwala fixed observation-derived reference/deadline
    provenance, expiry bez
    nowego runu atomowo ustawia stale i odbiera freshness-dependent capabilities
    bez zmiany inventory revision/identity/presence, a stale timer starszego
    commitu jest CAS-no-op;
16. run lifecycle tests dowodzą, że issuance nie wymaga completion fields,
    successful i failed completion finalizują record dokładnie raz, conflicting
    second finalization jest odrzucane, a crash po issuance pozostawia incomplete
    record, zużyty sequence i durable ownership wymagający controlled recovery;
    successful finalization, reconciliation, commit/health provenance, release
    ownership i oba global revisions są atomowym all-or-nothing commitem;
17. ownership/health tests dowodzą, że source config lub transport context
    transition serializuje się z issuance/finalization, czeka na active run albo
    atomowo go fences przed issue runu nowego contextu, oznacza current state jako
    stale z origin `controlled_context_transition` bez fake observation data,
    applicable invalid outcome odbiera mutation freshness, a initial source
    atomowo tworzy non-fresh health record i published revision;
18. publication tests dowodzą, że każda zmiana publikowanego pola — także ten
    sam health enum z nowszym run provenance albo old-context completion audit —
    zwiększa unique global `published_state_revision`; concurrent source commits
    nie współdzielą resulting revision; canonical snapshot publikuje fixed
    timestamps/deadline, nie dynamiczny age, a dwa odczyty tej samej revision
    zwracają identyczne fixed freshness facts;
19. consistent-read tests wymuszają `revision N + complete view N` albo
    `revision N+1 + complete view N+1` i odrzucają torn API snapshot z danymi
    należącymi do różnych committed revisions; API read oraz bezpośredni future
    mutation eligibility check niezależnie wymuszają expiry przed użyciem
    authoritative freshness nawet przy zatrzymanym pollerze/timerze, a nowy
    successful applicable run może przywrócić fresh tylko z nowym deadline i
    published revision.

Freshness contract tests obejmują dodatkowo: observation w `T0` i opóźniony
commit bez przesunięcia deadline z `T0`; deadline już miniony przed successful
reconciliation commit, który zapisuje last-known inventory od razu jako
non-fresh bez transient `fresh`; normalny szybki run publikujący fresh do fixed
deadline; oraz kolejny successful run ustanawiający nowy observation-derived
anchor i deadline.

Do tego czasu nie powstają produkcyjne discovery, tabele, endpointy, credentials,
policy mutations ani lifecycle/snapshot/update/maintenance.

Po spełnieniu wszystkich obowiązkowych warunków wymienionych powyżej read-only
discovery/inventory może być implementowane niezależnie od trzech dalszych
gates:

- brak zaakceptowanego authoritative interval-wide absence proof blokuje
  `confirmed_removed`, absence-based closure incarnation i automatyczne removal
  transitions; nie blokuje `present`, observational `missing` ani direct
  replacement opartego na osobnym positive replacement evidence;
- brak zaakceptowanego workload continuity proof/enrollment model blokuje
  globalnie `trusted` destructive capabilities i każdą zależną mutację;
- brak zaakceptowanego source-binding/attestation contract blokuje zmianę active
  transport targetu, replacement active endpointu, aktywację candidate/inactive
  endpointów i multi-endpoint automatic failover.

Żaden z tych trzech braków nie blokuje podstawowego read-only inventory przy
jednym active endpoint. Odpowiednie capabilities/features pozostają wyłączone
fail-closed.

## Sources / Evidence

Semantyka pól Proxmox oraz ACL jest udokumentowana wraz ze źródłami w ADR 0001
i ADR 0002. Ten dokument jest architektoniczną inferencją i zaakceptowanym
backendowym modelem; nie przedstawia backendowych UUID, tombstones ani
continuity states jako funkcji dostarczanych przez Proxmox.
