# Hubinet Ops 0.5 — konceptualny inventory model

Status: **PROPOSED**

Ten dokument materializuje proponowane decyzje z:

- [ADR 0001: identity zasobu i incarnation](adr/0001-resource-identity-incarnation.md);
- [ADR 0002: read-only discovery i reconciliation](adr/0002-proxmox-discovery-reconciliation.md).

Nie jest schema SQL, migracją ani kontraktem endpointu. Hubinet Ops 0.5 tworzy
nową bazę od zera i nie importuje SQLite 0.4.

## Identities i relacje

```text
backend_instance
  └─ inventory_sources
       ├─ source_endpoints
       ├─ nodes
       │    ├─ node_bindings
       │    └─ node_attestations
       ├─ discovery_runs
       └─ resource_incarnations
            ├─ resource_locator_bindings
            ├─ resource_observations
            ├─ continuity_evidence
            ├─ resource_tombstone (optional 1:1)
            └─ resource_policies + policy revisions (optional, retained)
```

## Encje

### `backend_instance`

- primary identity: losowy `backend_instance_id` UUID;
- immutable: ID, `created_at`;
- mutable: schema/application metadata;
- authoritative: tożsamość instalacji Hubinet Ops;
- retention: cały czas życia nowej bazy;
- constraint: dokładnie jeden aktywny record w jednej bazie.

URL/IP nie jest identity. Clean reinstall bez przywrócenia tej samej bazy tworzy
nową instalację i nowe ID.

### `inventory_sources`

- primary identity: backendowy `inventory_source_id` UUID;
- relacja: należy do `backend_instance_id`;
- immutable: ID, provider kind, `created_at`;
- mutable presentation/observed: display name oraz cluster/standalone facts;
- controlled mutable source configuration: lifecycle/configuration state
  istotny dla discovery, provider/discovery settings, credential/secret
  reference, active discovery-route lifecycle oraz wymagane provider contract
  parameters;
- monotonic concurrency contract: `source_config_revision`, inkrementowany
  atomowo przy każdej zmianie controlled source configuration wpływającej na
  znaczenie lub dopuszczalność discovery runu; revision nigdy nie jest source
  identity i nie jest cofany ani ponownie używany;
- constraints: source ID unikalny w backendzie; nazwa klastra nie jest unique
  identity;
- authoritative: operatorowa definicja granicy jednego Proxmox environment;
- retention: trwała; po usunięciu source pozostaje historyczny record.

Credentials są przechowywane poza observation/audit payloads. Record zawiera
secret reference, nie jawny token. Rotacja credential material/version — także
pod tym samym secret reference — zmiana samego reference, provider/discovery
settings, discovery-relevant lifecycle/configuration state albo wymaganych
contract parameters zwiększa `source_config_revision`. To samo dotyczy
controlled transition lub canonicalization migration zmieniającej active
discovery route. Zmiana wyłącznie display label, inert candidate metadata albo
zapis nowych observed facts nie zwiększa revision, ponieważ nie zmienia
interpretacji bieżącego runu.

Source configuration mutation i reconciliation commit muszą serializować się w
jednej backendowej concurrency boundary. Run zapisuje expected revision pobrany
przed fetch. Commit jest dozwolony wyłącznie, gdy bieżąca wartość nadal jest
równa expected; mismatch oznacza invalid/stale run, bez reconciliation i bez
publikacji snapshotu. Oddzielne exact checks endpointu, canonical locatora,
canonicalization version i TLS trust revision pozostają obowiązkowe.

### `source_endpoints`

- primary identity: `endpoint_id` UUID;
- relacja: wiele endpointów do jednego source;
- immutable w zwykłym lifecycle: ID, `inventory_source_id`, stored canonical
  HTTPS URL/transport locator i `canonicalization_contract_version`, która go
  wytworzyła; initial pair pozostaje w creation provenance/audit, a każda
  controlled migration dopisuje immutable old/new provenance;
- mutable operational: health/availability i non-identity metadata;
- controlled mutable: lifecycle status (`active`, `candidate`, `inactive`,
  `retired`) oraz TLS policy/fingerprint metadata wraz z monotonic
  `transport_trust_revision`, wyłącznie przez audytowane state transitions;
  nadanie `active` nie jest direct field assignment;
- constraints:
  - dokładnie jeden endpoint ma status `active` dla aktywnego source;
  - candidate/inactive endpoints nie uczestniczą w discovery, retry ani
    automatic failover;
  - operatorowa zmiana URL nie może zmodyfikować istniejącego record; nowy URL
    tworzy nowe `endpoint_id` jako `candidate`; jedynym wyjątkiem zmiany stored
    canonical pair jest controlled version migration opisana niżej;
  - `(inventory_source_id, canonical_transport_locator)` jest unikalne w
    retained endpoint history; retire/recreate tego samego URL używa historii
    istniejącego record, a reactivation nadal podlega source-binding gate;
    `canonicalization_contract_version` nie tworzy alternatywnego namespace dla
    tego constraint;
  - endpoint record nigdy nie zmienia `inventory_source_id`;
  - direct candidate/inactive → active, direct active replacement oraz
    delete/recreate-as-active wymagają accepted source-binding procedure;
  - historyczny active endpoint i jego relation/provenance nie są hard-deleted,
    więc recreation nie zeruje gate;
  - retire active endpointu wyłącza discovery source i nie pozwala bezpośrednio
    wskazać zastępstwa;
  - disable/re-enable source nie przywraca initial-creation exception;
- authoritative: operatorowa konfiguracja transportu, nie identity source;
- retention: historyczne bindings zachowane w audit.

Canonical transport locator powstaje przed zapisem przez jedną
deterministyczną, wersjonowaną canonicalization function. Raw user URL nie jest
kluczem equality ani history lookup. Contract normalizuje HTTPS scheme, casing
DNS, canonical IPv6/brackets, brak portu względem jawnego `:443`, non-default
port, root/trailing slash; fail-closed odrzuca userinfo, query, fragment oraz
ambiguous/invalid URL. Brak portu nie oznacza automatycznie PVE `:8006`; direct
PVE wymaga jawnego portu. Reverse-proxy subpaths nie są wspierane bez późniejszego
contract/evidence.

Dwa teksty URL dające ten sam canonical locator wskazują tę samą retained
endpoint history i nie mogą utworzyć niezależnych identities. Reactivation albo
alias istniejącego locatora nadal podlega source-binding gate. Implementacja
wymaga wersjonowanych positive/negative canonicalization contract tests.
Przykładowo `https://PVE.EXAMPLE/` i `https://pve.example:443` są jednym
locatorem, lecz `https://pve.example:8006/` jest odrębnym non-default locatorem.

### Lifecycle wersji canonicalization

Stored pair `(canonical_transport_locator,
canonicalization_contract_version)` nie jest po cichu reinterpretowana po
upgrade backendu. Zmiana algorytmu/version wymaga explicit, audytowanej
schema/data migration albo równoważnej controlled migration procedure. Tylko ta
procedura może atomowo zastąpić stored canonical pair, zachowując immutable
historię wartości przed/po; nie jest to zwykła mutacja endpointu.

Migration musi:

- zachować `endpoint_id` i immutable relation do `inventory_source_id`;
- zachować pełne source-binding, activation i retained-history gates;
- deterministycznie przeliczyć cały retained endpoint namespace, nie tylko
  active records;
- wykryć textual aliases i collisions między wszystkimi retained endpointami;
- fail-closed zatrzymać migration przy ambiguity/collision, bez automatycznego
  merge historii, stworzenia drugiej endpoint identity albo nadania `active`;
- zachować audyt starej i nowej canonical pair oraz migration provenance.

Canonicalization version nie tworzy osobnego uniqueness namespace. Nowy raw URL
po upgrade nie może ominąć retained-history/source-binding gate przez zapis pod
nowszą wersją. Przed endpoint create/reactivation backend musi mieć zakończoną i
jednoznaczną migration retained namespace albo równoważny, jawnie zaakceptowany
cross-version lookup contract. Przy braku możliwości honorowania starej wersji
lub kolizji operacja jest `configuration_error`/blocked; nie powstaje nowy
record. Implementacja wymaga positive/negative contract tests dla version
upgrade, cross-version alias i collision.

Nieudana migration jest atomowa: pozostawia stare canonical pairs i wersje bez
zmian. Discovery istniejącego endpointu może być kontynuowane tylko wtedy, gdy
backend nadal potrafi wykonać i zweryfikować zapisany stary contract; w
przeciwnym razie source ma `configuration_error`. Create/reactivation pod nowym
contractem pozostaje zablokowane do jednoznacznego resolution.

Atomowe initial source creation może utworzyć nowy `inventory_source_id` i
dokładnie jeden initial active endpoint. Po commit tej transaction source jest
existing; każda późniejsza zmiana transport targetu tworzy inert candidate.
Niedostępność active endpointu daje `source_unavailable`; backend nie próbuje
candidate endpointu.

Aktywacja candidate, replacement active endpointu albo multi-endpoint failover
wymaga późniejszego zaakceptowanego source-binding/attestation contract. Dopóki
go nie ma, operator potrzebujący innego endpointu tworzy nowy
`inventory_source_id`. Cluster name, node membership, VMIDs, hostname, IP, DNS,
TLS certificate/fingerprint i URL nie wystarczają samodzielnie do związania
endpointu z istniejącym source.

Stable URL nie jest proof physical source continuity: DNS/reverse-proxy change
lub rebuild może skierować ten sam locator do innego environment. To świadoma
observational limitation read-only Phase 1, nigdy podstawa destructive trust.
Security-sensitive TLS configuration ma monotonic
`transport_trust_revision` albo równoważną wersję contractu. Każda zmiana jest
explicit, audytowana i kontrolowana; discovery run wiąże exact `endpoint_id`,
canonical locator i expected trust revision. Zmiana revision w trakcie runu
unieważnia commit wyniku pod poprzednim contractem. Broadening/replacement CA
roots, pin/fingerprint albo verification policy wymaga revalidation i nie nadaje
source identity ani nie omija activation gate. Normalne CA-valid certificate
renewal przy niezmienionej configured trust policy jest peer-observation change;
rotation exact pin jest security-sensitive transition. TLS trust revision nigdy
nie jest source-binding proof, a pełny rotation/attestation protocol pozostaje do
security review.

### `nodes`

- primary identity: backendowy `node_id` UUID;
- relacja: należy do source;
- immutable: ID, source, first seen;
- mutable: display name, presentation presence i `last_seen`; external node name
  należy do wersjonowanego `node_binding`, nie jest swobodnie nadpisywanym polem;
- constraints: security routing nigdy nie używa samego `node_id` ani nazwy;
- authoritative: backend dla internal identity; discovery dla current facts;
- retention: historyczna identity nie jest natychmiast usuwana.

Node name i Corosync nodeid są evidence/locator facts. Bez oficjalnej globalnej
immutable gwarancji nie zastępują backendowego `node_id`.

`node_id` może zachować HA presentation continuity po operatorowym potwierdzeniu,
ale samo zachowanie `node_id` nie zachowuje mutation trust.

### `node_bindings`

- primary identity: `node_binding_id` UUID;
- relacja: należy do `node_id` i `inventory_source_id`;
- immutable: external node name, binding generation, `valid_from`, enrollment
  provenance;
- mutable: `valid_to`, trust state (`unverified`, `trusted`, `revoked`) i
  monotonic `binding_revision`;
- constraints:
  - co najwyżej jeden aktywny binding dla `(inventory_source_id,
    external_node_name)`;
  - co najwyżej jeden aktywny trusted binding dla `node_id`;
  - każda zmiana security-relevant evidence zwiększa revision albo zamyka
    binding;
- authoritative: backendowa decyzja, który obserwowany host może być mutation
  target;
- retention: historia bindingów bezterminowo.

Binding jest minimalnym odpowiednikiem node incarnation dla granicy wykonawczej,
bez przesądzania, że presentation `node_id` zawsze musi zmieniać się przy
reinstall. Nowy host używający starej nazwy nigdy nie przejmuje active trusted
binding automatycznie.

### `node_attestations`

- primary identity: `attestation_id` UUID;
- relacja: należy do dokładnego `node_binding_id` i revision;
- immutable: typ evidence, fingerprint/public-key identity lub inny później
  zaakceptowany proof, provenance, `verified_at`;
- mutable: validity/revocation metadata;
- authoritative: backend dla statusu trust; zewnętrzne certificates/keys są
  evidence, nie backendową identity;
- retention: bezterminowo dla każdego bindingu użytego do mutacji.

Konkretny attestation protocol pozostaje unresolved. Certyfikat TLS endpointu
discovery, PVE node certificate, SSH host key i hostd identity nie mogą być
zamiennie traktowane jako ten sam proof.

### `resource_incarnations`

- primary identity: `resource_id` UUID — trwała backendowa inventory/candidate
  identity; dla `unverified` nie jest proof fizycznej incarnation;
- relacja: należy do source;
- immutable: ID, source, `resource_type`, `first_seen`;
- mutable: lifecycle (`active`, `quarantined`, `retired`), observational
  continuity (`consistent`, `uncertain`, `replaced`), security continuity
  (`unverified`, `trusted`, `revoked`), current presence, `last_seen`, enrollment
  state/revision;
- constraints: resource ID nie jest wyliczany z VMID/nazwy/node'a;
- authoritative: backendowa identity inventory/candidate record; physical
  incarnation dopiero po zaakceptowanym security continuity proof;
- retention: bezterminowa w audit/history.

Nie wprowadzamy osobnego „logical service ID” w tej fazie. Jeśli przyszły
product model będzie łączył kolejne incarnations tej samej usługi, lineage jest
osobną, operatorową relacją i nie może przenosić destructive policy.

Zgodne kompletne polling observations mogą zachować `resource_id` resource'u
`unverified` dla UX/HA. Niewidoczny delete/recreate może być nierozróżnialny i
również zachować tę read-only identity. Dlatego `resource_id` bez
`security_continuity=trusted` nigdy nie autoryzuje mutacji.

### `resource_locator_bindings`

- primary identity: `binding_id` UUID;
- relacja: jedna incarnation ma co najmniej jeden historyczny binding;
- slot locator: `(inventory_source_id, vmid)`;
- immutable: binding ID, locator, `locator_generation`, `valid_from`;
- mutable: `valid_to`, closure reason, expected continuity revision;
- constraints:
  - jeden aktywny binding na `(inventory_source_id, vmid)`, niezależnie od
    `resource_type`;
  - jeden aktywny primary binding na resource;
  - unique `(inventory_source_id, vmid, locator_generation)`;
- authoritative: backendowy wynik reconciliation;
- retention: bezterminowa historia slotu.

`locator_generation` rośnie przy nowym bindingu po replacement, confirmed removal
albo nierozstrzygniętej luce. Nie jest identity i nie jest dowodem replacement.
`resource_type` pozostaje immutable w `resource_incarnations` i opisuje occupant
slotu. Schema zabrania jednoczesnego aktywnego LXC101 i QEMU101 w jednym source.

### `discovery_runs`

- primary identity: `run_id` UUID;
- relacja: należy do source;
- immutable: start/finish/observed timestamps, expected i commit-observed
  `source_config_revision`, exact `endpoint_id`, canonical transport locator,
  `canonicalization_contract_version`, expected/observed
  `transport_trust_revision`, fetch outcome,
  `baseline_completeness`, covered/failed baseline scopes, snapshot hash,
  optional provider cursor range, canonical ACL topology snapshot/hash BEFORE i
  AFTER, effective per-path permission snapshot/hash BEFORE i AFTER, derived
  permission coverage, boundary consistency, optional interval-wide evidence
  reference, `detail_error_count`, failed detail scopes oraz redacted errors;
- constraints: committed order monotoniczny per source;
- authoritative: audit tego, co provider faktycznie odczytał;
- retention: długoterminowa; payload może podlegać bezpiecznej kompakcji, ale
  decyzje continuity/removal muszą zachować provenance.

`baseline_completeness` opisuje wyłącznie source-wide locator enumeration i jej
wymagane prerequisites. `detail_error_count` oraz failed detail scopes są
osobną osią diagnostyczną. Błąd detail jednego resource nie może zmienić
`baseline_completeness=complete` na `partial`.

Mismatch `source_config_revision`, endpoint/canonicalization provenance albo
transport trust revision klasyfikuje run jako invalid/stale i uniemożliwia
reconciliation/published snapshot commit. Redacted audit failed run może zostać
zapisany osobno; nie staje się committed inventory observation.

### `resource_observations`

- primary identity: `observation_id` UUID albo `(run_id, resource_id)` po
  jednoznacznym reconciliation;
- relacje: run, resource, binding i optional current node, gdy relacja jest
  wiarygodnie resolved;
- immutable: normalized facts, status, name, observed config metadata, presence
  input, `observed_at`, per-resource `detail_status` (`ok`,
  `temporarily_unavailable`, `error`) i detail read result;
- constraints: JSON-like schema/version, deep immutable input;
- authoritative: source dla zaobserwowanych facts; nie dla policy;
- retention: pełne recent history plus kompakcja starszych facts; first/last,
  evidence i audit decisions bezterminowo.

### `continuity_evidence`

- primary identity: `evidence_id` UUID;
- relacje: source, run, locator binding, old/new candidate resource;
- immutable: kind, value/hash, provenance, timestamp, confidence class,
  supports/refutes oraz optional covered cursor;
- authoritative: fakt o evidence; ostateczna decision należy do reconciler;
- retention: bezterminowo dla evidence użytego do enrollment, replacement lub
  removal.

`digest`, `vmgenid`, `meta.ctime`, name i fingerprints muszą zachować swój typ;
nie wolno ich promować do immutable identity przez sam fakt zapisania tutaj.

### `resource_tombstones`

- primary identity: `resource_id` starej incarnation;
- relacje: ostatni binding, removal evidence/run, optional successor lineage;
- immutable po utworzeniu: source, slot VMID, occupant type, generation,
  first/last seen, `removed_at`, reason, continuity/evidence digest;
- authoritative: backendowa pamięć zajęcia i zakończenia slotu;
- retention: bezterminowo w audit history; automatyczny purge nie jest częścią
  projektu.

Tombstone uniemożliwia traktowanie powracającego locatora jako „pierwszego
widzenia” bez historii. Nie rezerwuje VMID w Proxmox i nie nadaje permissions.

### `resource_policies`

- primary identity: backendowy policy record/revision identity; foreign
  identity zawsze wskazuje dokładny `resource_id`, nigdy sam locator;
- immutable: attachment do resource ID, enrollment/continuity context, revision
  provenance i audit origin;
- mutable przez nowe revisions: jawne ustawienia operatora; historycznych
  revisions nie nadpisujemy;
- retained state: stored policy i revision history pozostają po `uncertain`,
  revocation trust, replacement, retirement i tombstone transition;
- derived applicability: backend wylicza osobno `active`, `suspended` albo
  `inapplicable` wraz z reason na podstawie current continuity/enrollment,
  expected resource/binding revision, lifecycle i operation-specific gates;
- constraints: brak policy dla samego locatora; optimistic revision check;
- constraints bezpieczeństwa: obecność retained policy nie nadaje permission ani
  capability; dla `unverified`/`revoked` effective destructive policy=false,
  maintenance permission=none i effective destructive capabilities=none;
- authoritative: backend/SQLite, nigdy discovery ani HA;
- retention: historia revisions i audit bezterminowo zgodnie z polityką audytu.

Policy applicability wymaga przecięcia:

```text
stored policy allows operation
∩ policy applicability
∩ trusted security continuity
∩ backend capability
∩ exact resource/binding/revision
∩ operation-specific preconditions
= operation eligible
```

Flagi takie jak `automatic_rollback`, `manual_rollback_allowed` i
`manual_snapshot_restore_allowed` pozostają granularnymi policy gates, ale
żadna flaga sama nie autoryzuje rollback/restore. Po trust loss nie tworzymy
nowych destructive approvals/jobs, a istniejące active destructive operations
są fail-closed blokowane/przerywane według późniejszego audytowanego contract.

Po replacement successor `resource_id` nie dziedziczy stored policy, approvals
ani jobs. Ewentualne przyszłe „copy settings” musi być osobną, jawną, audytowaną
operacją tworzącą nową policy dla successor resource.

### Przyszłe plans/jobs/locks/audit

Nie są implementowane w tej fazie. Ich kontrakt musi używać `resource_id` oraz
zapisywać snapshot oczekiwanego locator binding i continuity revision. Executor
nie może przyjąć samego VMID. Dla host routing zapisuje również expected
`node_binding_id`, node `binding_revision` i `attestation_id`. Po zmianie
któregokolwiek binding/revision job fail-closed i wymaga ponownej autoryzacji.
Nie wolno tworzyć ani pozostawiać wykonywalnego destructive approval/job dla
resource bez `security_continuity=trusted`; utrata trust natychmiast blokuje lub
przerywa execution według przyszłego audytowanego kontraktu. Rekord operacji i
jego wynik pozostają retained dla audytu.

### Host routing invariant

```text
resource current node fact
∩ trusted node binding revision
∩ valid node/hostd attestation
∩ executor readiness
∩ host policy
= eligible typed host route
```

HA `via_device` korzysta z presentation `node_id`, ale nie uczestniczy w
wyborze route. Backend bezpośrednio przed każdą mutacją ponownie rozwiązuje
resource location i sprawdza exact binding/revision/attestation. Po reinstall
node'a pod tą samą nazwą stary binding jest revoked, nowy zaczyna `unverified`,
a wszystkie zależne destructive capabilities są `none` do jawnej re-attestation.
TLS rotation discovery endpointu ani przyszły, osobno zaakceptowany endpoint
failover nie przywracają hostd trust.

## Autorytatywność danych

| Dane | Source of truth |
| --- | --- |
| locator presence i baseline completeness | boundary-valid discovery run |
| per-resource detail facts/status | konkretna `resource_observation`; błąd nie degraduje baseline |
| raw/normalized Proxmox facts | udany odczyt odpowiedniego baseline/detail scope |
| boundary permission coverage/completeness | zgodne canonical `GET /access/acl` topology snapshots oraz zgodne per-path upstream effective permission results na obu granicach discovery window |
| interval-wide consistency/absence | osobno zaakceptowany proof; **UNKNOWN** dla stockowego polling discovery |
| internal resource/node/source identity | backend + SQLite |
| locator binding/generation | transactional reconciliation |
| continuity/removal decision | reconciler + trwałe evidence/audit |
| stored policy/revision history i enrollment | backend + SQLite, trwale przypięte do `resource_id` |
| policy applicability/suspended reason | backendowa derivation z current trust, binding, lifecycle i operation gates |
| effective capabilities | backendowa derivation w chwili odczytu/operacji |
| HA device/entity state | prezentacja committed backend snapshotu |

Discovery opisuje rzeczywistość. Policy opisuje pozwolenie. Żadna wartość ze
snapshotu discovery nie awansuje automatycznie resource do `managed`.

`complete` nie może wynikać z samej odpowiedzi `/cluster/resources`, ponieważ
ACL filtering może po cichu pominąć guest. Sam `GET /access/permissions` także
nie dowodzi braku restrictive descendant ACL: effective permission map może nie
zawierać ścieżki, na której `NoAccess` wyzerował inherited privileges.

Boundary consistency musi otoczyć discovery window dwoma rodzajami odczytu:

```text
canonical ACL topology BEFORE
+ per-path effective permissions BEFORE
→ source-wide baseline i required facts
→ canonical ACL topology AFTER
+ per-path effective permissions AFTER
```

`GET /access/acl` enumeruje security-relevant descendant paths wymagające
kontroli. Dla każdego odpowiedniego path backend zleca Proxmox obliczenie
effective permissions przez `GET /access/permissions?path=<path>` albo
równoważny oficjalnie zweryfikowany kontrakt. Hubinet Ops sprawdza wynik względem
wymaganego `VM.Audit`/`Sys.Audit` coverage, ale nie implementuje własnej kopii
semantyki inheritance, deeper-path replacement, user/group precedence, token
privilege separation, `NoAccess` ani propagation. Ewentualny własny recursive
ACL evaluator wymagałby osobnego ADR i dowodu zgodności z upstream.

Obie pary BEFORE/AFTER muszą być identyczne. Odczyt pełnej topologii przez
`GET /access/acl` wymaga `Sys.Audit` na `/access`. Jest to read-only, lecz
zwiększa zakres widocznych metadanych ACL i stanowi jawny security tradeoff
boundary-complete discovery.

Jeżeli pełnej topologii nie można odczytać lub jednoznacznie ocenić, run jest
`partial`/`configuration_error` i nie uruchamia absence/removal transitions.
Per-VM/per-pool visibility nie zastępuje source-wide coverage. Dokładna finalna
endpoint/ACL matrix pozostaje przedmiotem późniejszego implementation/contract
review.

Matching boundary snapshots nie wykluczają zmiany ACL `A → B → A` podczas
pobierania baseline. Potwierdzają stan wyłącznie na próbkowanych granicach:

```text
boundary-consistent snapshot != interval-wide ACL proof
boundary-consistent complete snapshot != authoritative absence proof
```

Monotonic ACL/config revision albo cursor pokrywający cały interval pozostaje
**UNKNOWN**. Boundary-complete snapshot może ustawić widoczny resource na
`present`; brak wcześniej znanego locatora może dać observational `missing` i
`uncertain`. Nie wystarcza do `confirmed_removed`, physical removal,
security-sensitive closure incarnation ani nadania/przeniesienia destructive
authority. Polling-only automatic `confirmed_removed` pozostaje wyłączone do
zaakceptowania authoritative absence proof.

## Tombstones i retention

Tombstone oraz minimalna historia locator bindings pozostają bezterminowo,
ponieważ ich rozmiar jest mały, a utrata otwiera ryzyko VMID reuse po długiej
przerwie. Szczegółowe observations można kompaktować według późniejszej policy,
ale trzeba zachować:

- resource/source identity;
- wszystkie generacje locatora;
- first/last seen i removed_at;
- evidence i decyzje użyte do continuity/removal;
- policy/enrollment revisions;
- plan/job/audit references.

Purge source, tombstone albo HA device nie jest automatycznym skutkiem
discovery. Osobny retention/purge design może powstać później, ale nie może
usuwać referencji wymaganych do security/audit.

## Published inventory view

API i HA otrzymują wyłącznie widok po commit:

```text
backend_instance_id
sources[]
nodes[] {node_id, source_id, facts, availability}
resources[] {
  resource_id,
  source_id,
  resource_type,
  vmid,
  locator_generation,
  current_node_id | last_known_node_id,
  display_name,
  presence,
  detail_status,
  node_availability,
  observational_continuity,
  security_continuity,
  enrollment/state level,
  retained_policy/history (optional),
  policy_applicability,
  effective_policy,
  suspended_reason,
  read-only facts,
  effective capabilities
}
snapshot_revision
observed_at
```

API może pokazać retained policy/history, ale osobno publikuje derived
applicability/effective policy, suspended reason i capabilities; normalized
discovery snapshot nie zawiera żadnej z tych wartości. HA nie wylicza
applicability z istnienia policy record.

Docelowa relacja node jest zgodna z [ADR 0002](adr/0002-proxmox-discovery-reconciliation.md#node-relation-i-ha-availability):
`present` może mieć znany `current_node_id` przy node `available` albo
`unavailable`, a przy nierozstrzygniętej current relation ma
`current_node_id=null` i opcjonalny `last_known_node_id`. Detail failure nie
zmienia presence. `missing`/`confirmed_removed` nie mają current node i zachowują
last-known presentation relation, jeśli była znana. `last_known_node_id` nigdy
nie jest mutation route.

## HA Device Registry

Rekomendowane identyfikatory są opaque i wersjonowane w serializacji:

```text
backend device: backend_instance_id
source device:  backend_instance_id + inventory_source_id
node device:    backend_instance_id + node_id
resource:       backend_instance_id + resource_id
entity:         backend_instance_id + resource_id + entity_description_key
```

`via_device_id` resource wskazuje Device Registry ID current node'a, gdy relacja
jest resolved. Po migracji relacja się zmienia bez zmiany resource/entity unique
ID. Przy znanym, lecz niedostępnym node pozostaje przy current node. Przy
nierozstrzygniętej relacji, `missing` i `confirmed_removed` integracja zachowuje
last-known presentation relation, dopóki backend nie poda lepszego committed
faktu. Nie ma to znaczenia dla host routing.

Rename aktualizuje display name. `confirmed_removed` oznacza unavailable, nie
delete z registry. Wykryte i potwierdzone ponowne użycie VMID tworzy nowe
`resource_id`, więc nowy workload nie dziedziczy HA device/entity identity
starego. Niewidoczne replacement pomiędzy pollingami może zachować read-only HA
identity, ale nigdy destructive authority.

## Warunki wejścia do implementacji Phase 1

Przed implementacją wymagane są osobne akceptacje:

1. ADR 0001 i ADR 0002 przechodzą z `PROPOSED` do `ACCEPTED`;
2. cały Phase 0 contract zostaje zmieniony zgodnie z `PHASE 0 AMENDMENT
   REQUIRED`: identity, osobne osie locator presence/detail status/node
   availability, semantyka current/last-known node, Coordinator/entity
   availability oraz snapshot/Device Registry validators i tests;
3. endpoint/ACL matrix, w tym delegowanie per-path effective permission
   evaluation do Proxmox, oraz supported PVE versions są jawne;
4. transaction invariants i schema zostają przełożone na testowalny kontrakt,
   który z góry klasyfikuje baseline prerequisites i dowodzi, że per-resource
   detail failure nie degraduje `baseline_completeness`;
5. atomowe initial source creation ustanawia dokładnie jeden initial active
   endpoint; dla existing source URL/relation endpoint record są immutable, a
   replacement, candidate/inactive activation i automatic failover pozostają
   wyłączone do accepted source-binding contract;
6. jedna deterministic/versioned endpoint canonicalization function oraz jej
   positive/negative contract tests zamykają textual alias/history bypasses;
7. controlled `transport_trust_revision` wiąże każdy discovery run, a zmiana
   revision w locie uniemożliwia commit snapshotu starego trust contract;
8. monotonic `source_config_revision` i transaction/CAS tests dowodzą, że każda
   discovery-relevant source mutation serializuje się z reconciliation commit;
9. lifecycle `canonicalization_contract_version`, controlled namespace
   migration oraz negative alias/collision tests zapobiegają obejściu retained
   history po upgrade.

Do tego czasu nie powstają produkcyjne discovery, tabele, endpointy, credentials,
policy mutations ani lifecycle/snapshot/update/maintenance.

Po spełnieniu podstawowych warunków 1–9 read-only discovery/inventory może być
implementowane niezależnie od trzech dalszych gates:

- brak zaakceptowanego authoritative interval-wide absence proof blokuje
  `confirmed_removed`, security-sensitive closure incarnation i automatyczne
  removal/tombstone transitions; nie blokuje `present`/observational `missing`;
- brak zaakceptowanego workload continuity proof/enrollment model blokuje
  globalnie `trusted` destructive capabilities i każdą zależną mutację;
- brak zaakceptowanego source-binding/attestation contract blokuje zmianę active
  transport targetu, replacement active endpointu, aktywację candidate/inactive
  endpointów i multi-endpoint automatic failover.

Żaden z tych trzech braków nie blokuje podstawowego read-only inventory przy
jednym active endpoint. Odpowiednie capabilities/features pozostają wyłączone
fail-closed.
