# Hubinet Ops 0.5 — konceptualny inventory model

Status: **PROPOSED**

Ten dokument materializuje proponowane decyzje z:

- [ADR 0001: identity zasobu i incarnation](adr/0001-resource-identity-incarnation.md);
- [ADR 0002: read-only discovery i reconciliation](adr/0002-proxmox-discovery-reconciliation.md).

Nie jest schema SQL, migracją ani kontraktem endpointu. Hubinet Ops 0.5 tworzy
nową bazę od zera i nie importuje SQLite 0.4.

## Identities i relacje

```text
backend_instance
  └─ inventory_sources
       ├─ source_endpoints
       ├─ nodes
       │    ├─ node_bindings
       │    └─ node_attestations
       ├─ discovery_runs
       └─ resource_incarnations
            ├─ resource_locator_bindings
            ├─ resource_observations
            ├─ continuity_evidence
            ├─ resource_tombstone (optional 1:1)
            └─ resource_policy (optional 1:1, enrolled only)
```

## Encje

### `backend_instance`

- primary identity: losowy `backend_instance_id` UUID;
- immutable: ID, `created_at`;
- mutable: schema/application metadata;
- authoritative: tożsamość instalacji Hubinet Ops;
- retention: cały czas życia nowej bazy;
- constraint: dokładnie jeden aktywny record w jednej bazie.

URL/IP nie jest identity. Clean reinstall bez przywrócenia tej samej bazy tworzy
nową instalację i nowe ID.

### `inventory_sources`

- primary identity: backendowy `inventory_source_id` UUID;
- relacja: należy do `backend_instance_id`;
- immutable: ID, provider kind, `created_at`;
- mutable: display name, lifecycle status, cluster/standalone facts, discovery
  settings i secret reference;
- constraints: source ID unikalny w backendzie; nazwa klastra nie jest unique
  identity;
- authoritative: operatorowa definicja granicy jednego Proxmox environment;
- retention: trwała; po usunięciu source pozostaje historyczny record.

Credentials są przechowywane poza observation/audit payloads. Record zawiera
secret reference, nie jawny token.

### `source_endpoints`

- primary identity: `endpoint_id` UUID;
- relacja: wiele endpointów do jednego source;
- immutable: ID, creation audit;
- mutable: HTTPS URL, priority, enabled, TLS policy/fingerprint metadata;
- constraints: URL unikalny w aktywnym zestawie source; endpoint nie może być
  aktywnie przypięty do dwóch sources bez jawnego review;
- authoritative: operatorowa konfiguracja transportu, nie identity source;
- retention: historyczne bindings zachowane w audit.

### `nodes`

- primary identity: backendowy `node_id` UUID;
- relacja: należy do source;
- immutable: ID, source, first seen;
- mutable: display name, presentation presence i `last_seen`; external node name
  należy do wersjonowanego `node_binding`, nie jest swobodnie nadpisywanym polem;
- constraints: security routing nigdy nie używa samego `node_id` ani nazwy;
- authoritative: backend dla internal identity; discovery dla current facts;
- retention: historyczna identity nie jest natychmiast usuwana.

Node name i Corosync nodeid są evidence/locator facts. Bez oficjalnej globalnej
immutable gwarancji nie zastępują backendowego `node_id`.

`node_id` może zachować HA presentation continuity po operatorowym potwierdzeniu,
ale samo zachowanie `node_id` nie zachowuje mutation trust.

### `node_bindings`

- primary identity: `node_binding_id` UUID;
- relacja: należy do `node_id` i `inventory_source_id`;
- immutable: external node name, binding generation, `valid_from`, enrollment
  provenance;
- mutable: `valid_to`, trust state (`unverified`, `trusted`, `revoked`) i
  monotonic `binding_revision`;
- constraints:
  - co najwyżej jeden aktywny binding dla `(inventory_source_id,
    external_node_name)`;
  - co najwyżej jeden aktywny trusted binding dla `node_id`;
  - każda zmiana security-relevant evidence zwiększa revision albo zamyka
    binding;
- authoritative: backendowa decyzja, który obserwowany host może być mutation
  target;
- retention: historia bindingów bezterminowo.

Binding jest minimalnym odpowiednikiem node incarnation dla granicy wykonawczej,
bez przesądzania, że presentation `node_id` zawsze musi zmieniać się przy
reinstall. Nowy host używający starej nazwy nigdy nie przejmuje active trusted
binding automatycznie.

### `node_attestations`

- primary identity: `attestation_id` UUID;
- relacja: należy do dokładnego `node_binding_id` i revision;
- immutable: typ evidence, fingerprint/public-key identity lub inny później
  zaakceptowany proof, provenance, `verified_at`;
- mutable: validity/revocation metadata;
- authoritative: backend dla statusu trust; zewnętrzne certificates/keys są
  evidence, nie backendową identity;
- retention: bezterminowo dla każdego bindingu użytego do mutacji.

Konkretny attestation protocol pozostaje unresolved. Certyfikat TLS endpointu
discovery, PVE node certificate, SSH host key i hostd identity nie mogą być
zamiennie traktowane jako ten sam proof.

### `resource_incarnations`

- primary identity: `resource_id` UUID;
- relacja: należy do source;
- immutable: ID, source, `resource_type`, `first_seen`;
- mutable: lifecycle (`active`, `quarantined`, `retired`), continuity state,
  current presence, `last_seen`, enrollment state/revision;
- constraints: resource ID nie jest wyliczany z VMID/nazwy/node'a;
- authoritative: backendowa identity jednej incarnation;
- retention: bezterminowa w audit/history.

Nie wprowadzamy osobnego „logical service ID” w tej fazie. Jeśli przyszły
product model będzie łączył kolejne incarnations tej samej usługi, lineage jest
osobną, operatorową relacją i nie może przenosić destructive policy.

### `resource_locator_bindings`

- primary identity: `binding_id` UUID;
- relacja: jedna incarnation ma co najmniej jeden historyczny binding;
- slot locator: `(inventory_source_id, vmid)`;
- immutable: binding ID, locator, `locator_generation`, `valid_from`;
- mutable: `valid_to`, closure reason, expected continuity revision;
- constraints:
  - jeden aktywny binding na `(inventory_source_id, vmid)`, niezależnie od
    `resource_type`;
  - jeden aktywny primary binding na resource;
  - unique `(inventory_source_id, vmid, locator_generation)`;
- authoritative: backendowy wynik reconciliation;
- retention: bezterminowa historia slotu.

`locator_generation` rośnie przy nowym bindingu po replacement, confirmed removal
albo nierozstrzygniętej luce. Nie jest identity i nie jest dowodem replacement.
`resource_type` pozostaje immutable w `resource_incarnations` i opisuje occupant
slotu. Schema zabrania jednoczesnego aktywnego LXC101 i QEMU101 w jednym source.

### `discovery_runs`

- primary identity: `run_id` UUID;
- relacja: należy do source;
- immutable: start/finish/observed timestamps, endpoint, outcome,
  completeness, covered/failed scopes, snapshot hash, optional provider cursor
  range i redacted errors;
- constraints: committed order monotoniczny per source;
- authoritative: audit tego, co provider faktycznie odczytał;
- retention: długoterminowa; payload może podlegać bezpiecznej kompakcji, ale
  decyzje continuity/removal muszą zachować provenance.

### `resource_observations`

- primary identity: `observation_id` UUID albo `(run_id, resource_id)` po
  jednoznacznym reconciliation;
- relacje: run, resource, binding i current node;
- immutable: normalized facts, status, name, observed config metadata,
  presence input, `observed_at`, read result;
- constraints: JSON-like schema/version, deep immutable input;
- authoritative: source dla zaobserwowanych facts; nie dla policy;
- retention: pełne recent history plus kompakcja starszych facts; first/last,
  evidence i audit decisions bezterminowo.

### `continuity_evidence`

- primary identity: `evidence_id` UUID;
- relacje: source, run, locator binding, old/new candidate resource;
- immutable: kind, value/hash, provenance, timestamp, confidence class,
  supports/refutes oraz optional covered cursor;
- authoritative: fakt o evidence; ostateczna decision należy do reconciler;
- retention: bezterminowo dla evidence użytego do enrollment, replacement lub
  removal.

`digest`, `vmgenid`, `meta.ctime`, name i fingerprints muszą zachować swój typ;
nie wolno ich promować do immutable identity przez sam fakt zapisania tutaj.

### `resource_tombstones`

- primary identity: `resource_id` starej incarnation;
- relacje: ostatni binding, removal evidence/run, optional successor lineage;
- immutable po utworzeniu: source, slot VMID, occupant type, generation,
  first/last seen, `removed_at`, reason, continuity/evidence digest;
- authoritative: backendowa pamięć zajęcia i zakończenia slotu;
- retention: bezterminowo w audit history; automatyczny purge nie jest częścią
  projektu.

Tombstone uniemożliwia traktowanie powracającego locatora jako „pierwszego
widzenia” bez historii. Nie rezerwuje VMID w Proxmox i nie nadaje permissions.

### `resource_policies`

- primary/foreign identity: `resource_id` incarnation;
- immutable: przypięcie do resource ID i enrollment audit origin;
- mutable: policy revision i jawne ustawienia operatora;
- constraints: brak policy dla samego locatora; optimistic revision check;
- authoritative: backend/SQLite, nigdy discovery ani HA;
- retention: historia revisions i audit bezterminowo zgodnie z polityką audytu.

Po replacement nowy `resource_id` nie ma policy. Ewentualne przyszłe
„copy settings” musi być osobną, jawną, audytowaną operacją enrollment i nie
może kopiować aktywnych approvals/jobs.

### Przyszłe plans/jobs/locks/audit

Nie są implementowane w tej fazie. Ich kontrakt musi używać `resource_id` oraz
zapisywać snapshot oczekiwanego locator binding i continuity revision. Executor
nie może przyjąć samego VMID. Dla host routing zapisuje również expected
`node_binding_id`, node `binding_revision` i `attestation_id`. Po zmianie
któregokolwiek binding/revision job fail-closed i wymaga ponownej autoryzacji.

### Host routing invariant

```text
resource current node fact
∩ trusted node binding revision
∩ valid node/hostd attestation
∩ executor readiness
∩ host policy
= eligible typed host route
```

HA `via_device` korzysta z presentation `node_id`, ale nie uczestniczy w
wyborze route. Backend bezpośrednio przed każdą mutacją ponownie rozwiązuje
resource location i sprawdza exact binding/revision/attestation. Po reinstall
node'a pod tą samą nazwą stary binding jest revoked, nowy zaczyna `unverified`,
a wszystkie zależne destructive capabilities są `none` do jawnej re-attestation.
TLS rotation discovery endpointu i endpoint failover nie przywracają hostd
trust.

## Autorytatywność danych

| Dane | Source of truth |
| --- | --- |
| raw/normalized Proxmox facts | udany discovery run |
| internal resource/node/source identity | backend + SQLite |
| locator binding/generation | transactional reconciliation |
| continuity/removal decision | reconciler + trwałe evidence/audit |
| user policy/enrollment | backend + SQLite |
| effective capabilities | backendowa derivation w chwili odczytu/operacji |
| HA device/entity state | prezentacja committed backend snapshotu |

Discovery opisuje rzeczywistość. Policy opisuje pozwolenie. Żadna wartość ze
snapshotu discovery nie awansuje automatycznie resource do `managed`.

## Tombstones i retention

Tombstone oraz minimalna historia locator bindings pozostają bezterminowo,
ponieważ ich rozmiar jest mały, a utrata otwiera ryzyko VMID reuse po długiej
przerwie. Szczegółowe observations można kompaktować według późniejszej policy,
ale trzeba zachować:

- resource/source identity;
- wszystkie generacje locatora;
- first/last seen i removed_at;
- evidence i decyzje użyte do continuity/removal;
- policy/enrollment revisions;
- plan/job/audit references.

Purge source, tombstone albo HA device nie jest automatycznym skutkiem
discovery. Osobny retention/purge design może powstać później, ale nie może
usuwać referencji wymaganych do security/audit.

## Published inventory view

API i HA otrzymują wyłącznie widok po commit:

```text
backend_instance_id
sources[]
nodes[] {node_id, source_id, facts, availability}
resources[] {
  resource_id,
  source_id,
  resource_type,
  vmid,
  locator_generation,
  current_node_id | last_known_node_id,
  display_name,
  presence,
  continuity_state,
  enrollment/state level,
  read-only facts,
  effective capabilities
}
snapshot_revision
observed_at
```

API może pokazać policy i derived capabilities, lecz normalized discovery
snapshot ich nie zawiera. `present` resource wskazuje `current_node_id` istniejący
w tym samym published snapshot. Dla pozostałych presence states obowiązuje
jawny `last_known_node_id`, jeśli kiedykolwiek był znany.

## HA Device Registry

Rekomendowane identyfikatory są opaque i wersjonowane w serializacji:

```text
backend device: backend_instance_id
source device:  backend_instance_id + inventory_source_id
node device:    backend_instance_id + node_id
resource:       backend_instance_id + resource_id
entity:         backend_instance_id + resource_id + entity_description_key
```

`via_device_id` resource wskazuje Device Registry ID bieżącego node'a. Po
migracji relacja się zmienia bez zmiany resource/entity unique ID. Przy
`node_unavailable`, `missing` i `confirmed_removed` integracja zachowuje
last-known relation, dopóki backend nie poda lepszego committed faktu.

Rename aktualizuje display name. `confirmed_removed` oznacza unavailable, nie
delete z registry. Ponowne użycie VMID tworzy nowe `resource_id`, więc nowy
workload nie dziedziczy HA device/entity identity starego.

## Warunki wejścia do implementacji Phase 1

Przed implementacją wymagane są osobne akceptacje:

1. ADR 0001 i ADR 0002 przechodzą z `PROPOSED` do `ACCEPTED`;
2. Phase 0 identity contract zostaje zmieniony zgodnie z `PHASE 0 AMENDMENT
   REQUIRED`;
3. zostaje zaakceptowany continuity proof/enrollment model albo destructive
   capabilities pozostają globalnie wyłączone;
4. endpoint/ACL matrix i supported PVE versions są jawne;
5. transaction invariants i schema zostają przełożone na testowalny kontrakt.

Do tego czasu nie powstają produkcyjne discovery, tabele, endpointy, credentials,
policy mutations ani lifecycle/snapshot/update/maintenance.

Brak zaakceptowanego workload continuity proof nie blokuje przyszłej
implementacji read-only discovery/inventory. Blokuje globalnie nadanie
`trusted` destructive capabilities i każdą ścieżkę mutacji zależną od takiego
trust.

## Sources / Evidence

Semantyka pól Proxmox oraz ACL jest udokumentowana wraz ze źródłami w ADR 0001
i ADR 0002. Ten dokument jest architektoniczną inferencją i proponowanym
backendowym modelem; nie przedstawia backendowych UUID, tombstones ani
continuity states jako funkcji dostarczanych przez Proxmox.
