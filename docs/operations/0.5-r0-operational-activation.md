# Hubinet Ops 0.5 R0 — operational activation runbook

Status: operator checklist for the **first real activation** of the
merged WAVE R0-B read-only runtime. This document does not perform that
activation — it is the authoritative procedure a later, separately
authorized mission must follow.

Authorized implementation baseline for this runbook:

```text
main merge commit:            20c0484d1efffcf1fe700ac1cd232cecba4fc0ea  (PR #35)
reviewed R0-B implementation:  84f3b5e632337b5c495ed34bc150cabfe9c67813
```

R0-B passed an independent architecture/contract review, a corrective
pass closing five P2 findings, a second independent implementation
review (PASS, one non-blocking P3), Linux `validate` CI, and Home
Assistant `2026.8.1` CI, at that exact reviewed HEAD. See
`docs/architecture/0.5-implementation-status.md` for the full review
history. **None of that means R0 has been deployed anywhere.** This
runbook exists because it hasn't been yet.

## 0. Non-negotiable framing

This is 0.5's own clean break, not a 0.4 upgrade:

```text
target host:        a freshly rebuilt CT110 (or equivalent), never a host
                     that has ever run the 0.4 production service
0.4 migration:       NONE -- no DB import, no config import, no state
                     transfer
static inventory:    NONE -- no VMID/resource list anywhere; every node/
                     QEMU/LXC is discovered dynamically through the PVE
                     API after source bootstrap
coexistence:         NONE -- this is not a canary, not a sidecar, not a
                     cutover period; the rebuilt host runs only the R0
                     runtime
```

If any step in this runbook reveals the target does not actually meet
this model, **STOP** — see §1. Do not improvise an in-place migration or
a side-by-side deployment to work around it.

Every step below is written for the human operator performing the real
activation. Nothing in this document should be executed by an agent
against a real host, a real PVE endpoint, or a real Home Assistant
instance.

## 2. PVE read-only credential preparation

R0's production PVE transport (`app/inventory_pve_transport.py`) is
GET-only by construction — it defines no `post`/`put`/`patch`/`delete`/
`request` method, so it cannot issue a mutating PVE API call even if a
broader token were supplied. This section documents the credential
*shape* R0's discovery contract actually requires; it does not create
one.

### 2.1 Exact endpoints and privileges required

Derived directly from `app.inventory.provider.ENDPOINT_ACL_MATRIX` and
`evaluate_permission_coverage` (`app/inventory/provider.py`) — not
guessed:

| Endpoint | Purpose | ACL path | Privilege required |
| - | - | - | - |
| `GET /version` | provider version check | `/` | none (self-describing) |
| `GET /access/acl` | ACL topology boundary read | `/access` | `Sys.Audit` |
| `GET /access/permissions` | effective-permission proof (self) | n/a | none — any authenticated token may query its own effective permissions |
| `GET /cluster/status` | cluster vs. standalone mode | `/` | `Sys.Audit` |
| `GET /nodes` | node baseline | `/nodes` | `Sys.Audit`, **with propagation** |
| `GET /cluster/resources?type=vm` (cluster mode) | guest locator baseline | `/vms` | `VM.Audit`, **with propagation** |
| `GET /nodes/{node}/qemu`, `GET /nodes/{node}/lxc` (standalone mode) | guest locator baseline | `/vms` | `VM.Audit`, **with propagation** |
| `GET /nodes/{node}/{type}/{vmid}/config` | optional per-guest detail (not used by this R0-B package) | `/vms/{vmid}` | `VM.Audit` (not required today — no code path calls this endpoint yet) |

`evaluate_permission_coverage` additionally re-checks `Sys.Audit` at the
exact path `/nodes/{each-discovered-node-name}` for every node the
source reports — in practice this is satisfied automatically once
`Sys.Audit` on `/nodes` propagates, since PVE reports the inherited
grant as effective at the child path too.

**Net requirement: `Sys.Audit` + `VM.Audit`, granted at `/` (or at least
at `/access`, `/nodes`, and `/vms`) with propagation enabled.** This is
exactly the stock PVE `PVEAuditor` role's privilege set — a read-only
role Proxmox ships by default. No custom role is required unless the
operator specifically wants to trim it to only these two privileges.

### 2.2 Why a restricted/per-VM token is insufficient

A token scoped only to a specific pool or a specific `/vms/{vmid}` path
**cannot** satisfy `collect_boundary_baseline`'s source-wide coverage
requirement: the contract explicitly requires `Sys.Audit` on `/nodes`
and `VM.Audit` on `/vms` — the *whole-source* locator baseline paths —
not a per-guest grant. A narrower token will make discovery runs
complete with `baseline_completeness=configuration_error` (never
`complete`), and the source will never leave the "not fresh"/
"configuration_error" state. This is fail-closed, not a bug — see ADR
0002's `configuration_error` definition (§28 Finding 3 of the prior
review closed exactly this classification path).

### 2.3 What must never be granted

Do not grant, and do not use a token that already carries:

```text
VM.Config.*        (any guest configuration mutation)
VM.PowerMgmt        (start/stop/reboot)
VM.Monitor           (guest console/monitor access — not audit)
Datastore.Allocate*  (snapshot/disk mutation)
Sys.Modify           (host/cluster configuration mutation)
Sys.PowerMgmt        (host power management)
Realm.AllocateUser, User.Modify (identity mutation)
root@pam full administrative token
```

R0 has no code path that could use any mutation privilege even if
granted (§9/§10 of `docs/architecture/0.5-r0-read-only-runtime-
activation.md`), but the operator should still provision the
*narrowest* credential as defense in depth, consistent with least
privilege.

### 2.4 Creating the token (operator action, not performed here)

Standard PVE operator procedure (illustrative — run on the PVE host by
the operator, not by this runbook):

```bash
pveum user token add hubinetops@pve r0-readonly --privsep 1
pveum acl modify / --tokens 'hubinetops@pve!r0-readonly' --roles PVEAuditor
```

`--privsep 1` (the default) means the token's *own* effective
permissions are the intersection of the user's permissions and the
token's own ACL grant — assign the `PVEAuditor` role directly to the
token (as above), not only to the user, so the token cannot silently
inherit broader user-level privileges later.

The resulting token secret goes only into
`/etc/hubinet-ops/agent.env`'s `HUBINET_OPS_R0_PVE_TOKEN`, in the exact
shape `user@realm!tokenid=secret` (see `.env.r0.example`). It is never
written to `config/inventory.yaml`'s `credential_reference` (which is a
non-secret opaque label, not the token itself — see §5/§7 of
`docs/architecture/0.5-r0-read-only-runtime-activation.md`) and never
committed to the repository.

### 2.5 Verifying the token cannot mutate (safe method only)

Do **not** issue a real mutating PVE API call merely to prove it fails.
Instead, verify statically and administratively:

1. `pveum acl list` (or the PVE web UI's Permissions view) on the
   token's exact path — confirm the only role attached is `PVEAuditor`
   (or an equivalently audit-only custom role), not `PVEAdmin`,
   `PVEVMAdmin`, `PVEDatastoreAdmin`, or any role containing a
   `.Modify`/`.Allocate`/`.Config`/`PowerMgmt` privilege.
2. `pveum role list` / `pveum role show PVEAuditor` — confirm the role's
   own privilege set contains no mutation privilege (stock `PVEAuditor`
   never does).
3. Cross-check against R0's own transport: `app/inventory_pve_transport.
   py`'s `ProxmoxHttpTransport` class defines no `post`/`put`/`patch`/
   `delete`/`request` method at all — even a token with broader
   privileges could not be used to mutate through this code path. This
   is a repository-level, already-tested guarantee
   (`tests/test_inventory_pve_transport.py::
   test_12_adapter_exposes_no_mutation_or_generic_request_method`), not
   something this runbook needs to re-prove against the real endpoint.

## 3. TLS trust preparation

Strict TLS verification is mandatory and cannot be disabled — R0's
transport rejects `verify=False` at construction
(`app/inventory_pve_transport.py::_require_verification_enabled`; see
also the corresponding `source.tls.verify` fail-closed check in
`app/inventory_runtime_config.py`). Never document, request, or apply:

```text
verify=false
--insecure
skip TLS verification
temporary certificate bypass
```

Exactly two supported cases, both already implemented:

### 3.1 System CA trust (`source.tls.verify: true`, `ca_bundle_path: null`)

Use this when the PVE endpoint's certificate chains to a CA the target
host's own OS trust store already recognizes (a publicly-trusted CA, or
an internal CA whose root has been installed into the target's system
trust store separately). No further action needed in
`inventory.yaml` beyond the example's defaults.

### 3.2 Explicit CA bundle (`ca_bundle_path: /path/to/ca.pem`)

Use this when the PVE endpoint presents a certificate from a private CA
not already in the system trust store. Before enabling the service,
verify:

```text
[ ] the CA bundle file exists at the exact path configured
[ ] it is a regular file (not a directory, symlink to a missing target,
    device, etc.)
[ ] it is readable by the hubinetops service user (mode 0640, owner
    root:hubinetops matches the installer's own convention for
    /etc/hubinet-ops/* -- see deploy/install-0.5.0-fresh.sh)
[ ] the path in inventory.yaml (source.tls.ca_bundle_path) matches
    exactly where the file was actually placed
[ ] the certificate chain is expected to validate successfully against
    that bundle (verify with `openssl verify -CAfile <bundle>
    <server-cert>` against a copy of the PVE endpoint's certificate,
    obtained through your organization's normal certificate-management
    process -- not by having R0 itself attempt and observe a real
    connection during this readiness mission)
```

`app/inventory_runtime_config.py` already fails closed at process
startup if the configured `ca_bundle_path` does not exist or is not
readable (`R0ConfigError`) — this is a second, independent safety net
beyond the operator's own pre-flight check above, not a substitute for
it (a file that exists and is readable at startup can still not be
placed at the path the operator *intended*, which is why the
`[ ] the path in inventory.yaml ... matches exactly` line above matters
independently).

No real endpoint is contacted by this runbook to validate any of the
above — that validation happens for real only during the later,
separately authorized activation.

## 4. Firewall activation order

**This order is mandatory and must never be reversed.** Reusing exactly
the model documented in `deploy/README-0.5-firewall.md`:

```text
1. install files/unit          (deploy/install-0.5.0-fresh.sh)
2. service remains disabled     (the installer itself never calls
   and stopped                  systemctl enable/start -- verified by
                                 tests/test_deploy_0_5_fresh_install.py::
                                 test_43_install_script_never_starts_or_
                                 enables_the_service_itself)
3. configure secrets/config    (edit inventory.yaml + agent.env)
4. apply firewall              (deploy/README-0.5-firewall.md examples)
5. verify firewall             (see checks below)
6. only then:
   systemctl enable --now hubinet-ops
```

Never run step 6 before step 5. Never treat "the installer finished" as
equivalent to "the service is safe to enable."

### 4.1 Required effective policy

```text
ALLOW  ingress  HA host/subnet -> R0 host TCP 8787
DENY   ingress  everything else -> R0 host TCP 8787
ALLOW  egress   R0 host -> configured PVE endpoint HTTPS port (8006 by default)
DENY   egress   every other R0 outbound connection class, per the
                selected firewall model (nftables per-service-user
                skuid scoping, or ufw host-wide default-deny-outgoing --
                see deploy/README-0.5-firewall.md for both worked
                examples and why each is genuinely restrictive, not
                merely documented as such)
```

### 4.2 Verification checklist (before step 6)

```text
[ ] systemctl status hubinet-ops reports inactive/disabled
[ ] firewall policy applied (nft list ruleset / ufw status verbose)
[ ] nftables: `meta skuid "hubinetops" drop` present as the effective
    fallthrough for the hubinetops user's own output traffic, with the
    PVE-HTTPS allow rule ahead of it
    -- OR --
    ufw: `ufw status verbose` reports `Default: deny (outgoing)` with an
    explicit `ALLOW OUT` rule only for the configured PVE endpoint:8006
[ ] HA host/subnet -> R0:8787 rule present and correctly scoped to the
    actual HA IP/subnet from §1 row 10 (not 0.0.0.0/0)
[ ] no other inbound rule permits reaching 8787 from elsewhere
[ ] if source.pve_endpoint is a hostname (not a literal IP), either:
      (a) a DNS-resolution allow exists, narrowly scoped to your own
          local/internal resolver only (never "DNS at large" / any
          public resolver) -- see deploy/README-0.5-firewall.md, or
      (b) pve_endpoint has instead been configured as a literal IP
          address, and no DNS rule is needed at all
    Do not broaden R0's egress beyond this pairing for any other reason.
```

Do not enable the service until every line above is checked.

## 5. First-start acceptance sequence

Only after §4 completes (firewall verified) does the operator run:

```bash
systemctl enable --now hubinet-ops
systemctl status hubinet-ops --no-pager
```

Then work through this sequence in order:

```text
[ ] systemd reports the service `active (running)`, not `activating` or
    `failed`
[ ] no restart loop -- `systemctl status` shows a stable start
    timestamp, not a rapidly incrementing restart count
    (journalctl -u hubinet-ops --since "-5min" for corroborating detail)
[ ] GET http://<target>:8787/r0/v1/health returns 200 and exactly
    {"status": "ok"} with no authentication header -- confirms the
    process is alive and the authority DB opened successfully
[ ] GET http://<target>:8787/r0/v1/backend with
    `Authorization: Bearer <HUBINET_OPS_R0_API_TOKEN>` returns 200 with
    a backend_instance_id -- record this UUID; it must remain identical
    across every future restart of this exact authority DB
[ ] GET http://<target>:8787/r0/v1/snapshot with the same bearer token
    returns 200 with a well-formed snapshot body
[ ] the snapshot's sources[] contains exactly the one bootstrapped
    source, matching inventory.yaml's display_name
[ ] source health/freshness is understood: immediately after the first
    successful discovery cycle, health should be "healthy" and
    freshness "fresh"; before the first cycle completes, "not_yet_
    observed" is expected and correct, not an error
[ ] nodes[] reflects the real PVE node(s) -- confirms dynamic node
    discovery, no config edit was needed for them to appear
[ ] resources[] contains the real QEMU guests present on the source
[ ] resources[] contains the real LXC guests present on the source
[ ] confirm no VMID/resource was ever typed into inventory.yaml to make
    any of the above appear -- discovery is entirely dynamic
[ ] every resources[].state_level is "discovered" -- none is "managed",
    "maintenance", or "break_glass" (R0 has no path to any of those)
[ ] every resources[].security_continuity is "unverified" (or
    "revoked" if applicable) -- never "trusted"
[ ] every resources[].effective_capabilities is an empty list
[ ] no resources[].presence is ever "confirmed_removed" on this first
    pass -- that transition requires an explicit, separate, currently-
    dormant operator decision (ADR 0004) that nothing in R0 ever
    triggers automatically
[ ] no attestation-related field changes on its own between polls --
    source attestation enrollment (ADR 0003) is never called by R0
```

### 5.1 Log inspection (secrets must never appear)

```bash
journalctl -u hubinet-ops -n 200 --no-pager
```

Confirm the log output contains **none** of:

```text
the PVE API token value
the literal Authorization header value (either direction)
the R0 API bearer token value
```

R0's own code has no logging statement that emits any of these
(`app/inventory_pve_transport.py` has no logger at all; `app/
inventory_runtime.py`'s bearer-check never logs the header value; this
is covered by `tests/test_r0_architecture_regression.py::
test_r0_bearer_token_never_appears_in_server_logs`). If any of the
above ever appears in a real log, treat it as a NO-GO per §14 and do not
paste the leaked value into any issue, chat, or report while
investigating — redact it first.

## 6. Real Home Assistant acceptance checklist

Perform this only after §5 passes. Do not perform it as part of this
readiness mission.

```text
[ ] confirm HA can reach R0 only through the firewall-permitted path
    (HA host/subnet -> R0:8787) -- attempt from a host outside that
    subnet and confirm it is refused, if you have a safe way to do so
[ ] configure the Hubinet Ops HA integration with exactly: R0 base URL
    (http://<target>:8787), the R0 API bearer token, and verify_tls per
    §3's decision -- nothing else
[ ] confirm HA's config entry never asks for, stores, or references any
    PVE credential -- structurally impossible per the contract (§17 of
    docs/architecture/0.5-r0-read-only-runtime-activation.md), but
    confirm the config flow form itself has no such field
[ ] confirm the config entry's unique_id matches the backend_instance_id
    recorded in §5 -- reauth/reconfigure against a different backend
    must be rejected (existing, unchanged config_flow.py behavior)
[ ] confirm source/node/resource devices appear in HA's device registry,
    matching what §5 observed via the raw HTTP API
[ ] add a new PVE VM or LXC (in a safe/reproducible test environment,
    not production guests) and confirm it appears in HA on the next
    coordinator refresh with zero Hubinet Ops config change or reload
[ ] rename a guest in PVE and confirm HA's device/entity identity is
    preserved (same resource_id, updated name) rather than creating a
    new device
[ ] migrate a guest to a different node (if your topology allows) and
    confirm resource identity is preserved across the node change
[ ] simulate or wait for a source outage and confirm HA retains the
    prior inventory view and reflects the changed source health/
    freshness, rather than clearing/inventing state
[ ] confirm HA never computes freshness locally -- it always reflects
    exactly what the backend published (coordinator.py's existing,
    unchanged behavior)
[ ] confirm a terminal/retained resource (if one exists from prior
    testing) is presented as unavailable per the accepted contract,
    not silently dropped from the registry
```

Do not add, request, or wire any mutation control into HA as part of
this checklist — none exists in R0 and none is authorized (§15).

## 7. Observation window

This is an operational recommendation, not a new architecture invariant.
Before declaring R0 operationally accepted (§8), observe the running
service across **at least 24 hours and multiple scheduler cycles**
(the scheduler's interval is derived from `freshness_duration_seconds`,
clamped between 30s and 3600s — see `app/inventory_scheduler.py::
_clamped_interval_seconds`), covering:

```text
[ ] normal successful rediscovery (health stays "healthy", freshness
    stays "fresh" across several consecutive cycles)
[ ] unchanged-inventory rediscovery (inventory_revision does not churn
    when nothing on the source actually changed -- published_state_
    revision may still advance on pure health/freshness transitions,
    which is expected)
[ ] new workload discovery, if safely reproducible in a test PVE
    environment (§6)
[ ] a rename or other harmless presentation change, if safely
    reproducible
[ ] a temporary PVE API outage/unavailable condition, if it can be
    tested safely (e.g. a maintenance window on a non-production PVE
    test instance) -- confirm health becomes "source_unavailable",
    freshness becomes "stale", and all prior inventory is retained
    exactly (this exact behavior is already covered by
    tests/test_r0_architecture_regression.py::
    test_34_source_unavailable_retains_prior_inventory_end_to_end
    against a simulated fixture; the observation window's purpose is to
    see it hold against the real environment, not to re-derive it)
[ ] a full R0 service restart (systemctl restart hubinet-ops) --
    confirm backend_instance_id is unchanged, startup recovery runs
    without error, and discovery resumes normally
[ ] R0 restart recovery specifically after an abnormal stop (kill -9 the
    process, or a host reboot) -- confirm the next start's startup
    recovery (perform_startup_recovery) cleanly fences any stranded
    discovery run and resumes scheduling
[ ] a Home Assistant restart/reload of the config entry -- confirm the
    integration reconnects and reflects state correctly without
    requiring reconfiguration
[ ] freshness transition behavior specifically: let one cycle's
    freshness deadline elapse without a new successful run (e.g. by
    temporarily lengthening the gap beyond freshness_duration_seconds)
    and confirm the source transitions to "stale"/"time_expiry" on the
    next GET /r0/v1/snapshot, purely as a backend-owned computation
```

**Do not** perform destructive guest replacement or removal merely to
exercise R0's acceptance criteria — none of that is required, and R0's
confirmed-removal path is deliberately dormant and must stay that way
during this window (§15).

## 8. Explicit ABORT / rollback procedure

R0 is clean-break; there is no 0.5→0.4 migration path and none should be
invented. If activation must be aborted at any point:

```text
1. systemctl stop hubinet-ops
2. systemctl disable hubinet-ops
3. If a real HA config entry was created (§6), remove/disconnect it in
   HA so it stops polling a service that is no longer expected to
   respond.
4. Retain, do not delete:
     - the fresh 0.5 authority DB (/var/lib/hubinet-ops/authority.db and
       its -wal/-shm siblings)
     - journalctl output covering the activation window
       (journalctl -u hubinet-ops --since <start-time> > <file>)
     - the exact inventory.yaml used (with secrets already absent --
       this file never contains them)
   for diagnosis, before any rebuild or retry.
5. Do NOT mutate PVE in any way as part of the abort -- R0 never had
   mutation capability to begin with, so there is nothing to "undo" on
   the PVE side.
6. Do NOT fabricate a database rollback (e.g. hand-editing authority.db)
   -- if the authority DB is suspect, the correct next step is a fresh
   clean install against a newly rebuilt target, never an in-place
   repair.
7. Do NOT restore or migrate any legacy 0.4 state into this runtime --
   if 0.4 operation is still needed on this specific host, that is an
   entirely separate decision outside this runbook's scope, not a
   "rollback" of R0.
```

For this first activation, "rollback" means **stop accepting the new
read-only runtime as operational** and collect evidence — it does not
mean reverting to a 0.4 runtime on the same host, which this design
never supports side-by-side in the first place (§0).

## 9. Explicit R0 operational acceptance criteria

Final decision, made only after §1–§7 are all complete:

### GO

All of the following hold:

```text
[ ] service stable across the full observation window (§7)
[ ] firewall verified per §4.2, both directions
[ ] strict TLS verified per §3 (system trust or CA bundle, never bypass)
[ ] PVE discovery reaches baseline_completeness=complete on a normal
    cycle (visible indirectly via source health="healthy"/
    freshness="fresh")
[ ] HA HTTP integration stable per §6
[ ] backend_instance_id stable across every restart observed
[ ] dynamic source/node/QEMU/LXC inventory confirmed per §5/§6 --
    zero static config was needed for any of it
[ ] no mutation path observed or reachable (structurally guaranteed by
    the transport/HTTP surface, additionally confirmed by observation)
[ ] no trusted continuity path observed -- security_continuity never
    left "unverified"/"revoked"
[ ] secrets absent from every inspected log (§5.1)
[ ] restart/recovery behavior accepted per §7
```

### GO WITH OBSERVATION

Use this instead of a plain GO when every item above holds except one or
more *non-security* operational items still need a longer soak (e.g. the
24-hour window in §7 has not yet fully elapsed, or a specific rare
condition like PVE-outage recovery has not yet been naturally observed
and a safe synthetic test is still pending). Document exactly which
item(s) remain open and the date they will be re-checked.

### NO-GO

Any of the following is an **immediate** NO-GO, regardless of how well
everything else performed:

```text
- any unexpected mutation attempt (should be structurally impossible;
  if observed at all, this is a critical finding, not a tuning issue)
- security_continuity ever observed as "trusted"
- any automatic confirmed_removed transition
- any automatic source attestation/enrollment or endpoint activation/
  failover
- any dependency on legacy 0.4 DB/config discovered at runtime
```
