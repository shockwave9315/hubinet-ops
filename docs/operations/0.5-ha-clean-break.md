# Home Assistant 0.4 → 0.5 clean break: design and operator purge plan

Status: **DESIGN DOCUMENT — not executed.** Nothing in this document has been run
against any real Home Assistant instance. It defines what "clean" means, inventories
every legacy artifact that must be gone before 0.5 enrollment, and lays out a purge
sequence for a later, separately-authorized operator session. See
[`0.5-r0-operational-activation.md`](0.5-r0-operational-activation.md) for how this
gate fits into the overall R0 activation runbook.

## 0. Why this document exists

The 0.5 rewrite is a clean-break architecture (`docs/architecture/adr/0001-resource-identity-incarnation.md`,
`docs/architecture/adr/0002-proxmox-discovery-reconciliation.md`): opaque
backend-generated `resource_id` identity, source-centric dynamic discovery, no static
VMID inventory. The legacy 0.4.x Home Assistant surface (`home-assistant/*`, deployed
onto a real HA instance by `deploy/install-ha-*.sh`) is the opposite of that on every
axis: hardcoded VMIDs, static generated dashboards, MQTT-era entity names, and REST
mutation commands driven straight from HA scripts/automations, bypassing the 0.5
identity and policy model entirely.

A real Home Assistant installation belonging to this operator currently has the 0.4.2
package and dashboard installed and active. That is a fact about the *real instance*,
not about this repository — nothing here deletes or touches it. This document exists so
that when the operator later decides to enroll 0.5, they do it against a Home Assistant
that has **zero** active 0.4 Hubinet Ops surface, rather than layering a new integration
on top of an old one that still holds real mutation authority over CT101-CT110/VM100.

## 1. Core invariant

> **A fresh 0.5 config entry must never coexist operationally with the old 0.4 Home
> Assistant presentation/control plane.**

This is not a migration. There is:

- **no** entity-ID mapping from the old MQTT/static `sensor.hubinet_ops_*` entities into
  new 0.5 resource identities;
- **no** preservation of the old VMID-based dashboard/card structure;
- **no** automatic carry-over of old automations, scripts, `rest_command:` definitions,
  `input_boolean:` helpers, or `secrets.yaml` entries.

The 0.4 surface is removed first, as an independent operator action, verified absent,
and only then is a brand-new 0.5 config entry created. The two systems are never
simultaneously live against the same PVE resources.

## 2. Legacy artifact inventory and classification

Four classifications, matching the review vocabulary this repository already uses:

- **ACTIVE LEGACY SURFACE (real-instance)** — content that, once deployed onto a real HA
  instance, is *live* there: it holds mutation authority, appears in the sidebar, or is
  loaded by `configuration.yaml`. Must be purged from the real instance before 0.5
  enrollment (§4). The files under `home-assistant/` in this repo are the *source* for
  that live content, not the live content itself — deleting/keeping them in the repo is
  a separate, later decision (§6) and is explicitly out of scope for this document.
- **HISTORICAL RELEASE ARTIFACT** — stays in the repository; supports the still-shipped
  0.4.x track (builds it, validates it, tests it); not part of the 0.5 runtime or
  install path in any way.
- **0.5 CONTRACT/INTEGRATION** — the current 0.5 presentation layer; preserved, this is
  what the fresh enrollment in §5 actually uses.
- **UNKNOWN — requires on-site inventory** — cannot be classified from the repository
  alone; must be checked against the operator's actual live HA instance before any
  deletion.

## 3. What is explicitly NOT mapped forward

The following 0.4 behaviors are retired as part of the clean break, not migrated,
translated, or reproduced in any form under 0.5 R0:

- Hardcoded `VM100` / `CT101`–`CT110` VMID references anywhere in HA config, entity
  IDs, scripts, or automations.
- Fixed resource "groups" (group 1/2/3-style static categorization).
- Old-version presentation: 0.4-era sensor attributes, health-status strings, "agent
  availability/version" entities tied to CT110 self-inspection.
- Pending-update / approval / active-job UI: `input_boolean` approval toggles, job
  progress sensors, approve/reject scripts — R0 is read-only and has no lifecycle
  concept to present.
- Every `rest_command:` issuing POST/DELETE mutation calls (scan, refresh,
  retry-healthcheck, rollback, approve, reject, self-update-plan, start/shutdown/
  reboot/force-stop, snapshot create/restore/delete/delete-oldest/delete-unprotected,
  host start, host offline recovery).
- Lifecycle controls and snapshot controls of every kind.
- CT110 break-glass/offline-recovery scripts (`..._offline_snapshot_restore_ct110`,
  `..._offline_force_stop_ct110`) — R0 has no host-control or recovery-credential
  concept; that trust boundary does not extend into 0.5 at all yet.
- MQTT-era entity naming (`sensor.hubinet_ops_ct1XX_*`, `sensor.hubinet_ops_agent_*`,
  `sensor.hubinet_ops_vm100_*`) and the MQTT discovery mechanism itself. 0.5 uses HA's
  native config-entry + coordinator + Device/Entity Registry model exclusively
  (§5, §6) — there is no MQTT broker in the 0.5 data path at all.

None of the above gets an equivalent in R0. R0 is observation-only; it has no approval,
job, snapshot, or lifecycle model to present, so there is nothing to translate these
into — they are simply absent until (and unless) a later, separately-designed R1+ wave
adds them.

## 4. Purge sequence (design only — for a later, separately-authorized operator session)

This sequence is **not executed by this document or this mission**. It is written so
that a future operator session has an unambiguous, low-risk procedure to follow,
preferring supported HA UI/config paths over any direct storage-file edit.

### 4.1 Preconditions

1. Take a full HA `config/` backup (HA's own Settings → System → Backups, or an
   equivalent file-level backup of `/config`) before touching anything below. Confirm
   the backup is restorable before proceeding.
2. Inventory the real instance's current state against §2's table: confirm which files
   actually exist under `/config/packages/`, `/config/dashboards/`, whether
   `configuration.yaml` still includes the `lovelace:` block from
   `home-assistant/configuration.snippet.yaml`, and whether `secrets.yaml` still holds
   the `hubinet_ops_*` keys from `home-assistant/secrets.example.yaml`. Record this
   inventory as evidence before deleting anything — this closes the §2 UNKNOWN row.
3. Confirm, by reading the real automations/scripts list in the HA UI (Settings →
   Automations & Scenes, Settings → Scripts), whether anything *outside* the shipped
   `hubinet_ops.yaml` package references a `sensor.hubinet_ops_*`/`script.hubinet_ops_*`
   entity. If so, that reference needs its own resolution before its target entity is
   removed — do not delete out from under a live reference without checking first.

### 4.2 Purge steps

Each step uses HA's supported UI/config removal path, not a `.storage` JSON edit.

1. **Disable, don't yet delete, the old dashboard's sidebar entry.** Settings →
   Dashboards → remove the "Hubinet Ops" custom YAML dashboard entry (this is the
   supported UI action corresponding to removing the `lovelace:` block from
   `configuration.yaml`).
2. **Remove the `lovelace:` dashboard-registration block** matching
   `home-assistant/configuration.snippet.yaml` from the real `configuration.yaml`, and
   restart/reload HA per its own change-detection requirements (a `lovelace:` change
   normally needs a full restart, not just a config reload).
3. **Remove `/config/dashboards/hubinet_ops.yaml`** now that nothing references it.
4. **Remove the package include.** If `packages/hubinet_ops.yaml` is loaded via a
   `homeassistant: packages: !include_dir_named packages` (or equivalent) block already
   present in `configuration.yaml` for *other* packages too, do not touch that shared
   include mechanism — only remove the single file
   `/config/packages/hubinet_ops.yaml`. This automatically removes its `rest_command:`,
   `script:`, `automation:`, and `input_boolean:` definitions on next restart.
5. **Restart Home Assistant** and confirm, via Settings → Automations & Scenes,
   Settings → Scripts, Developer Tools → States, that no `hubinet_ops_*` automation,
   script, or `rest_command` service remains registered.
6. **Remove the now-orphaned `secrets.yaml` entries** listed in
   `home-assistant/secrets.example.yaml` (§2) — the URL/authorization/webhook/notify
   keys — from the real `secrets.yaml`. Leave every unrelated secret untouched.
7. **Confirm no MQTT discovery state remains.** If Home Assistant's MQTT integration
   was used for anything beyond Hubinet Ops 0.4, do not disable MQTT itself. Only
   remove the Hubinet Ops-originated discovery topics/devices: in Settings → Devices &
   Services → MQTT → Devices, remove any device whose entities are exclusively
   `hubinet_ops_*`. Removing a device this way is the supported path that also clears
   its retained discovery config from the broker and its Device/Entity Registry
   objects — prefer this over manually deleting registry entries.
8. **Remove stale Device/Entity Registry objects only after their owning
   integration/device is already gone.** After steps 4-7, any `sensor.hubinet_ops_*`
   entity still visible in Settings → Devices & Services → Entities is orphaned
   (unavailable, no owning integration). Remove those individually via the UI's
   "delete" action on the entity page. Do **not** hand-edit
   `.storage/core.entity_registry` or `.storage/core.device_registry` JSON — those are
   HA-internal files; if an entity cannot be removed through the UI, that is a signal
   to stop and investigate why (something still owns it), not a signal to edit the
   storage file directly. A direct `.storage` edit is only in scope if a later,
   separately-reviewed recovery procedure explicitly authorizes it for a specific
   stuck object — this document does not grant that authorization.

### 4.3 Acceptance condition

> **HOME ASSISTANT HAS ZERO ACTIVE HUBINET OPS 0.4 CONTROL/PRESENTATION SURFACE BEFORE
> 0.5 IS ENROLLED.**

Concretely, before proceeding to §5:

- no `hubinet_ops` dashboard in the sidebar;
- no `hubinet_ops_*` entry in `configuration.yaml`'s `lovelace:` block;
- `/config/packages/hubinet_ops.yaml` and `/config/dashboards/hubinet_ops.yaml` absent;
- zero `rest_command.hubinet_ops_*`, `script.hubinet_ops_*`, `automation.hubinet_ops_*`
  registered (Developer Tools → States search for `hubinet_ops` returns nothing under
  those domains);
- zero `hubinet_ops_*` keys remaining in `secrets.yaml`;
- zero MQTT-discovered `hubinet_ops_*` devices/entities remaining;
- unrelated HA configuration (other packages, dashboards, automations, MQTT devices,
  secrets) verified untouched.

Only once every item above is independently confirmed true does §5 begin.

## 5. Fresh 0.5 HA enrollment boundary

A brand-new Hubinet Ops config entry, created only after §4.3's acceptance condition
holds, is bounded to exactly the fields `custom_components/hubinet_ops/const.py` /
`config_flow.py` define — confirmed by direct read of `__init__.py` and
`config/inventory.example.yaml`:

**In scope for the config entry (`create_api_client`, `HubinetOpsApi`):**

- `base_url` — the R0 HTTP API's own base URL (never a PVE endpoint).
- `api_token` — the R0 read-only bearer token (`config/.env.r0.example`'s
  `HUBINET_OPS_R0_API_TOKEN`), entirely independent from, and never derived from or
  shared with, the PVE API token.
- `verify_tls` — strict TLS verification against the R0 API.
- The backend-instance-id binding already enforced by `config_flow.py`/`coordinator.py`
  on setup/reauth/reconfigure (rejects silently pointing an existing entry at a
  different backend).

**Explicitly out of scope for the config entry — none of these exist in
`custom_components/hubinet_ops/const.py`, and none may be added as part of this or any
future 0.5 R0 enrollment:**

- a PVE API token or any direct PVE endpoint (HA never talks to Proxmox directly, only
  through the R0 backend, per the mutation trust path in `CLAUDE.md`);
- any MQTT broker configuration — 0.5 has no MQTT foundation at all;
- a VMID list, node list, or any other static inventory field — `source:` in
  `config/inventory.example.yaml` is source-only, no per-resource fields exist there
  either;
- any legacy REST mutation command, approval control, job control, or snapshot control
  — R0 is read-only end to end; there is nothing in `custom_components/hubinet_ops/`
  that issues a mutating HTTP call, and none may be added under this document's scope;
- any migration path importing 0.4 config-entry data, `secrets.yaml` values, or entity
  history — `async_migrate_entry` in `__init__.py` only handles future 0.5 config-entry
  schema versions (`entry.version == 1` today), it is not, and must not become, a 0.4→0.5
  bridge.

## 6. Dynamic inventory/UI contract

Confirmed by direct read of `custom_components/hubinet_ops/__init__.py`,
`coordinator.py`, `entity.py`, and `sensor.py`:

- `async_setup_entry` creates exactly one `HubinetOpsCoordinator` per config entry and
  calls `async_config_entry_first_refresh()` once; every subsequent refresh is one
  snapshot fetch through `HubinetOpsApi`.
- The coordinator is explicitly not a reconciler (per `CLAUDE.md`'s architecture
  section, confirmed by the coordinator's own design): it never infers `missing` by
  diffing two polls, and never assumes revision `N -> N+1` implies adjacency — the
  backend snapshot itself is the sole source of truth for what currently exists.
- Entities are generated from whatever the snapshot actually contains (sources, nodes,
  resources), parented in the Device Registry source → node → resource, via
  `entity.py`/`sensor.py` — there is no compiled-in VMID list anywhere in this code
  path, and no per-resource config to edit when a new guest appears in Proxmox.

This gives R0 the following acceptance contract for granted, natively, with **zero**
additional design work required in this document:

> PVE change → R0 discovers/reconciles → backend snapshot changes → HA coordinator
> receives it on its next poll → Device/Entity Registry reflects the change
> dynamically.

No config edit, no VMID edit, no reload-solely-to-discover-new-resources, and no
regenerate-and-redeploy-a-dashboard step is needed for a new resource to appear. This
is exactly what §3's retired 0.4 behaviors ("hardcoded VM100/CT101-CT110," "fixed
groups," "regenerate dashboard after new VM," "manual VMID addition") are replaced
with — not reproduced, but structurally made unnecessary.

### 6.1 What this document does not solve: the dashboard/card question

The above guarantees dynamic Device Registry and Entity Registry population — it does
**not** by itself guarantee a dynamic, auto-updating *dashboard card layout*. Home
Assistant's stock Lovelace model has two supported ways to present entities:

1. **HA's own native Devices/Entities pages** (Settings → Devices & Services →
   Hubinet Ops, and the auto-generated per-device entity list) — these are already
   fully dynamic: they read directly from the Device/Entity Registry and require no
   authoring or regeneration as resources appear or disappear. This is the initial R0
   presentation path, because it is the only mechanism already proven, by the code
   read above, to be truly dynamic with zero extra work.
2. A **hand-authored or auto-entities-style Lovelace dashboard** (e.g. an
   `auto-entities` custom card filtering by a Hubinet Ops device/label) can present a
   more curated view and *can* stay dynamic if built around a filter rather than an
   enumerated card list — but that is additional frontend design/authoring work this
   document does not perform. Building it is explicitly **not** in scope here.

What is explicitly rejected, per this mission's own framing, is solving this by
resurrecting `scripts/generate_ha_dashboard.py`'s pattern against the 0.5 snapshot: a
generator that produces N cards today and needs rerunning when a new guest appears is
still static, regardless of which backend it reads from, and is **not** an acceptable
0.5 presentation architecture. If a dedicated dynamic dashboard is wanted beyond HA's
native Devices/Entities pages, that is a real, separate UI-architecture decision for a
future design pass — not something this operational-readiness document resolves. Using
HA's native dynamic Devices/Entities pages as the initial R0 presentation is accepted
here specifically because it is the only currently-supported, already-verified-dynamic
option, not because the dashboard question is considered closed.

## 7. Relationship to the R0 activation runbook

`docs/operations/0.5-r0-operational-activation.md`'s Home Assistant phase requires,
in order:

1. **HA CLEAN-BREAK GATE** — §4.3 of this document's acceptance condition holds on the
   real HA instance.
2. **Legacy 0.4 surface confirmed absent** — the operator has recorded the §4.2
   evidence and independently re-checked the §4.3 checklist.
3. **Fresh 0.5 enrollment** — a new config entry is created per §5's boundary.
4. **Dynamic inventory acceptance** — the operator confirms a real PVE inventory change
   (e.g. a new/removed guest) is reflected in HA's Devices/Entities view without any
   manual HA-side edit, per §6.

The runbook must not be read as permitting 0.5 enrollment to begin while any 0.4
dashboard/package/MQTT surface is still active on the same instance.
