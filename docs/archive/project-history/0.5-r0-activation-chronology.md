# Archived project history — 0.5 R0 activation chronology (WAVE B0/R0-A/R0-B/R0-C)

**Status: ARCHIVED HISTORICAL NARRATIVE. Not architecture authority. Not a
current implementation map. Not a roadmap.**

Read `docs/architecture/README.md` first. Ordinary implementation agents must
**not** read this file by default.

## Why this file exists

`docs/architecture/0.5-implementation-status.md` had grown into a ~2,200-line
mixture of two different things: a current implementation map, and a long
review-by-review / PR-by-PR / dogfood-by-dogfood narrative of how the 0.5 R0
read-only runtime reached operational GO.

The narrative half is preserved here **verbatim**, unedited, so that no
historical fact, commit SHA, review finding, or operator observation is lost.
The status document now keeps only the current map plus a pointer to this file.

Nothing was rewritten to make history look different from what it was. Where a
sentence below says "current", it means current *as of the moment that sentence
was written into the status document*, not current today. The single source for
current state is `docs/architecture/0.5-implementation-status.md`.

## Authority

- This file is **non-normative**. It authorizes nothing.
- Where it conflicts with an ACCEPTED ADR, the ADR wins.
- Where it conflicts with the current implementation status document, the
  status document wins for "what is true now".
- It grants `security_continuity=trusted` nowhere, selects no Blocker-B
  mechanism, and authorizes no mutation, schema, runtime, or Home Assistant work.

## Contents

1. ADR/wave acceptance and review narrative (former status-document preamble).
2. WAVE R0-A / R0-B narrative (design and implementation history).
3. WAVE R0-C narrative — the automated Proxmox bootstrap, its seven corrective
   review passes, the three real dogfood runs, and the historical PR #43 / PR #47
   operational checkpoints.

The current, condensed outcome of all of it: R0 is implemented, merged,
deployed on a real host, and the R0 operational decision is **GO**, strictly
read-only, mutation authority **NONE**, Blocker B **OPEN**.

    storage, network, PVE endpoint, TLS strategy, the detected source

    had a second, separate "Deploy exactly this commit?" prompt
    immediately after it, which has been removed. `--yes` may skip that
    one remaining prompt (interactive invocations only) but never makes an

    `app/inventory/publication.py` and

    genuinely **committed, fresh, current** result, not merely

    NOT required to be non-empty). A source stuck in `not_yet_observed`,

    committed context, zero nodes, `configuration_error`/
    `source_unavailable`, or a discovery/auth/TLS failure never yields a

    insufficient. This runs inside the CT as
    `deploy/lib/hubinet-ops-bootstrap-accept.py` (python3, already

  - **Secrets**: the PVE API token and the R0 API bearer token are never
    passed as a literal command-line argument to any process (not
    printf, not jq/python3/awk, not curl) -- every helper that needs to
    read secret-bearing content takes a file path and reads it
    internally (e.g. `awk` reads the PVE token via `getline` from a
    restrictive temp file inside its own `BEGIN` block; the discovery-
    acceptance script reads the R0 bearer token directly from
    `/etc/hubinet-ops/agent.env` inside the CT). Secrets are never moved
    into an exported environment variable as a substitute fix (that only
    relocates, not closes, the exposure surface).
  - **Rollback**: cleanup of PVE-identity objects and the CT's service
    state is gated on an "attempted" marker recorded *before* the first
    mutating call in each phase (not a success-only marker recorded
    after), so a command that mutates PVE/CT state but still reports a
    nonzero exit for an unrelated reason is still evaluated for cleanup.
    PVE identity is a **cluster-wide** namespace: a second corrective pass
    closed a TOCTOU ownership race where two concurrent bootstrap runs (or
    any other creator) racing for the same fixed user/role/token name
    could make the *losing* run's rollback delete the *winning* run's
    legitimately-created object, via a random per-invocation
    `BOOTSTRAP_RUN_ID` embedded in every PVE object comment this bootstrap
    creates that supports one (user, token). A **third** corrective pass
    closed a narrower residual gap in that same mechanism: the ownership
    check's `ledger_has` fast path proved only "this run created an object
    with this name *at some earlier point*," not "the *current* object is
    still that same object" -- if the object was deleted and replaced by
    another actor between this run's own successful creation and a later,
    unrelated phase failing and triggering rollback, the ledger-only fast
    path would still report "owned" and delete the replacement. Rollback
    now *always* performs a live read-back of the CURRENT object's comment
    immediately before deletion and requires it to carry this run's exact
    `BOOTSTRAP_RUN_ID` -- `ledger_has` is consulted only as diagnostic
    context (a more specific "replaced since creation" warning), never as
    an independent deletion authorization. A read-back command failure,
    malformed JSON, a missing object, or a non-matching comment are all
    treated identically: not owned, preserved, with a loud manual-
    remediation message. PVE roles have no comment/provenance field at
    all, so this live re-verification is structurally impossible for
    them -- the conservative policy is that PVE-identity rollback *never*
    automatically deletes `HubinetOpsR0Auditor`, regardless of ledger
    state (a stricter policy than the second pass's "only an ambiguous
    role-creation failure is preserved"); an orphaned role from a failed
    run is always left for the operator, with an exact manual-remediation
    command, and the next bootstrap attempt correctly fails closed at
    phase 6's pre-existing-conflict check until it is removed. A residual,
    structurally unavoidable race remains even with the live read-back:
    PVE exposes no atomic verify-then-delete (compare-and-delete)
    primitive for users/tokens, so an external actor could in principle
    replace the object in the narrow window between this run's read-back
    check and its subsequent delete call -- documented as an accepted,
    external-administrator-only residual risk, not claimed as fully
    closed. Every cleanup action remains idempotent. The container itself
    is preserved by default for forensic diagnosis (`--cleanup-on-failure`
    opts into automatic destruction instead); CT `onboot` is left at `0`
    on any failure path. A pre-existing VMID or PVE user/role/token is
    never touched by any rollback path.
  - **Pre-existing-conflict inspection is fail-closed** (third corrective
    pass): phase 6's checks for a pre-existing `hubinetops@pve` user or
    `HubinetOpsR0Auditor` role previously ran `pveum user/role list ...
    || true` and treated a command failure or malformed JSON identically
    to a genuinely empty result -- a transient `pveum` error or an
    unreachable pmxcfs would then be silently read as "absent, safe to
    proceed," letting the run create a PVE identity without a reliable
    conflict check. `deploy/lib/bootstrap-identity.sh::_assert_pve_object_absent`
    now distinguishes command failure, malformed JSON, a genuine conflict,
    and a genuine (valid) absence as four separate outcomes, and only the
    last one is ever a "proceed." A **fourth** corrective pass strengthened
    this further: array-validity alone (an earlier `_json_list_is_valid`)
    proved only "the top-level value is an array" -- a syntactically valid
    but semantically wrong array (`[{}]`, `[{"user": "..."}]` with the
    wrong field name, `["hubinetops@pve"]` bare strings, `[1]` non-object
    elements, `[{"userid": 123}]` wrong field type) would all pass that
    weaker check, and the field-lookup helper's own "no match found"
    result would then be indistinguishable from a genuine absence. New
    `bootstrap-common.sh::_json_list_has_string_field_schema` validates
    the exact minimum schema each caller depends on (an array of objects,
    each carrying the target identifier field as a non-null string) --
    deliberately not validating any other/optional PVE field such as
    `comment`, which real PVE omits when unset. The same class of
    check was applied to the rollback ownership read-backs
    (`_user_object_owned_by_this_run`/`_token_ownership_state`, the
    latter renamed from a boolean `_token_object_owned_by_this_run` in
    the eighth pass -- see the "second real dogfood" entry below),
    now requiring the `userid`/`tokenid` schema respectively before ever
    considering a comment match -- an unrecognized shape there means
    ownership is UNPROVEN, preserved, exactly like a read-back command
    failure) and to effective-permission verification (a new
    `_json_object_is_valid` requires the token-permissions read-back to be
    a genuine JSON object before extracting truthy privilege keys from it,
    so an unexpected top-level shape is an explicit STOP rather than an
    incidental one that happens to still fail the exact-set comparison for
    an unrelated reason).
  - **DNS resolver authority** (third corrective pass): a hostname
    `--pve-endpoint` previously resolved `--dns-resolver` only into the
    firewall's own allow-rule, with nothing tying it to the resolver the
    fresh CT would actually use at runtime -- a declared/actual mismatch
    would surface only later as an opaque discovery-timeout symptom, after
    the firewall had already activated. `--dns-resolver` is now
    authoritative for the CT from its very first boot: phase 3
    (`bootstrap-container.sh`) passes it to `pct create --nameserver`, and
    phase 10 (`bootstrap-firewall.sh::_verify_ct_dns_resolver_matches_declared`)
    performs a live read-back of both the CT's own PVE config (`pct
    config`) and its actual `/etc/resolv.conf` before any hostname
    resolution or firewall-rule generation -- a command failure, a missing
    PVE config entry, an unreadable/empty `/etc/resolv.conf`, or any
    resolver entry that does not exactly match the declared one is a hard
    stop before the firewall is ever generated, never a warning that the
    operator "should" make them match. If the selected template manages
    DNS via a stub resolver (e.g. `systemd-resolved`), this check
    correctly, safely refuses to proceed rather than falsely claim a match
    it cannot prove -- hostname mode is not currently supported on such a
    template; literal-IP `--pve-endpoint` is unaffected and needs no
    resolver at all.

- **Real-PVE precheck notes -- effective-permission JSON contract**
  (sixth corrective pass): a real-host read-only precheck against
  **Proxmox VE 9.2.3** disproved an assumption this bootstrap's
  effective-permission verifier had made about the shape of
  `pveum user token permissions`'s JSON output.

  Target: PVE 9.2.3.
  Observed command:
  `pveum user token permissions ha@pve ha-token --path / --output-format json`
  Observed structural result: `{"/":{}}`.
  (No credential or secret is recorded here or anywhere in this repository
  -- only the JSON structural shape.)

  This proves the command returns a **path-keyed** object -- for a token
  actually holding privileges at `/`, the real shape is
  `{"/": {"Sys.Audit": 1, "VM.Audit": 1}}` -- never the flat object of
  privilege names directly at the top level
  (`{"Sys.Audit": 1, "VM.Audit": 1}`) `deploy/lib/bootstrap-identity.sh`'s
  `_verify_effective_permissions` and `tests/_bootstrap_fake_pve.py`'s
  fake had both (independently, wrongly) assumed. Under the old flat-
  object assumption, real PVE 9.2.3's actual path-keyed response would
  have made `actual_keys` come back empty every time (the top-level `"/"`
  value is an object, never truthy `1`/`true`), deterministically failing
  phase 6's exact-set check on every real deployment even when the token
  was correctly configured -- fail-safe (an empty set never equals the
  required nonempty set), but for the wrong reason, on a supported real
  path.

  Fixed: a new `bootstrap-common.sh::_json_truthy_keys_sorted_at_path
  <file> <path>` requires the top level to be an object, the exact
  requested path (`"/"`) to be present, and its value to itself be an
  object -- privilege names are read only from that nested object, never
  flattened in from any other path. Any other shape (missing path, `"/"`
  present but not an object, non-object top level, malformed JSON) is an
  explicit STOP with a message naming the expected path-keyed shape,
  never silently reinterpreted as "zero privileges" for an unrelated
  reason. `tests/_bootstrap_fake_pve.py`'s `pveum user token permissions`
  handler now emits the same path-keyed shape by default (keyed by
  whatever `--path` value was actually requested, not hardcoded to `"/"`)
  so its own default/ACL-derived test path exercises the real contract;
  new regression coverage (both a local-safe pure-helper test class and
  an end-to-end smoke test class) proves: the real observed `{"/":{}}`
  empty-grant shape is schema-valid (and still correctly fails the
  exact-set comparison, on a correctness basis, not a schema basis);
  reordered keys, a missing required privilege, and an unexpected extra
  privilege are each handled correctly; a missing path key, a non-object
  value at `"/"`, a non-object top level, and -- explicitly -- the OLD

  **P3 -- exception-graph traversal only followed one edge per node,
  then (round 2) was bounded the wrong way.**
  `app/inventory_pve_transport.py::_exception_chain` originally used
  `current.__cause__ or current.__context__`, which silently discards
  `__context__` whenever `__cause__` is also set -- but Python preserves
  both independently (`raise X from Y` sets `__cause__` without clearing
  whatever `__context__` the runtime had already recorded), so a real
  `ssl.SSLCertVerificationError` reachable only through the discarded
  `__context__` edge on a node that also happened to have an unrelated
  `__cause__` would never be found. Round 1 rewrote this as a breadth-
  first walk of both edges from every node, bounded (as first written)
  by total queue *pops* rather than unique nodes visited, reasoning this
  was needed to keep a duplicate-heavy graph from doing unbounded work.

  queue happens only as a direct result of visiting a genuinely NEW
  node, and each such node pushes at most two references, so bounding
  UNIQUE visits at 20 already caps total pushes at 40 (and total pops at

  instead, and a real correctness cost: a genuinely distinct cert error
  within the first 20 unique ancestors could be missed simply because
  earlier duplicate references exhausted a pops-based budget first.

  non-cert `__cause__` is also set (both as a standalone helper test

  (every node's cause and context pointing to the same previous node)
  where a cert error 10 unique hops away is still found DESPITE the
  duplication; and the same shape with the cert error 25 unique hops
  away (beyond the bound) correctly not found.
